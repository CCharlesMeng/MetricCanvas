# 范围交付

## 开始实施

独立改动尽早在合适的干净 worktree 中实施，从已确认基线开始。记录本批文件范围；混合工作区的依赖改动若是必要前提，明确纳入范围或先解决基线，不能靠拷贝整个目录带入。优先复用本任务已有、适合该基线的 worktree。

普通的“提交并 push”只检查本批路径、当前提交与目标远端；输出范围摘要。用户要求合并其他分支、全仓盘点或范围不明时，才展开其他 worktree 和分支历史。

## 验证与提交

1. 从 `package.json` 的项目命令进入验证。指定 TypeScript 测试用 `pnpm test <测试路径>`，保留已有 `svelte-kit sync` 前置步骤；按改动选择 check/build/browser 验证。
2. 验收记录对应 checkout、基线提交、源码及锁文件内容、构建参数和测试命令。同一输入可复用已有结果；换基线、转移了代码或输入发生变化时，重跑受影响的检查。单纯补充交付说明不重复业务回归。
3. 交付前 fetch 目标分支，审阅本批 diff，显式暂存文件或属于本批的 hunks。混合文件仅移入本批变更；保留并行修改，不使用全仓暂存。语义冲突交由用户决定。
4. commit、push 后读取一次远端 ref，确认包含本次提交。推送被拒时 fetch 后重新核对，不 force push。

## 等待 CI

默认完成标准为推送已确认且 CI 已完成。分别报告提交、远端和 CI 结论，`expected/bypassed` 不代表通过。

从交付 checkout 执行：

```sh
node tools/scripts/wait-ci.mjs <完整提交SHA>
```

工具按该 SHA 定位 CI，用一个 watcher 等待，只输出新增的完成/失败步骤，最后核对提交和完整结论。正常等待复用这个进程；仅在失败、取消、查询错误或状态异常时额外诊断。进度说明聚焦新结果，不重复抄送未变化的阶段。

用户明确要求只完成 push、后台通知或其他完成点时，按其要求执行，清楚报告尚未完成的 CI；未来通知按用户授权使用可用调度工具，不能假称已安排。

## 收口

保留用户需要的构建产物后，收起本任务创建且已完成使命的 worktree。原工作区和历史 worktree 的其他修改保持原状。最终答复给出提交、远端验证和 CI 链接；真实服务或部署只报告实际运行过的结论。
