# 页面元数据定位与修复

把页面校验器视为证据源，不视为完备性证明。沿“失败现象 → 最早可控边界 → 最小修复 → 同路回归”完成闭环。

## 1. 建立现场

1. 确定目标页面、用户意图、失败入口和是否涉及查询页面数据源。
2. 读取 `CONTEXT.md`、`PAGE-METADATA.md`、`packages/page/src/version.ts` 和当前组件定义。先读 `docs/adr/README.md`，再按问题涉及的能力展开 ADR。
3. 查看 `git status --short` 和目标文件 diff；把现有改动当作用户工作，不覆盖。
4. 保留原始失败输出、JSON Pointer 路径和触发命令，在首次修改前建立错误台账。

若用户只提供一段 JSON，先将它视为单文档诊断；不把文件名、跨页导航或真实查询默认为已验证。

## 2. 复现并分层

对单文件或目录先运行：

```bash
pnpm exec tsx .agents/skills/repair-page-metadata/scripts/inspect-page-metadata.ts <file-or-directory>
```

读取 [references/validation-surfaces.md](references/validation-surfaces.md)，按其覆盖矩阵补齐必要证据。至少区分：

1. JSON 语法与版本；
2. 页面 Schema 与文档内不变式；
3. 文件名与跨页引用；
4. 数据上下文与取数单元清单；
5. DQE 真实执行、查询字段映射与结果字段契约；
6. 统一运行时与呈现；
7. 用户意图与业务口径。

一组错误若由同一个缺失引用、错误字段空间或旧版结构级联产生，只把最上游的一项列为根因，其余标记为派生错误。错误类型是路由线索，不是根因结论。

## 3. 定位最早可控边界

按以下证据优先级判定预期值：

1. 用户已确认的业务需求和口径；
2. 当前身份的数据上下文快照与已验证查询；
3. 经清单校验且真实执行的取数单元；
4. 当前 Schema、统一运行时和组件实现；
5. 样例和内嵌初始行。

第 5 层只能复现问题，不能用来猜测类型、字段角色、指标口径或查询意图。数据上下文不足时记录 `DATA_CONTEXT_ERROR`，说明缺少的确证，不发明字段、关系、维度取值或 DQE 协议。

根因落点：

- 文档违反当前契约：修页面元数据。
- 查询输出与契约不一致：回到取数单元验真或结果字段契约，不在组件中补偿。
- 文档合法但校验器漏报：先构造最小反例；用户授权修代码时，修单一真源并加回归测试。
- 页面校验通过但业务答案错：回到用户意图、指标口径和已验证查询；不通过改展示文案掩盖。
- 数据正确但展示错：再进入组件绑定、格式、布局和浏览器验证。

## 4. 实施最小修复

1. 每轮只修一个根因簇，保留用户未提及的显式设置。
2. 使用 JSON Pointer 定位到最小对象，同时检查该对象所在的引用链。
3. 在定义处修复：页面数据源、结果字段契约、筛选器、内容分区或组件各自保持局部完整，不新建局部补丁协议。
4. 保持三个字段空间分离：DQE 输出字段名只出现在查询、`queryField` 和原始内嵌初始行；组件只引用稳定页面字段 id。
5. 修复不得放宽 Schema、删除有效约束或将错误吞掉，只为了让生成文档通过。

每轮修改后立即重跑原始失败入口。如果错误数没有减少或新错误落在更上游，回滚该轮推断，重新定位。

## 5. 验证闭环

根据涉及的层级完成所有适用项：

- 目标文档的诊断结果为零错误；
- 文件位于 `pages/` 或包含导航时，整个页面目录校验通过；
- 查询页面数据源的取数单元重跑清单校验和真实执行，并证明返回行通过查询字段映射与结果字段契约；
- 修改了校验器、Schema 或组件能力时，加入能在修复前失败的最小回归测试，并运行相关包测试与类型检查；
- 问题与呈现有关时，在统一运行时预览精确页面修订，覆盖 ready / empty / error 与必要交互。

“`validate_page` 通过”只完成单文档结构和语义校验，不能单独作为查询正确、业务正确或呈现正确的完成证据。

## 6. 交付错误台账

用简洁表格报告：

| 现象 / 路径 | 根因层 | 修复 | 回归证据 | 剩余缺口 |
|---|---|---|---|---|

明确列出“现有算法未覆盖、本次用其他证据验证”的项。如果修复暴露了可稳定自动判定的新不变式，建议将它落到现有校验单一真源和回归测试中；不把该规则只留在 skill 文字里。
