# 多源查询定位与修复

用户说“联合查询”“多表关联”“A left join B”，或出现“每个成员必须显式消费全部组合业务筛选”“对象数据集不支持账期的查询”、补列未请求、重复键或关联缺行时读取本文。先确定查询关系，再定位最早失败的成员与规则。

## 先确认实际查询关系

| 页面声明 | 执行意图与读取入口 |
|---|---|
| `pagedJoin` | 按业务键补列；普通模式与 `records` 的行粒度、筛选豁免不同。按需分页读 `data.pagedJoin.pagination`，记录语义同时读 `data.pagedJoin.records`，历史完整关联另读 `data.pagedJoin`。 |
| `pagedUnion` | 多来源逐行合并，不按合同 ID 做横向关联。读 `data.pagedUnion` 和[多来源表格](multi-source-table.md)。 |
| `resultBindings` | 上游原始维度集合成为下游查询输入，本身不合并展示列。读[查询结果绑定](page-metadata/queries-and-bindings.md)；确认上游是当前页还是完整结果。 |
| `joinAggregate` | 对已声明完整结果做跨源计算。读[具名算子](page-metadata/compute.md)；当前页数据不能冒充完整输入。 |

下面重点处理按键补列。协议语义及完整示例分别见[数据源](page-metadata/data-sources.md)、[按需普通关联](page-metadata/examples/paged-join-query-page.json)、[按需记录关联](page-metadata/examples/record-join-query-page.json)。

## 建立可复现现场

1. 锁定实际加载的 Page.id、文件或修订、当前 Tab、组合源、表格消费者和成员原始查询；保留原稿及完整错误的 type/path/message。按入口完成旧页升级检查，不能用未加载的候选解释线上现象。
2. 先对原稿运行独立 `validate-page.mjs`，区分页面协议错误、真实 DQE 拒绝与成功空结果；记录实际 execute 请求、响应及最早失败的数据源。顶层 HTTP 200 或 retCode 成功时仍要核对查询项结果码。
3. 对每个组合成员列出下表；筛选来自成员消费集合，不将页面所有筛选无差别下推。查询参数与业务筛选分开核对，保留各成员静态条件和服务权限。

| 成员 | 普通查询源／实际分支 | 一行代表什么 | 唯一记录字段 | 关联键及类型 | 消费的业务筛选 | 不适用筛选及依据 | 查询能力证据 |
|---|---|---|---|---|---|---|---|
| A 主表 | 填原 source id | 如一条风险记录 | 真实唯一标识或待确认 | 如合同 ID／string | 如 period | 无或已声明项 | 数据上下文、已验证查询或真实请求响应 |
| B 补列表 | 填原 source id | 如一份合同当前信息 | 按实际契约 | 与 A 关联键对照 | 按实际绑定 | 如 period：无适用账期 | 同上；仅静态 JSON 不足 |

字段可输出不等于支持过滤；`output_fields` 未列某字段也不能单独证明该字段不可查询。用数据上下文、已验证查询及真实服务响应确认过滤字段和编码；有明确不支持证据时在创作期阻止错误下推。

## 成员业务筛选冲突

未启用 `records` 的普通 `pagedJoin` 要求每个成员显式消费组合成员的全部业务筛选。若 A 消费 period、B 不消费，会在 B 成员的 `/source` 路径报“每个成员必须显式消费全部组合业务筛选”。该规则检查绑定声明，不证明服务支持声明的字段。

对“A 有账期，B 没有；按合同 ID 补列”的场景，依次确认：

1. B 若已被补上 `period -> 账期`，先查其字段查询能力。B 不支持时移除错误绑定；把绑定加回只能消除结构报错，不能修复真实查询。
2. 仅在符合“主表逐条记录 + 多对一信息补列”的业务语义时评估 `pagedJoin.records`。按需模式保留 `pagination:{mode:"query",pageSize:10,batchSize:10}`，`records` 声明 maxBytes、timeoutMs；批次仍放 pagination，不沿用完整读取预算或本地 timeFilters。
3. 记录模式的 B 成员可用 `notApplicableFilters:["period"]` 显式声明该筛选不适用。此属性与成员 source/key 同层，且只允许记录模式非主表成员；不能同时在 B 消费 period、不能列未知筛选、不能取消其他业务或权限条件。
4. 核对真实记录行键后再形成可用修复。按需模式的 rowKey 必须投影 A 的真实唯一记录字段；合同 ID 可作为关联键，但同合同多条风险记录时不能当行键。非空声明、样本没重复或 `canSelectPage:true` 都不能证明记录唯一与服务分页能力。缺真实标识时保存未验候选并列明缺口，不发明 ID、复合拼接键或后端字段。

有界完整记录模式与按需模式分别按参考配置；不能为了豁免筛选而悄悄改成全量读取。无法满足现有协议的行粒度或服务能力时，说明需要后端关联或产品能力支持。修复保持既定左关联语义：补列缺匹配时主行保留，补充字段按声明缺失策略处理。

用同一页面做最小对照，逐次只改变一项并保存回执：

| 对照 | 能证明什么 |
|---|---|
| 普通模式，A 绑定 period，B 不绑定 | 应复现 B 缺少组合业务筛选的静态错误。 |
| 在该普通模式仅给 B 加 notApplicableFilters | 应仍被拒绝；该声明不是普通模式的通用跳过开关。 |
| 具备真实行键的记录模式，A 绑定 period，B 显式不适用 | 应通过结构校验；是否真实可执行继续看服务和关联结果。 |
| B 被加上不支持的账期绑定 | 结构可能通过；真实服务拒绝仍是未修复状态。 |

## 成员未请求、重复键与缺行

- **B 没有 execute：** 先核对 Tab 是否激活、A 是否成功且有非空关联键。A 失败或成功空集合时，依赖 B 可能不被调度；不能据此判断调度器故障，也不手工补发请求冒充页面执行。
- **重复键或主表少行：** 先区分记录行键与关联键。普通模式一键一行；多条主记录共享关联键应评估记录模式。核对 B 在该关联键上的基数，依据真实模型处理，不能用前端去重改变业务结果。
- **有 B 数据但投影为空：** 对照 A/B 原始字段映射、键类型、实际值及请求键范围，再看 projection 与缺失策略。保留真实业务键，不通过转类型、裁剪或补值猜测关联关系。
- **排序、列筛选或翻页后异常：** 核对当前选页成员、canSelectPage 与真实能力、total_count 和 offset/limit。记录模式的补列成员不能接管基准记录分页；不以当前页过滤代替全局语义。

## 验收与内网运行证据

按[后端分页优先](query-pagination.md)核对请求范围。A 应携带自己的业务筛选，先取当前页；B 仅按本页去重关联键补查，并保留自己适用的固定条件和权限。筛选不适用于 B 时，其请求中不应出现该筛选目标。真实有返回行时再核对一对多主行保留、补列缺匹配与翻页结果。

分别报告页面结构校验、合成执行、浏览器实际 HTTP 和真实内网服务结论。缺查询环境时仍完成静态对照与候选，列出未验证字段、行粒度和能力；静态校验通过不能当作查询成功，仿真结果不能替真实数据。

追查“内网为什么没定位出来”时，核对当时安装的 Skill metadata.version、整个目录的发行回执、页面原稿、实际读取的主题、validate-page 回执及 execute 响应。区分知识缺失、入口未命中、未执行已有步骤、数据上下文缺失与部署版本差异。协议知识中已有字段，并不证明当轮读取和执行了它；没有当轮记录时仅报告已证实的流程缺口，不猜测旧包、网络或模型原因。

完成结论须写清：根因落在哪个成员及规则、改动的绑定和模式、真实行键是否已确认、首次失败请求与尚未发起的依赖、是否改动引擎或 Schema。保留所有未验证项，不用“校验已绿”替代业务可用结论。
