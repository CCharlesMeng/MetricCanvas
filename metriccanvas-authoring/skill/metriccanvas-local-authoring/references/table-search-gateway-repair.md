# 全表文本搜索能力未配置：定位与修复

用于表格右上角搜索触发 `DQE_CONFIG_ERROR: 数据网关未配置全表文本搜索能力`。先确认搜索语义，再选择页面配置修复或集成应用的数据网关适配；本问题有现成协议可用，无需新增 Schema。

## 根因与判定

这条特定错误由 MetricCanvas 数据网关在编码生效查询时抛出，发生在该搜索查询进入 HTTP 传输之前：查询携带非等值 `search`，但创建网关时没有提供 `encodeSearch`。同页其他查询仍可能发出请求，应按失败的数据源和搜索操作核对，不能只看 Network 中有没有请求。

| 实际搜索声明／状态 | 语义与执行路径 |
|---|---|
| `props.toolbar.search.fields` | 文本包含搜索；普通非完整 DQE 查询下推时需要已验证的 `encodeSearch`。仅一个字段也仍是包含搜索。 |
| `props.toolbar.search.options` | 单字段精确搜索；引擎生成 `match:"equals"`，已有原生等值编码，不依赖包含搜索编码器。多个选项用于切换字段。 |
| inline、显式完整结果或组合查询源 | 按各自完整行域／成员查询规则处理。先追踪实际执行计划，不能仅凭表格用了 query 分页断定编码路径。 |

“暂无数据”既可能来自成功零匹配，也可能来自查询失败后的空表；结合控制台、`data-error` 和网关诊断判断。Schema 校验通过不证明部署的数据网关具备搜索能力。

1. 固定实际运行的页面修订、引擎构建版本和网关创建配置，与附件／本地同名文件比较。文件名相同不代表运行内容相同。
2. 定位报错组件的搜索声明、`data.main`、结果字段契约与 `queryField`；检查所有相关组合源成员和未激活 Tab，列出仍使用包含搜索的入口。
3. 捕获提交后的搜索状态和生效查询：页面字段 id 应映射到正确 `queryFields`；精确搜索应保留 `match:"equals"`。若页面已用 `options` 却仍报此错误，沿组件 → 会话视图 → 生效查询 → 网关检查旧引擎、旧修订或集成层丢失标记的位置，不能直接认定 DQE 服务不支持。

## 方案 A：业务接受输入完整值，修改页面

只有业务已接受精确匹配时采用；业务仍需包含搜索时走方案 B。将目标表的整个 `props.toolbar.search` 对象从：

```json
{"fields":["approver-name"],"placeholder":"搜索审批人"}
```

替换为：

```json
{
  "options": [
    {
      "value": "approver-name",
      "label": "审批人",
      "field": "approver-name",
      "placeholder": "输入完整审批人姓名搜索"
    }
  ],
  "defaultValue": "approver-name"
}
```

`field` 使用目标结果字段 id，替换示例 id 为目标页已存在的字段。`options` 与旧 `fields`、根级 `placeholder` 互斥，提示放在选项内。匹配方式由分支决定，**不在页面 JSON 增加 `match`**。该分支自 6.42 支持，旧页按[旧页升级](page-upgrade.md)处理；单选项隐藏选择器还需部署支持该呈现行为的引擎。多个字段分别列为选项，表示切换精确搜索，不表示多列 OR。补充槽的 `{data,field}` 引用适用条件按包内 `table.slot-search` 知识核对，不把页面数据源 id 当成数据槽名。

精确搜索去除输入首尾空白，保留前导零、`%`、`_`。普通指标查询追加 `filter.dims` 中的 `{dim_name:<queryField>,dim_value_list:[<完整输入>]}`；对象查询追加 `filter.fields` 中的 `{field_name:<queryField>,value_list:[<完整输入>],operator:"="}`。保留原有筛选、授权条件、排序和分页，不替换同字段既有约束；服务端同字段条件组合与大小写行为仍须真实请求验收。

## 方案 B：保留包含搜索，补数据网关适配

修改拥有实际网关实例的集成应用，在 `createDqeGateway({ ...原配置, encodeSearch })` 中提供适配器。接口为 `(item, search) => JsonObject`；`search.queryFields` 已是查询字段名，`search.query` 是提交的关键词。适配器接收已编码其他条件的查询项，返回增加搜索谓词的查询项，并保留原有条件、授权范围、排序与分页。

先取得真实 DQE 文本搜索协议及请求／响应证据，再实现编码和验收多字段 OR、字面字符、大小写、分页总数与导出范围。仿真网关的搜索字段只能证明仿真协议，不能复制为真实 DQE 协议。没有上游依据时交付明确缺口；不猜测 `like`／`contains` 等请求字段，也不安装空操作编码器来消除报错。不能用筛当前页或自动拉全表替代后端全表搜索。

本案例曾出现附件用 `options`、仓库旧同名页用 `fields` 的差异；审批人修改后，另一 Tab 的评审组织人仍有同样缺口。对照页面不是通用业务模板，现场仍须核对实际修订。历史浏览器回归拦截了请求，证明引擎发送等值条件，不构成真实 DQE 验收。

## 完成条件

- 完整页面校验通过，差异限于已确认的搜索对象；保留原 JSON 排版和其他页面配置。
- 使用原运行入口复现提交、零匹配和清空；搜索回到第一页，已有筛选与排序保持，清空后恢复范围。多 Tab／多源逐一验证，不把首个错误消失当作全部修复。
- 精确路径确认生效查询保留 `match:"equals"`，实际请求包含每个应执行成员的正确等值条件；本案例商务成员使用“商务审批人”，合同成员使用“审批人名称”，由各自 `queryField` 决定，不能全局写死。
- 包含路径确认部署实例已注入编码器，使用当前页之外的匹配记录验收搜索、分页、`total_count` 和全部匹配结果导出，不能只验“无报错”。
- 分开报告静态配置、模拟请求、浏览器交互与真实 DQE 的已验范围；缺少真实环境时明确标记待联调。
