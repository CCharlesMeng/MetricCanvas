# Authoring deployment and extension protocol 1.0

Deployment assembly is separate from the canonical bundle skill registry. A deployment selects exactly one registrationName (metriccanvas-platform-authoring or define-report) backed by canonical author metriccanvas-platform-authoring and service metriccanvas-platform-content. The deployment returns the same Skill path/bytes and five-tool surface; it does not create another authored Skill, change ordinary ask or claim recall-report migration.

A manifest formatVersion 1.0 locks bundleVersion, skill source SHA256, contracts source SHA256 and a list of extension selections. Each selection has a unique id, version, kind (business/data/component/system), registered implementation key, implementation source SHA256, compatible contract version and explicit priority. The host supplies a closed registry of actual implementations and their verified metadata. Never import a module, execute code or load a filesystem path supplied by a manifest. Unknown fields, IDs/implementations, duplicate IDs, incompatible versions/hashes or unrecognized kinds fail assembly. A selection cannot override core schema fields, tools, components or lifecycle strategy; a claimed capability that its implementation does not provide is rejected. Registered implementation source hashes are host-verified facts, not assertions that manifest self-signing makes code trustworthy.

The assembled immutable selection chooses real injected dependencies using existing ports. There is no company-name branch or replacement submission state machine. A component declaration alone cannot enable a new component: until schema, builders/editors, rendering and tests support it, reject it. System/data adapters must retain existing authorization, exact-reference, source-mapping and lifecycle gates. Business interpretations return provenance and ambiguity rather than overwriting governed core fields; unresolved same-priority conflicts fail or remain explicit ambiguity. No internal rules or credentials are bundled.

Local acceptance must exercise two alternative registered data or business implementations through the same public unified flow with trusted scope, source descriptor and candidate gates, plus unknown/hash/version/core-conflict rejection and single-author define-report resolution. These synthetic checks do not prove internal migrations or production routing. F1–F17 and real provider/H1–H15 evidence remain separately tracked. Deployment lock and implementation versions must be retained together for rollback.

## S7 completed local consumer boundaries

Business extension port propose(query,data_context,now) returns versioned provenance (formatVersion 1.0, providerNamespace, sourceRef, sourceVersion), the exact dataContextVersion and candidates. A candidate is a governed metric/dimension alias (matchedTerm,kind,businessDomain,canonicalName) or a bounded time expression (matchedTerm,kind=time,granularity,start,end). Unique authored validation belongs to the business module. No raw query, spec rewrite, schema or arbitrary overrides. Core discovery always runs first, validates target definitions and existing time/granularity semantics, preserves provenance and surfaces ambiguities. Core/extension disagreement cannot silently replace core selection. Explicit spec construction remains the model's controlled choice; compose validates the original governed context. Missing extension preserves default behavior.

System selections bind exactly current_turns, candidate_store, execution_records, lifecycle_service, lifecycle_programs, lifecycle_identities and recovery_authority through existing ports. A trusted base_system may provide defaults; a selected system must resolve all seven slots. Verify required port methods and stable_save/exact_read/operation_lookup capabilities. Construct existing gates, Lifecycle, submission and recovery coordinators from those ports; registering a replacement state machine/factory is forbidden. Method/capability validation is structural, not proof of remote guarantees. Public candidate→lost-ack→original-operation recovery tests must exercise two isolated synthetic systems.

Component capability extension choose(scope,candidates) selects a component type from the immutable summaries of existing hard-gated product candidates. It can only prefer an existing fully assembled/rendered type, cannot introduce a schema, override props or change data/fields. Explicit user pinnedComponent takes precedence and is validated by the original gate. Any non-string, unknown, hard-rejected or assembly-unsupported choice fails without fallback. This boundary supports replaceable selection policy over existing end-to-end components; truly new component types still require coordinated product schema, editor/builder, renderer and compatibility tests. Provider provenance is retained in the deployment selection lock. No configuration alone enables a new renderer.

Registered business slot is business_interpretation (propose); registered component slot is component_policy (choose). Data/system/business/component slot sets are disjoint. All collisions fail; priority never grants overriding authority.
