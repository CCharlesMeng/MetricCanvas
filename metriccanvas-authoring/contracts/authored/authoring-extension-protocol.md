# Authoring deployment and extension protocol 1.0

Deployment assembly is separate from the canonical bundle skill registry. A deployment selects exactly one registrationName (metriccanvas-platform-authoring or define-report) backed by canonical author metriccanvas-platform-authoring and service metriccanvas-platform-content. The deployment returns the same Skill path/bytes and five-tool surface; it does not create another authored Skill, change ordinary ask or claim recall-report migration.

A manifest formatVersion 1.0 locks bundleVersion, skill source SHA256, contracts source SHA256 and a list of extension selections. Each selection has a unique id, version, kind (business/data/component/system), registered implementation key, implementation source SHA256, compatible contract version and explicit priority. The host supplies a closed registry of actual implementations and their verified metadata. Never import a module, execute code or load a filesystem path supplied by a manifest. Unknown fields, IDs/implementations, duplicate IDs, incompatible versions/hashes or unrecognized kinds fail assembly. A selection cannot override core schema fields, tools, components or lifecycle strategy; a claimed capability that its implementation does not provide is rejected. Registered implementation source hashes are host-verified facts, not assertions that manifest self-signing makes code trustworthy.

The assembled immutable selection chooses real injected dependencies using existing ports. There is no company-name branch or replacement submission state machine. A component declaration alone cannot enable a new component: until schema, builders/editors, rendering and tests support it, reject it. System/data adapters must retain existing authorization, exact-reference, source-mapping and lifecycle gates. Business interpretations return provenance and ambiguity rather than overwriting governed core fields; unresolved same-priority conflicts fail or remain explicit ambiguity. No internal rules or credentials are bundled.

Local acceptance must exercise two alternative registered data or business implementations through the same public unified flow with trusted scope, source descriptor and candidate gates, plus unknown/hash/version/core-conflict rejection and single-author define-report resolution. These synthetic checks do not prove internal migrations or production routing. F1–F17 and real provider/H1–H15 evidence remain separately tracked. Deployment lock and implementation versions must be retained together for rollback.
