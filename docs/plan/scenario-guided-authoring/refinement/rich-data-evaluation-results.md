# 数据丰富度评测结果

## 结论

**数据范围确实影响业务内容，但增加数据不能单独解决复杂页面的生成稳定性。** 本轮同需求、同新版 Skill/工具，基础 3 域与丰富 7 域各 3 轮真实 DeepSeek 调用已完成。没有追加收费补跑，也没有在运行中修改 Skill、工具或原始产物。

基础组 2/3 正常收尾、3/3 有候选；丰富组 **0/3 正常收尾、1/3 有合法候选**。丰富组唯一候选用 **4 个章节** 承接规模、客户增长、目标对照和风险复核，基础组却用 5–6 章仍只能呈现已有业务对象/走势和能力缺口。因此“更有信息”与“更多章节”不同；本轮不通过复杂创作稳定性验收。

方法与预定预算见 [执行前计划](rich-data-evaluation-plan.md)，数据边界见 [独立能力核查](rich-data-capability-audit.md)，两轮深入对照见 [独立语义初审](rich-data-semantic-review.md)。

## 本轮执行

相同 `deepseek-v4-flash`、参数、Skill、新版工具、用户需求和预算，仅改变可发现业务域。丰富组新增客户增长、风险客户、赛道与行业经营。客户名匿名化为“样例客户-NN”；不外发原始行、完整页面或明细 HTML。单计划仍最多 6 个取数需求、每需求 6 指标，不为评测放宽产品契约。

新增四源在收费前均经公共 create 成功验真。为保持字段角色，排除 semanticHtml/detail；非趋势源显式投影账期元数据；只在选定维度唯一确定每一行时允许省略其他维度，仍不聚合或合并行。基础和丰富两组共用同一执行器规则。原客户名称未进入请求载荷。

合计 **30 次真实模型请求、1,001,908 tokens**，在预先规定的 6 轮/最多 36 请求范围内。token 包含缓存命中量，不等于账单金额。丰富组中位数 180,287 tokens，比基础组 150,360 高约 19.9%；且失败更多，不能宣称性能或成本改善。

丰富 1 的 `TOKEN_BUDGET_EXHAUSTED` 不是已实际消耗 350000 tokens：传输层在发下一请求前把已用量与保守输入/输出预留相加检查，故实际 180287 tokens 时可能停止。预算规则两组相同，不为成功临时增加预算。丰富 2 被拒绝的超额调用、丰富 3 缺 title 的调用不在已保存工具摘要计数里，原始模型响应仍保留它们；计数不是全部尝试数量。

原 runner 状态不改写：基础 2/3 为 `inconclusive`（通用 runner 不评业务质量），其余 `blocked`。不能把正常结束、合法候选和业务/视觉验收混为一谈。

## 内容覆盖：看字段绑定而非标题

| 能力 | 基础组 | 丰富组唯一已接纳候选 |
|---|---|---|
| 当前规模与主辅变化 | 有 | 有 |
| 业务对象规模/走势线索 | 有，但非因果贡献 | 有，按需省略无关趋势 |
| 客户增长名单及金额/环比核对 | 无客户维度，只能说明缺口 | 有 growth-table，实际绑定客户名、amount、change |
| 年目标与年推演绝对值对照 | 只有推演/目标支撑率，没有目标绝对值 | 有 target-table，实际绑定 annual-target/annual-projection |
| 客户风险复核名单 | 无，文字说明缺口 | 有 risk-table，实际绑定匿名客户及已有金额列 |

丰富候选只使用 4/7 个可发现来源，没有铺满目录，三个表格各自回答增长、目标、风险问题。保留了“名单不代表整体贡献、目标差额未计算、风险原因缺失、风险列不能串成可靠时间序列”的限制。没有人工写业务章节再让模型填空，也没有修改候选来补齐覆盖。

这里只能证明这 **1 份候选**有更丰富的证据展示；不能把另两轮没有产物的失败排除后报告“丰富组100%成功”。某些标题如“增长来自哪些对象”仍偏强，应理解为排查线索而不是已证实原因。

## 真正暴露的瓶颈

1. **purpose 与 intent 混淆。** `intent: detail` 合法，`purpose: detail` 不合法。丰富 1 第一次错，第二次误删 intent，第三次才改为 `purpose: reconciliation`。独立审阅按保存输入重跑 Schema 已确认根因。
2. **错误摘要不够具体。** 多处只返回 `STRUCTURE_PLAN_INVALID` 和整个块路径，没有指明 `/purpose` 及允许枚举。保密边界应保留，但可以返回安全的字段路径/规则信息；当前过粗反馈促成了无效试错。
3. **发现和修订成本增长。** 7 域让最初发现占用 9 次工具调用（基线读取、入口发现、7 次域发现）；若再重复发现，两次修订的空间就不足。工具上限是实验约束，失败说明当前流程在此约束下不稳，不自动归因为模型能力绝对不足。
4. **入口格式失败没有形成可恢复的安全反馈。** 丰富 3 丢失顶层 title 后，MCP 返回非结构化错误，runner 立即退出；属于模型错误和评测恢复能力共同作用，不是数据查询失败。

建议下一轮先改善上述局部契约理解和反馈，再按同一需求/样例复测；不建议直接继续扩域、堆章节或放大付费预算。**本轮只完成评测，没有实施这些 Skill/产品工具修复。**
