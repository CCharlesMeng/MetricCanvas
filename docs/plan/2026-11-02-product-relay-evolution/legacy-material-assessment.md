# 存量拆分材料对本轮探查的影响

日期：2026-11-02。结论：**保留页面先行/数据先行共享产品能力的主方向；将探查重点从目录归属推进到真实部署差异、完整工具契约加载、内部适配与运行语义。多槽表格提前成为同步机制的验收案例。** 本文评估三份用户提供材料，没有执行其迁移方案。

## 2. 本轮已确认的产品事实

1. **多槽表格确有产品基础**：`packages/page/src/schema/primitives.ts` 的 tableData 允许具名槽、要求 main；`validate.ts:1891` 起要求参与行对齐的槽声明同名、同类型的维度 rowKey。`packages/engine/widgets/src/components/table/rows.ts:17` 起按主槽行序和 rowKey 读取辅助槽；它不是全外连接，也不合并辅助槽独有行。
2. **工具表达缺口在上游也存在**：作者维护的 DATA_BLOCK 必填单个 source；`compose_contract.py` 从它派生 compose 入参，`block_component` 按单源取字段，`page_building.py:219` 生成单槽 data。离线 JSON Schema 探针中合法单源 block 通过，材料提议的 sources/rowKey/columnBindings block 被拒绝。因此刷新 Relay 的页面快照不能单独修复这一缺口。
3. **实际编辑路径要纠正**：`add_source_component` 在 `pages/editing/section_editing.py` 使用同一 DATA_BLOCK 和 block_component；材料所列 text_map_building 在本仓位于 `pages/components/`，主要负责文本、字段文本和地图。不能照所列路径机械改造所有组件。
4. **工具顶层函数名不变不等于契约不变**：`platform_mcp.py:12–14` 以 WithJsonSchema 注册完整 request Schema。公共契约应同源供给注册与 MC；Relay 即便不用手改调度代码，也须加载新描述、刷新相关缓存并证明实际注册接受新结构。
5. **firstparty 目前是内部实现**：ownership.json 将整个 adapters/ 列为 internalRoot；RELAY-HANDOFF 明确 Java/DQE、Relay 和存储的具体接线在内部维护。产品公共 Port/协议校验与特定端点、认证、响应映射分开；不因名称为 firstparty 就整体纳入公共内容包。
6. **共享接口不能成为两份自由修改的实现**：当前部署入口校验 AuthoringAdapters 的 isinstance 与接口版本。分别复制并从不同模块加载 dataclass 可能产生不同类型身份。优先共享唯一契约依赖；若确需生成投影，须验证来源一致、运行时类型及兼容性。

补充运行 `table-rows.test.ts` 与 `dqe-query.test.ts`，共 15/15 通过；证明本地表格对齐和相关页面契约，不证明真实 Relay、查询限制、召回或生产渲染。前轮 218 项回执仍独立保留，没有在本轮重新执行。

## 3. 拆分边界：不能只分成两个目录

| 职责 | 建议所有权与演进方式 |
|---|---|
| 两种创作策略及公共方法 | 页面先行/数据先行保留不同起点与顺序；共享核对、映射、修复和完成标准。单一作者源投影到两个安装目录；Relay 修改过的决策规则先逐段盘点再归并 |
| 公共创作脚本与用例 | 页面分析、需求/证据关联、受控装配/增量变更、结果作用域、工作版本/CAS、保存协调和诊断由产品维护；沿现有协调器，不退化成只返回页面 JSON 的 compose 函数 |
| 公司服务适配 | Java/DQE/元数据、认证、字段映射、存储后端等属于内部适配实现；通用算法可经审查抽回产品，专有连接继续独立安装 |
| Relay 运行时接线 | loader/SDK、可信上下文注入、文件/进程通道、卡片占位符与 spool、模型/程序通道包装由 Relay 维护；实现产品定义的 Port，不能另定保存与结果有效期语义 |
| 页面协议 | Schema、字段绑定、查询/计算/渲染语义在产品真源维护；两种策略共享 |
| 创作工具协议 | 完整输入/输出、错误、partial/保存行为与业务实现同批演进；不能由 Relay 手写一套长期冻结的 request Schema |
| 适配和产物交接协议 | Adapter Interface、工作副本输入、artifactEnvelope/预览回执分别版本化；由产品定义公共语义、集成实现端口，不将所有版本绑成同一个号 |

“架子不动”的可验收含义应是：**兼容升级无需手改 Relay 调度逻辑，但注册描述、产品包、知识/脚本与版本组合会更新并验证。** 不承诺所有未来接口升级都零改动。

目录迁移后 import 不变也不是天然成立：须先查包构建、入口、资源寻址和依赖方向，再决定兼容导出或改包路径。`mc-tools` 可以是发行目录名，不能直接当普通 Python import 包名使用。拆分应减少跨边界知识，不能只换目录后保留原耦合。

## 4. 多槽表格：作为同步验收案例，而非现成补丁

材料给出的 sources + columnBindings 可作为候选输入设计；本轮不冻结其最终字段。实施须补齐：

- 单源兼容、多源仅表格、main 必选；明确顶层 sources 的 resultRef 映射与 block 内槽→源映射的不同含义，避免歧义。
- 每槽结果引用的授权、版本、字段契约、查询条件与完整性依据；不能拼接过期或异作用域结果。
- 多槽必须有稳定 rowKey，核对同粒度、键类型和实际数据；重复键、缺键、空槽、失败槽、截断与分页覆盖逐项明确既有语义，不静默取第一条冒充验真。
- 列字段使用明确的槽归属，保留来源单位、格式、期间、缺值语义；同名字段不能从主槽猜测。rowKey 与有歧义的跨槽列映射不能以“可选”掩盖缺口。
- 新建多槽表、在已有数据源上加表、从多个 resultRef 加表、修改已有表的槽/列、合并两张已有表是不同操作，分别登记支持范围。补 add_source_component 不会自动提供保留页面意图的合并/重绑定能力。
- 不默认扩展 ExecutableUnit 来携带呈现槽。它目前是 frozen/slots 的取数单元，一个取数单元对应一个页面数据源；多槽组件应在合适的装配职责连接多个源，先明确责任再选实现。
- 不将多槽行对齐、pagedJoin、resultBindings 级联和期间对比当作同一能力。业务“收入+同比+环比”可作场景；为何分查询、期间/分母如何确认，要有实际环境与执行证据。

recall-report/unified_dsl_execute/nl2sql_prefetch 在本轮限定搜索的公共实现中未定位到。材料说明了另一个执行入口，应加入探查。读取已发布页面不走 compose 入参，只能说明入口不同；是否正确执行多槽源、级联、空集合、参数、权限和错误，仍须单独验证，不能推导“自然召回”。

## 5. 对迁移计划的具体调整

1. **M0 增加部署差异台账**：参考源、Relay fork、安装副本、进程实际加载、模型可见注册五者对账；用完整 inputSchema 和内容指纹，不只对版本号。材料列出 15 个工具，本地公共注册为 9 个；差异中的桥接入口不等于底层能力不存在，须逐项定位新增、改写或未注册。
2. **增加同步验证支线 T1**：M0 后，以多槽表格重现“页面可用/工具拒绝”，再设计最小产品补齐与整包更新验证。可与 M1–M5 的页面先行闭环分开推进；不要求先大搬目录才修复。
3. **保留 M4 的首条切片**：仍先做保留合法表格意图的普通查询源替换。多槽新建证明数据先行装配及同步，普通源替换证明页面先行增量接数，二者不能相互替代验收。
4. **M5 增加 Relay Skill 差异归并**：核对实际 SKILL、引用规则和调用回放，将真实改良分为共享方法、产品事实、Relay 接线和部署约束。避免用参考 Skill 覆盖 Relay 已有迭代。
5. **M6 增加实际采用与召回对账**：产品实现/契约 → 实际 MCP 注册 → MC/local 投影与工作流 → 安装/部署组合 → 创建/编辑/预览/召回回放。每个阶段记录摘要、支持条件和未验项。
