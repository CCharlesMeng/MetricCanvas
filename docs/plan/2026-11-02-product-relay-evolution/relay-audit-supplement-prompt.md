# Relay 现状审计补充提示词

将本段与原现状探查提示词、三份存量设计材料一起交给能访问 Relay 源码及安装环境的 Agent。目标是只读核实；不执行拆分、升级或产品修复。

---

你需要核实 Relay 当前 authoring Skill 与 MetricCanvas 产品的真实接缝，为两种创作策略整合和独立同步提供证据。

已确认的产品方向：

- 页面先行：页面结构/交互意图 → 用数需求 → 数据发现和验真 → 映射接数 → 完善页面。当前 local-authoring 承载，也将进入线上用户自定义闭环。
- 数据先行：业务需求 → 数据发现和验真 → 据结果组织页面。当前 Relay authoring Skill 主要承载。
- 两者共享页面 Schema、运行时、公共创作能力；保留不同起点和步骤。不能把“本地/线上”当成策略边界，也不能仅合并两份 SKILL.md。
- 本次附带的三份拆分材料是待核实的设计/历史线索，不能据此宣称代码已改或部署已采用。

请在可用工具范围内充分调查。可以合理使用最多 3 个 subagent，建议分别调查 Skill/加载/注册、公共源码差异/适配、工作状态/预览/召回。主 Agent 必须交叉核实边界结论，不能直接拼接分工报告。先冻结身份和来源，再并行；对冲突保留双方证据并补查。不得启动子 Agent 就停止主任务。

审计只读，不改源、不覆盖安装、不清缓存、不重启生产、不执行保存/发布或业务查询、不调用付费模型。允许不连真实服务的离线注册与合成夹具；若启动代码可能连接服务或修改状态，先静态定位，并报告尚未执行。

必须回答以下 8 组问题：

1. **真正运行的是哪一份？** 找到仓库源、安装 Skill、local_mcp_servers、Python 环境/wheel、loader/入口及实际进程加载来源。记录 Git SHA/dirty、Skill/Schema/工具/Adapter 版本与文件摘要。拿不到进程或客户端权限时明确未知。核对材料中的 6.11、上游工程名与会话 `2bf03612db664601a38b305268ec9452`；不能沿用文字当事实。不要输出凭据、业务原始数据或用户隐私。

2. **旧 Skill 经过哪些真实改良？** 以可获得的共同提交/安装快照做差异，不只看 changelog。逐段归类：策略路由、需求/口径核对、工具选择与顺序、期间/多源处理、失败恢复、续轮、保存发布、正文/spool、MC 检索和私有规则。标出哪些可共享到页面先行，哪些只能保留在 Relay。至少以调用点或脱敏回放核实关键改良的生效路径；没有历史基线则不虚构演变过程。

3. **完整工具契约如何进入模型？** 导出实际注册的工具名、完整 inputSchema、输出包装和来源摘要。材料提到 compose/edit/publish/read/discover/query/preview、submit_ai_summary_body、list_existing_page_urls、tool_mc_query/compile/inspect、三项参数工具，逐项查存在性。跟踪 authored Schema → Python/Pydantic/FastMCP → loader/SDK → 模型可见描述；查是否存在手写 Schema、旧缓存、Schema 裁剪或转义。用同一多源 block 比较内容侧校验、离线注册校验、Relay 包装校验；不能只比较顶层函数签名。

4. **模块接缝与公司适配怎么分？** 从实际调用图识别公共用例、Java/DQE/元数据/存储适配、Relay 身份/上下文/卡片接线。不要将整个 firstparty 目录自动列为公共内容。核对 AuthoringAdapters 的类型身份、接口版本和装配；若复制为两份，调查 isinstance/导入路径风险。说明稳定 API 是否保留 mutate 协调中的版本竞争、保存、unknown 与回执，还是只返回页面 JSON。提出最小可抽离边界，不先假定新建 mc-tools 或大搬目录。

5. **状态、引用和副作用由谁保证？** 跟踪 context_ref、工作副本/基线、workVersion/CAS、resultRef/artifactRef、授权和数据上下文版本、文件 spool、缓存、保存/发布、预览、取消、迟到、unknown。明确哪些是产品语义、哪些是 Relay 存储/传输实现。区分当前 working-copy 输入模式与旧 current_match 模式，不强制两者都回读远端覆盖基线。记录一次变更到底在哪里保存、失败/重试是否可能再次保存，不能用设计图替代调用证据。

6. **多槽表格在哪些路径受阻？** 追踪 DATA_BLOCK、compose_contract、block_component、组件生成、section_editing/add_source_component、resultRef 新增路径及现有表修改路径。材料所列 text_map_building 路径可能不准。分别核对：新建多槽表、引用已有源新增表、从多个结果新增表、修改已有表槽/列、合并两张表。用合成数据测试主槽定序、同名同类型 rowKey、明确列槽归属、同名字段、单位/期间、缺行/空槽/重复键/错误槽/截断/分页。保持现有执行规则，不凭渲染成功宣称完整性已验真。来源限制明确时可仅静态核实，留下可执行探针。

7. **召回和真实查询约束在哪里？** 找到 recall-report、unified_dsl_execute、nl2sql_prefetch 的实际仓库/插件/代码及版本；定位不在本仓时明确外部依赖。核对已发布页面的读取、参数与权限、每槽取数、resultBindings 级联分批、空集合跳过、失败传播和预览实际采用哪套执行实现。不要从“不走 compose”推出“多槽自然能召回”。查“F5 同环比不能混查”的规则、作用环境、请求/诊断证据，区分查询协议限制、后端限制、Skill 规则和个别失败经验；拿不到证据则标为未确认。

8. **目前如何同步，怎样验证采用？** 检查 sync_upstream.py、allowlist/ownership、锁文件、生成器、手改文件、部署脚本和回滚。找出公共更新会覆盖/跳过哪些 Relay 改动；分别记录源码、工具契约、实际注册、MC、Skill、页面引擎和召回插件版本，禁止用一个 schemaVersion 代表全部兼容性。提出最小升级组合及兼容检查，允许兼容升级不手改 Relay 调度，但不能冻结旧 request Schema；对客户端缓存与活动轮次说明何时更新。不要执行更新。

交付一个可带回另一仓库继续规划的目录，至少包括：

- `report.md`：结论先行，给出真实加载链、Skill 改良、职责边界和迁移建议。每条关键结论有文件/符号/行号或脱敏探针；区分“本轮已核实 / 材料声称 / 推断 / 未取得证据”。
- `tool-contracts.json`：实际离线注册的完整 Schema、工具来源、摘要、采集方式和进程/客户端是否对账。无法取得实际注册时保留静态契约并显式降低证据等级。
- `source-diff.json`：公共基线、Relay 改动、安装/运行差异；每项标注产品补齐、共享方法、私有扩展、内部适配或待确认。缺共同基线时记录缺口，不伪造 diff。
- `seams.md`：每条接缝的调用方/被调方、输入输出、状态/副作用、版本与缓存、保留的内部实现、建议归属及证据。覆盖策略 → 脚本/工具 → 协议 → 部署/召回。
- `evidence.md`：命令与退出码、源路径/摘要、合成输入和输出、未运行项、矛盾与限制。关键摘录足够复核，不携带原始业务数据、凭据或仅在该机器可访问的唯一证据。

最后给出：应先同步而无需重构的内容、必须先补产品能力的缺口、真正需要 Relay 改造的接线、不能确认的事项。不要在审计中实施建议。
