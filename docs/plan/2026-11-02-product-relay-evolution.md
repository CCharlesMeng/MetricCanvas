## 1. 两种逻辑的起点与完成目标

| 项目 | 页面先行创作 | 数据先行创作 |
|---|---|---|
| 起点 | 已有页面、设计稿、期望结构/交互与用户自定义意图 | 业务问题、用数需求、可用数据能力与查询证据 |
| 推进方向 | 页面结构 → 用数需求 → 数据匹配/查询验真 → 映射绑定 → 完善页面 | 需求/口径 → 发现与查询验真 → 数据形状/证据 → 页面表达 → 完善页面 |
| 先保留什么 | 用户确认的结构、组件、布局和交互意图；已有可信绑定 | 业务口径、授权范围、结果字段、粒度、完整性与证据 |
| 数据不满足时 | 保留页面意图，标出具体用数缺口；结构调整要解释并取得相应决定 | 不凭空补结论；缩小或调整表达须保留口径和缺失说明 |
| 完成目标 | 页面按用户意图接到可信数据并运行，用户可继续修改和复验 | 证据形成合适页面，用户可继续定制和补数 |
| 当前主要载体 | local-authoring 的页面编辑、用数扫描/匹配与候选准备 | Relay 参考 Skill 的 discover/query → compose/edit |
| 长期承载 | 本地可独立用，也可作为线上页面自定义闭环 | 线上为主要现有入口，也可由其他可信集成消费 |

两者可在同一创作会话内衔接：数据先行生成第一页，用户随后固定布局并补接数据，转入页面先行；页面先行中发现一个新分析问题，可以进入数据先行补查，再回到原页面。切换不会自动生成另一个页面、丢弃工作副本或重置已确认意图。

## 2. 统一整合的范围

整合需求与约束表达、用数需求提取、数据能力发现、查询验真、字段/语义映射、受控页面变更、依赖影响分析、校验、预览和修复。不强制把两条逻辑合成相同的步骤顺序，也不要求立即物理合并成一个巨大 Skill。

| 层 | 共享什么 | 保留什么差异 |
|---|---|---|
| 创作策略 | 可复用的口径核对、解释、缺口处理和完成标准 | 页面先行与数据先行各自的入口、顺序、结构选择和用户决策 |
| 创作能力 | 页面用数分析、取数单元、数据发现/验真、映射、绑定、增量变更与影响分析 | 不同起点调用哪些能力、已有意图/证据如何成为约束 |
| 共同创作记录 | 当前工作副本、已确认约束、用数需求、映射状态、查询证据、待解决缺口与变更依据 | 本地文件/快照与线上工作稿/轮次的持有、存储与权限方式 |
| 产品知识 | Schema、组件/数据源/绑定规则、引擎语义、公共工具事实、布局与诊断 | MC 在线检索投影与 local 独立目录的包装 |
| 产品执行 | 相同 PageDocument、校验、共享查询执行、渲染与导出 | 各宿主获取文档、注入数据网关、保存和展示产物的方式 |
| 接入 | 版本化 Interface 和统一的可信证据要求 | 本地文件工具、线上工作台、Relay/云宝加载与权限/程序通道 |

共同创作记录是职责清单，不在本次发明一份新的通用状态协议。优先扩展现有工作副本、取数单元和分析报告，以稳定页面/组件/数据源标识关联需求和证据；不再另建与工作台或 Relay 竞争的创作会话系统。

## 3. 两套 Skill 如何整合

### 3.1 方法论保留两个入口，公共能力共享

页面先行工作流主要负责：理解期望页面、识别已有可信部分、提取组件和交互的用数需求、数据对接、保留页面意图并迭代。数据先行工作流主要负责：澄清业务问题、确定用数范围、取得证据、依证据组织表达和正文。

两者共同调用“分析用数—发现/查询—核对映射—应用变更—校验/预览”等能力，按需复用方法片段。产品事实只在真源维护，投影到 MC 与 local；方法论不是机械复制两份，也不是全部塞入 mc-content 的协议说明。

当前继续交付 local 独立 Skill 和 Relay 参考 Skill；先共享能力与验收，再根据实际使用决定是否在一个线上 Skill 中提供两个路由。不以引入多 Skill 框架或重命名现有安装目录为前置。

### 3.2 线上入口按任务与创作状态选择逻辑

- 用户提供页面/设计或明确固定结构，要求接数、换源、补字段或自定义交互：优先页面先行。
- 用户提出业务问题，希望据数据得到合适表达：优先数据先行。
- 仅改标题、布局或已有可信绑定：直接局部修改，不重复发现/查数。
- 存在页面不等于必须页面先行；在已有页面上新增一个分析问题仍可数据先行。起点不明确时只澄清影响结果的选择。

路由必须接续同一工作副本与证据，不因切换逻辑重跑全流程；计划确认、查询授权和保存状态仍各自核对。

### 3.3 缩短默认路径，将确定性检查收进工具

按[创作流程与 Skill 职责整理](2026-11-02-product-relay-evolution/skill-flow-simplification.md)细化 S2/M1/M5：根入口只保留任务路由与共通不变量，产品事实和布局组合按需查阅；语义、格式和绑定检查由现有取数与页面用例内部承担，不新增模型闸门步骤或公开工具。工具先验证承接的正确性，再删除对应重复提醒；独立安装的生成知识保留完整。

该整理目前仅为设计，含文件处置表、目标入口骨架、数值错误走读和实际加载量验收。运行代码、Skill 正文和分发包未按此切换；既有权限、保存恢复和交接契约继续有效。

已读取并对齐[「优化 mc-content 创作规范」会话](codex://threads/01a19b3f-9a13-7c42-92c8-c7d13ddc4a6d)。执行规格的[接缝 D4/I08](2026-11-02-product-relay-evolution/implementation-seams-v1.md#d4-现有工具承担呈现正确性随后做流程减法)明确首批呈现纠错、独立呈现工作树复用及 local 同源承接；“普通任务步骤/阅读减少、工具先承接再删提醒”作为整合验收条件，不另增创作检查流程。

## 4. 当前能力怎样归并

| 当前能力与位置 | 统一后的角色 | 需要补的工作 |
|---|---|---|
| local 的 scan/find/index/draft/check/prepare；`local-authoring-data-analysis.ts` | 页面用数需求提取、材料证据与映射准备的基础 | 提取宿主无关核心；区分材料匹配和真实元数据/执行证据；支持线上受控调用 |
| local 的页面编辑、升级、快照、校验与预览修复流程 | 页面先行策略及变更/验证能力 | 在线工作副本接入、受控变更与回执；不能仅开放服务器文件写入模拟上线 |
| 公共 discover_data_context/query_data、Python data 能力 | 两种逻辑共用的发现、授权和真实查询验真 | 接收从页面提取的用数需求；保留来源位置与约束，不另写一套查询逻辑 |
| compose_page / edit_page、Python pages 能力 | 证据到页面和增量页面变更 | 补页先行所需的源对接/字段映射/绑定更新；保留原组件身份、布局和共享依赖 |
| 产品参数、筛选、跨源计算、共享查询执行 | 两种逻辑共用的产品语义 | 对两个方向核对可用入口与行为，禁止仅更新一个方向的知识或工具 |
| MC、local 知识生成和平台参考事实投影 | 同源产品知识的两个消费投影 | 记录每项能力在哪个方向、哪个宿主、哪个公开入口可用 |
| 工作台/创作画布、Relay/云宝、Java | 线上用户继续定制、执行和保存的承载 | 适配共同创作记录、权限、冻结快照、预览与现有保存路径 |

当前 Schema/local 校验器为 6.77，公共目录 19 类组件，compose 数据组件 10 类，公共 MCP 9 个、edit 36 个分支。这些数字只能说明表达/工具范围，不能证明“页面到数据对接”或“数据到页面”任一完整任务已闭环；详见能力盘点。

## 5. 线上页面先行闭环要补齐的产品能力

1. **取得用户当前页面意图和工作副本**：同时覆盖新设计、已有页和未保存人工修改，沿 ADR-0118 冻结快照；不要重新读取远端页面覆盖它。
2. **从页面反向提取用数需求**：定位组件主值、序列、表列、详情、筛选/参数与依赖；保留页面位置、口径、单位、粒度、行身份、期间和完整性要求。
3. **复用数据发现与验真**：对匹配、歧义、缺失、口径冲突分别处理。模型匹配、MD 原文和产品结构校验都不能代替真实执行。
4. **提出并应用增量对接方案**：说明哪个页面数据源/字段/绑定变化、影响哪些消费者；保留不相关布局、交互和已验证数据。共享源变更做依赖闭包分析，不整页重建。
5. **用户核对并继续迭代**：呈现实际数据与预览、说明未完成位置，允许修改页面或口径后定向复验。沿现有可信保存/发布路径交付，不新增另一套资产治理。

现有 analyze-data 只是其中一部分，当前 MCP 也不保证拥有所有需要的源/绑定编辑操作。线上化须新增或扩充受控产品 Interface、程序通道和前端交互，再更新 Skill；本次不假称这些已存在。

页面意图、待匹配需求和未完成绑定是创作期状态，不直接塞入渲染 Schema。候选不完整时保存在创作记录中；正式交给引擎的 PageDocument 仍需满足现有完整引用和语义约束。已有演示 inline 必须标明性质，不可由演示行推导真实字段/口径或伪装接数完成。

## 6. 共享能力的连接契约

以下是待设计的内部连接要求，不是新增 MCP API 或第二份 Page Schema：

- **用数需求与页面位置的关联**：复用取数单元，关联组件/字段/筛选和稳定源 ID，说明需要何种粒度、口径和结果形状。
- **数据映射与验证证据**：区分已匹配、歧义、缺失、冲突；字段映射必须能追到真实输出与授权范围，证据变动使受影响映射重新核对。
- **页面意图和保留约束**：记录用户固定的结构/展示与已验证数据事实，遇到不兼容时解释选择，不静默改布局或粒度。
- **增量变更与影响范围**：绑定/源变更指向当前基线和版本，覆盖共享消费者、依赖、筛选/参数；结果按应用/失败/跳过及原因返回。
- **验证与交付事实**：页面合法、数据可信、意图满足、预览正确、保存回执分别判定；继续使用已有真实回执和 unknown 处理。

本地 TS 分析核心、公共 Python 创作与 TS 产品语义通过小 Interface 复用各自实现，不为统一而先重写一种语言，不重复查询执行/单位/绑定校验规则。

## 7. 如何同步演进

每项产品能力记录五个维度：产品声明/执行、页面先行流程、数据先行流程、宿主适配、知识与验收。覆盖分母来自产品能力/组件/数据源/规则和业务闭环，不能只数已登记的工具。

| 变更 | 同批必须核对 |
|---|---|
| Schema/引擎新增能力 | 两个方向如何形成声明/取得证据/创建或修改；MC 与 local 投影、公共工具、实际场景和限制 |
| 页面先行新增能力 | 页面需求提取/映射/变更共享核心；离线现有路径、线上目标入口；数据先行产物能否无损接续 |
| 数据先行新增能力 | 发现/查询/表达公共核心；结果能否被页面先行继续定制，不冻结成只能重新生成的结果页 |
| 数据接入/查询验真变化 | 两方向共用的口径、字段、完整性、授权和错误；不复制两套接入逻辑 |
| 知识/模板/默认值变化，即使不升 Schema | 同源生成、两个方向的使用示例、公共工具事实、各自流程的误用/限制 |
| Relay SDK、身份或预览接线变化 | 接入合同/权限/双通道/回执回归；产品语义未变时不重发核心能力 |
| 本地文件工具/包装变化 | local 独立安装与回退；共享核心改变才影响线上能力，文件包装不强行带入线上 |

mc-content 继续提供全部产品事实和完整公开 MCP 契约；local 仍整目录独立安装。现有生成链已经部分同源，需扩充覆盖和双向验收。服务/Skill/内容各保版本序列，以精确组合回执对齐；同一轮固定组合，新进程整包切换。不建设动态发布管理器，不新增 MC 保存准入。

## 8. 验收按业务逻辑与宿主交叉组织

| 场景 | 必须证明 |
|---|---|
| 页面先行·现有本地 | 从页面/设计提取所需数据，对接后保留页面意图；未执行候选和真实接通分开 |
| 数据先行·Relay 参考 | 从需求取得证据并组织合法页面；结构、数值/口径和预览分开验证 |
| 页面先行·线上目标 | 用户在工作台修改页面 → 补接/换接数据 → 预览 → 继续修改 → 原保存路径；无手工离线搬运 |
| 数据先行转页面先行 | 已生成页固定布局后换数据/加字段，保留身份/结构与有效证据，不强制重新 compose |
| 页面先行转数据先行 | 页面出现新问题，增量查询并补表达，再返回原工作副本；共享源变化无关组件不受损 |
| 不完整或冲突 | 数据缺失、单位/粒度/键不符、过期证据、权限失败、unknown 保存均给出具体结果，不伪造闭环 |

线上页面先行是待实施目标，不以现有 Node 脚本、参考 Skill 或本地测试替代。无需强制每种逻辑当前都在每个宿主上线；状态与承接批次必须明确。

## 9. 实施顺序与 Relay 拆分

| 批次 | 工作 | 退出条件 |
|---|---|---|
| S0 逻辑与能力清点 | 按页面先行/数据先行整理现有 Skill 段落、工具、证据、宿主与缺口，分型既有失败 | 不再以本地/线上定义方法；已实现/参考流程/线上目标分别标明 |
| S1 连接契约与共享核心 | 提取现有页面用数分析、需求/映射/证据关联、保留约束和变更影响；复用公共发现/查询/校验 | 两方向可交接同一页面与证据；无第二套 Schema/查询执行/会话系统 |
| S2 两入口工作流整合 | 两套 Skill 共用能力与知识，各保策略；页面先行从现有 local 迁出宿主假设 | 用同一任务验证两种逻辑，切换不丢意图/证据，不强迫步骤同序 |
| S3 线上页面先行闭环 | 工作副本、用数需求、数据映射、受控增量绑定/源更新、预览与保存接入 | 在真实工作台完成用户自定义闭环；未接通项据实记录 |
| S4 产品能力持续补齐 | IOC/分页/父子表/同比环比等逐项核对两个方向，完善公共创建/编辑 | 产品、MC/local 知识、工作流与实际页面行为同批闭合 |
| S5 独立分发与真实接入 | 产品组合、两套 Skill/适配、Relay 接线按归属发布 | 独立包与真实部署分层验收；兼容、缓存、活动工作稿与回退可核对 |

Relay 独立拆解仍聚焦 loader/SDK、工具包装/权限、可信上下文、程序/模型双通道、缓存和预览注入。MC 公共创作服务、工作稿规则、保存协调和完整工具事实留产品；页面先行上线也经同样接缝复用。线上页面先行不被定义成 Relay 专属能力，未来也可由其他集成应用承载。

## 10. 决策及完成边界

两种创作逻辑已经按用户指示写入 CONTEXT；它们与 AI/人工、Dashboard/Report、本地/线上正交。保持 ADR-0090 的公共工具/Relay/Java 责任、ADR-0105 的共享执行、ADR-0118 的当前前端工作副本，以及现行 MC/Skill 责任和完整包规则。两种逻辑的中间状态不进入页面渲染协议。

新增公开 Interface、接数交互或持久状态格式时须同批核对现行 ADR、Schema/公共契约、功能验收和复杂度；当前不提前冻结接口字段、重写 Skill 或移动运行代码。此前定向测试和 stale 结果仍只是存量基线，不因策略修订自动关闭。

本次为词汇与规划修订，无函数变更，复杂度测量不适用。链接/格式检查不等于业务闭环验收。后续按[功能验收](../agents/feature-acceptance.md)和[复杂度规则](../agents/code-complexity.md)实施，实际 Relay 部署和真实 DQE/Java 证据单列。
