# MC 内容包跨平台分发与调用防护方案

日期：2026-10-31。状态：本仓实施与本地验收完成，远端 CI/Windows/Relay 现场待验。范围：MC 内容包的构建、归档、安装约定、Python/Node 调用和诊断；Relay 接线作为外部协作项。配套事实与复现见[探查记录](2026-10-31-mc-content-distribution-hardening/audit.md)，结果见[实施与验收](2026-10-31-mc-content-distribution-hardening/implementation.md)。

## 目标与边界

让调用方能够区分“文件被转换或混装”“加载了旧代码”“运行依赖不可用”和“页面输入不合法”，并获得明确的恢复动作，避免为取得知识而修改 digest、跳过 verify 或直接读取 index 绕过安装检查。

保留原字节 SHA256 的内容身份。LF/CRLF、BOM 或正文变化后，旧发布包应校验失败；源代码有意修改后，由官方生成器重新生成清单并发布新包。诊断可识别换行差异，但不得用标准化后的摘要代替完整性校验。manifest 不包含自身的文件摘要，现有构建顺序不存在自引用死锁。

MC 提供包、程序能力、事实与恢复建议；不接管 Relay 的权限、保存、发布或 Skill 采用决定。不修改 Relay 私有实现，不新增发布管理服务，不将完整性检查当作来源认证或进程代码不可变的证明。

## 发现与优先级

| 编号 | 优先级 | 问题与影响 | 证据等级 | 处理方向 |
|---|---|---|---|---|
| R1 | P1 | LF→CRLF 导致整包查询失败；错误只给摘要失配，容易诱导修改校验器 | 本地复现 | 分发保真、受控路径换行约束、只读诊断与整包恢复建议 |
| R2 | P1 | Python↔Node 依赖系统默认编码；GBK 条件下读取合法 UTF-8 输出失败，CLI 含 emoji 的错误信息可能没有 JSON 回执 | 本地受控编码复现，非 Windows 实机验收 | 显式 UTF-8，统一流和异常边界，增加 Windows 测试 |
| R3 | P1 | timestamp `.pyc` 与源文件同大小、同 mtime 时可加载旧代码，而文件校验通过 | 独立新进程复现 | 空目录安装、版本目录不可变、受控加载与缓存策略；明确磁盘校验的证明范围 |
| R4 | P1 | `verify` 能通过不代表操作依赖齐全；缺 jsonschema 时 compile 直接 traceback；缺 Node 时 upgrade 与 knowledge 错误归类不同；upgrade 无超时 | 缺依赖已复现；超时为源码确认 | 按能力预检、统一环境错误、升级调用超时与取消边界 |
| R5 | P1 | 现有同步逐文件替换；中途失败留下新旧文件混合，重试又被旧锁和临时文件拦截 | 注入第二个文件替换失败后复现 | 分清源码同步与运行安装；运行包在旁路目录校验后切换，给同步中断提供恢复清单 |
| R6 | P1 | MC 打包会覆盖已存在的同名 release 回执；没有独立的归档 verify 命令及 MC 下载后回验步骤 | 回执覆盖已复现；工具与 CI 静态确认 | 完整输出拒绝覆盖、归档回读、同 SHA 来源检查、实际下载产物回验 |
| R7 | P2 | 缺文件和多文件均只报集合失配；BOM 报解析异常，缺少安装恢复动作 | 本地复现 | 有界列出 missing/extra/changed，识别 BOM/换行线索并给恢复动作 |
| R8 | P2 | 仅改 manifest 的 contentVersion 为错误值，verify 仍通过 | 本地复现 | 校验派生版本与 contentSha256 的一致性及必要字段类型 |
| R9 | 接入约定 | compile 返回 status=invalid 时 CLI 仍可退出 0；只读退出码会误判成功 | 本地复现；现有 README 已明确 | 保持现行语义，示例与 Adapter 同时检查操作状态、检查状态及截断状态 |
| R10 | P2 | sourceIdentity 对二进制构建输入先 UTF-8 解码再计算摘要，来源 SHA256 与原文件字节不一致 | 实施收口时发现，真实生成链路回归已先失败 | 来源摘要统一读取 Buffer，保留图片/二进制原字节 |

R1/R7 中拒绝被修改的包属于正确行为，缺陷是安装防护和诊断不足。R3 的证明对象是磁盘文件与实际加载代码可以分离，不表示当前 Relay 已发生旧缓存执行。R5 原有冲突保护有效，问题在中断后的可恢复性，不应通过放宽冲突检查解决。

## 实施顺序

### B0：锁定基线与建立回归

1. 核对当前 dirty 工作区和并行任务，只修改本计划列出的作者源与工程工具。禁止为本批运行清理或覆盖全仓工作区。
2. 在 `test_mc_content.py` 与既有 deployment 测试中补入 R1–R9 对应的最小回归，先记录现行结果；新增发包测试可参考现有 local-authoring release 测试组织方式。
3. 冻结包摘要、源文件摘要、解释器实际路径、Python/Node 版本和执行平台。当前包不是 Relay 引用的 1989 文件包，开始现场核对时重新固定双方身份。
4. 编码前按复杂度规则识别相关职责和分支、实测基线；新增及辅助函数逐个测量，不用外层工厂指标替代内部函数。

完成标准：每项已复现问题都有一个可独立运行的回归入口；平台模拟与实机结果分开记录。

### B1：编码、依赖与可执行诊断

涉及作者源：`tools/mc-content/scripts/mc_resources.py`、`mc_content.py`、`mc_inspection.py`，以及实际需要的测试与依赖声明。

- Python↔Node 的 stdin/stdout/stderr 明确使用 UTF-8；CLI JSON 输出使用确定的编码，错误路径同样保留合法 JSON。文件读取显式指定 UTF-8；页面输入中的 BOM 是否接受按页面读取契约单独判断，不能自动改写包资源。
- 复用现有 verify 入口增加只读诊断能力。正常查询继续 fail closed；诊断可收集有界差异，不自动修文件，不泄露正文，不根据 LF 标准化结果放行。
- 诊断先说明问题、影响和动作，再提供 code/path、预期与实际摘要。集合差异提供 missing/extra 示例和总数、truncated；换行识别仅在原摘要失败后进行。
- 增加按操作分层的预检：文件完整性、Python 版本与编译依赖、Node 版本与可执行路径。`verify` 仍可保持标准库可用；预检不能把它包装成全部能力可运行的证明。
- 统一缺依赖、子进程启动失败、超时、非法输出的结构化诊断。upgrade 的 timeout 采用与操作规模相称的明确上限，并保留调用方取消/终止的说明；不把环境故障归为页面输入错误。
- 校验 contentVersion 派生关系；保留现有退出码与业务状态约定，新增诊断字段采用兼容扩展。诊断无法收敛为兼容扩展时，明确 Interface 版本迁移，不静默改义。

完成标准：中文、emoji、GBK 默认编码、缺 Node/依赖和超时场景均得到可消费回执；坏包仍然拒绝，正常包行为保持。

### B2：分发保真、加载隔离与恢复

涉及：受控路径的 `.gitattributes`、MC 安装说明、加载约定、`sync_upstream.py` 的中断诊断及必要测试。

- 明确 Git 路径分工：作者维护的文本统一 LF；生成的摘要固定资源按原字节保存，禁止检出或复制工具转换。先检查受控目录，避免全仓 renormalize 触碰并行修改及冻结来源。
- 正式消费优先使用已验证 `.tar.gz`；仍支持完整目录复制，但复制工具必须保真。禁止在内容包内放日志、下载回执、临时页或编辑器文件；禁止遇到多余文件时直接删除未知数据。
- 运行安装采用全新版本目录：解压/复制 → 独立校验与能力探针 → 启动对应进程 → 切换后续调用。旧轮次保持固定目录/摘要，失败保留旧目录；不在正在使用的目录逐文件升级。
- 加载前核对缓存与模块来源。安装目录不携带 `.pyc`；生产运行目录只读并从空目录建立，禁用字节码写入。对存在缓存或已载入同名模块的程序接线明确拒绝/重启；直接 API 接入必须补缓存与来源回归，不能仅设置 `sys.dont_write_bytecode=True` 后声称禁止了缓存读取。
- 针对 R3 增加专门探针：旧 timestamp pyc、unchecked-hash pyc、checked-hash pyc、同名模块预载入、不同包目录。受控启动必须保证执行当前源代码或明确拒绝启动，不能用更新 LOADED_CODE 快照来掩盖旧代码。
- 源码同步保留内部 Adapter 的所有权和原字节冲突检查。中断时列出已变更/未变更/临时文件及旧锁身份；恢复须使用已保留备份或新目录，不自动重算旧锁，也不盲删 `.sync-tmp`。本批不承诺把完整 authoring 仓库同步改成跨目录事务。

完成标准：更新失败不影响旧版本继续服务；新进程没有旧代码静默执行；源码同步中断有可核对的恢复步骤。

### B3：归档与来源回验

涉及：`tools/scripts/mc-content-pack.py`、`.github/workflows/ci.yml`、对应工程测试。参考 `tools/scripts/skill-release.py` 的既有做法，复用可独立复用的小职责，不将两个交付物强行合成一个发布系统。

- 保留现有打包调用兼容性，增加独立归档验证入口：核对回执、归档摘要、安全文件集合、解包后的资源摘要与公共调用探针。
- 归档与回执任一已存在均拒绝覆盖；临时目录内完成归档及回读后才写出最终交付物。失败不得留下貌似完成的归档/回执组合。
- 所有包内身份从同一暂存树读取，包括 sourceIdentity；源码 HEAD、内容摘要、归档摘要各自记录。CI 中拒绝 dirty 或与目标 SHA 不同的产物，本地 dirty 打包必须如实标识。
- sourceIdentity 的每个构建输入按原文件字节计算 SHA256，包括 pages 中的图片与二进制附件；不得先按 UTF-8 解码再哈希，不改动原附件。
- CI 上传 MC 归档后下载同一产物并执行独立 verify；Linux 与 Windows 分别验收解包后调用。编码模拟用于快速回归，Windows 实机任务用于平台验收。
- 检查完整 authoring Bundle、MC 独立包、local-authoring 独立 Skill 中相同的摘要/编码规则；已有可靠路径保持，不扩大到其他 Skill 行为或真实模型验收。

完成标准：真正下载的产物可在仓外独立使用；旧回执受保护；归档被破坏、夹带额外条目、来源错配时均明确失败。

### B4：文档、Skill 与接入收口

- 同批生成 `metriccanvas-authoring/mc-content`、锁和参考投影，禁止手工修改分发副本绕过生成器。
- 更新 `tools/mc-content/README.md`、`HANDOFF.md` 和程序调用样例：安装、预检、错误分流、整包恢复、固定摘要与缓存边界。
- 调用样例显式检查 content 是否被截断、操作 status、inspection/correlation 状态；命令退出 0 只说明命令正常返回。环境故障应停止该能力并报告恢复动作，不进入改校验器或绕过包封装的修复路径。
- 按[功能与协议能力验收要求](../agents/feature-acceptance.md)核对现有 MC 页面场景、页面元数据文档与 local-authoring 同步范围。复用 `mc-content-layout-demo` 做包内检查/浏览器回归，记录它只能证明的层次；如无页面协议语义变化，明确对应文档/Skill无需变化的依据，避免编造新字段或静态页面冒充安装诊断。
- 新增/修改函数按[复杂度规则](../agents/code-complexity.md)实测，报告同口径前后值及未关闭项。当前仅形成计划，没有修改可执行分支，不填写虚构测量值。

## 验收矩阵

| 场景 | 预期结果 | 验收层 |
|---|---|---|
| LF 原包、包含中文和空格的安装路径 | 内容身份保持，程序查询与 Node 检查通过 | 仓外程序、Linux/Windows |
| CRLF、BOM、正文改动 | 不放行；定位差异并建议重新安装 | 单元/仓外程序 |
| 缺文件、多 `.DS_Store`、同名新旧文件混装 | 分开报告集合差异；不删除未知文件 | 单元/仓外程序 |
| 目录内日志、临时输出 | 明确安装污染，给正确输出位置 | 调用示例/程序 |
| GBK 默认编码、中文、emoji | UTF-8 JSON 可消费，没有乱码或裸 traceback | 受控编码/Windows |
| 缺 Python 依赖、Node 缺失/过旧 | 指向对应运行环境，不误报页面输入 | 预检/程序 |
| Node 超时或输出非 JSON | 有界结束，结构化错误，不残留成功状态 | 子进程行为 |
| timestamp/unchecked-hash/checked-hash pyc、旧模块预载入 | 加载当前源或明确拒绝；没有静默旧代码 | 独立进程 |
| 更新中断、跨版本并发轮次 | 旧版本可用，新轮次只用已验证新目录 | 文件故障注入/Relay另验 |
| 归档或回执已存在、写出中断 | 不覆盖；不遗留貌似完成的输出组合 | 打包行为 |
| 归档篡改、非法条目、回执不匹配 | 下载后 verify 拒绝 | 分发/CI |
| contentVersion 与摘要不一致 | 明确清单错误 | 单元 |
| compile invalid、inspect not_run、查询 truncated | 调用方不误报业务成功 | 程序样例/Relay另验 |
| 现有页面、旧页迁移和知识查询 | 行为保持，生成与独立安装闭合 | 产品/浏览器/Skill |

实施检查入口沿用：`pnpm mc:content:test`、`pnpm mc:content:coverage`、`pnpm authoring:contracts:check`、`pnpm skills:check`、相关 deployment 测试和 MC 归档回验。Python 工程检查使用安装了锁定依赖的维护解释器；操作系统平台、浏览器、CI、Relay现场分别报告，不互相替代。

## Relay 需配合的内容

1. 提供现场包 contentSha256/contentVersion、实际模块路径、Python/Node 路径与版本、错误 code/path；只采集诊断身份，不采集凭据或业务正文。先确认引用的 1989 文件包来自哪一发布物。
2. 保真安装到独立版本目录，固定每轮内容摘要；停止在正在使用的包内写业务输出，更新后新建对应调用进程。
3. 消费结构化诊断与业务状态，安装/环境故障交给安装恢复，禁止以 monkey-patch digest、跳过 verify、重写旧 manifest 作为恢复动作。
4. 验证真实 Relay 下的编码、模块缓存、目录切换、并发轮次、失败恢复及取消行为。本仓本地探针通过后，这些仍列为现场待验。
