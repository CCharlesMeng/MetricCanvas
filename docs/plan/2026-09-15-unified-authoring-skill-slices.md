## 2. 切片原则与依赖

- 功能 slice 以可演示的用户行为和可观察产物为边界，契约、程序、工具接线、必要前端与验证一起交付。
- S0 是准备门禁，不计用户功能交付。B1 是各片开工前共同契约收敛工作，不单独计功能完成；先冻结身份、轮次、精确引用、错误和版本语义，再随消费者扩展，禁止先搭完整通用执行平台。
- S1 优先兑现本次 Skill 优化目标；不得以 S2–S8 未完成为理由延后。
- 数据映射首片必须同时贯通新建和当前页新增数据，不把 mapper 或离线调试包当作交付。
- 本仓代码、真实模型行为、真实服务接入分别验收。某层缺环境不阻塞无依赖的后续代码工作，也不能改写为通过。

```text
S0 基线 → S1 统一入口与分发
               ↓
          S2 最新上下文与只读问答 → S3 局部编辑自动提交 → S4 故障恢复与精确发布
                                      ↓
                                  S5 数据映射纵切 → S6 完整页面组合
                                      ↓
                                  S7 扩展装配与迁移

S8 真实联调与切换：依赖 S1–S7 的相应验收全部满足
```

上图表达功能集成依赖，不要求所有开发任务串行。单执行者可按 S0 → S1 → S2 → S3 → S4 → S5 → S6 → S7 → S8 推进；多人实施按 §8 分波次并行。S5 的映射研究/向量准备可提前；S7 的 F1–F17 台账在 S0 起建，扩展核心字段在相关消费者实现前收敛。S5/S6/S7 可以在 S4 的外部联调等待期间推进，但未经恢复验收的写路径不能用于生产切换。

### S2：每轮取得最新上下文，并准确回答当前组件配置

**映射：** B1 的上下文/读取契约+B2。**依赖：** S1 的代码与分发基线。

**演示：** 人工修改列宽后问“这个表格怎么配置”，回答来自最新修订；澄清等待期间再次手工修改，回复后重新读取；全过程不保存、不发现业务数据。

交付：

- 在 `contracts/authored/` 收敛轮次、精确页面引用、能力版本、结构投影和同修订补读语义，沿现有生成链产出消费者。
- 扩展现有 `authoring-coordinator.ts`、`authoring-language.ts` 和 dialogue 接线，完成停止人工输入、收敛输入、同步确认、按 pageId 最新读取、注册本轮基线。
- 程序投影与公开受控补读能力；顶层单选传稳定 ID，明确文字目标优先。控制消息不创建用户轮次；新建明确空基线。
- 内容生成入口验证新鲜上下文前置，旧 token 不能绕过。凭据、完整页面、原始查询与数据行留在程序通道。

**验证与退出：** 最新读取失败保留本地工作且不继续；删除、跨页、同名歧义不猜目标；大页省略可补读且不能跨身份/页/修订；等待澄清解锁，迟到结果被隔离。通过公开读取工具与工作台交接集成测试，真实提供方 latest 保证另记。

### S3：局部编辑经候选链，只自动提交最终草稿

**映射：** B1 的候选契约+C1+C2 的正常提交闭环。**依赖：** S2。

**演示：** 人工改列宽后让 AI 改标题，同轮再调整候选措辞，最终只新增一个页面修订，列宽及未触及内容保持。

交付：

- 扩展 `content_ports.py`、`edit_page.py`、`create_content_page.py` 与内容 MCP，复用完整基线、领域编辑器和页面校验。
- 候选存储与引用绑定身份、轮次、根基线、候选版本、产物完整性及实际影响范围；可继续编辑候选，模型只收摘要。
- 可信运行协调消费最终候选，复用 lifecycle 提交用例；发送前记录冻结操作和不可变载荷，提交后精确回读再回显。
- 普通草稿无需通用审批；内容模型没有直接保存载荷或发布旁路。人工/AI 互斥、跨窗口基线门禁与操作去重生效。

**验证与退出：** 同轮多候选仅最终一次提交；独立成功子集仍须整页合法，全失败/无变化不新增修订；跨身份/轮次/根基线拒绝；其他窗口更新不被覆盖。注入未知回执至少进入可保留的未决状态，禁止立即重做；自动恢复与重启闭环由 S4 验收。

**部署限制：** S3 是可演示的本仓纵切，未完成 S4 之前不开放生产写路径。不得只写成功路径而丢弃未决操作。

### S4：取消、未知结果和重启可恢复，发布绑定精确候选

**映射：** C2 的完整恢复与发布；B1 的执行/操作兼容语义。**依赖：** S3。

**演示：** 保存实际成功但回执丢失，进程重启后查询原操作，显示原精确修订且没有第二次写入；确认发布后若候选变化，原确认不能发布新内容。

交付：

- 接通持久执行记录、候选存储、原操作查询、取消和恢复检查点；Relay 保持模型循环，Java 保持修订和写入结果权威。
- 共享模型/程序重试预算；超预算、断流、重启不删除未决状态；不兼容版本不能重解释原命令。
- 复用 `lifecycle.py`、`lifecycle_publish.py` 及工作台 recovery/publication 接线，完成精确确认、发布重放与预览恢复。

**验证与退出：** 故障覆盖受理前后取消竞争、回执丢失、重复恢复、权限变化、另一窗口更新、预算耗尽和预览失败。同一操作保持原载荷；仅权威确认未应用且可重试时重发。未知结果不得解锁后开启新修改；已保存但预览失败按原修订恢复。无确认/错误确认对象不能发布，原发布重放不重复发布。

**外部边界：** 本仓以可替换 Adapter 契约证明消费行为；真实持久记录、原子比较/取消与操作查询需要提供方实证，缺失不能由虚构 HTTP 端点补齐。

**验证与退出：** 标签/别名/次序变化保持逻辑身份与现存绑定；不存在的输出列和类型冲突阻塞。覆盖 fraction/percent/百分点、元/万元、0/null/负值、舍入边界、末尾零、未知规则/参数/顺序。需要数值转换时验证首次、刷新、筛选、召回及适用导出路径的一致性，否则明确不支持。公开创建和编辑内容工具都产出整页合法候选，单测 mapper 不计完成。

## 5. 开工与提交方式

下一步先开 S0，建立基线后优先交付 S1；同时可按 §8 启动契约收敛、测试设施和迁移调查。S1 内部执行次序为：

1. 固定比较场景、来源清单和能力边界。
2. 统一文档作者与加载条件，同时修改生成器和注册。
3. 更新生成物、锁、引用检查及受影响测试，验证独立分发。
4. 运行确定性回归与真实行为比较，分别落证据；缺真实环境继续后续可实施片。

已核对的根目录命令：

```sh
pnpm authoring:contracts
pnpm authoring:contracts:check
python3 metriccanvas-authoring/scripts/check_bundle.py
pnpm authoring:test
pnpm exec vitest run tests/authoring-export-isolation.test.ts
```

S2–S7 开工时据实际变更补充工作台、内容工具、生命周期及跨语言向量命令，不先猜不存在的测试文件。正常先跑受影响测试，生成链收敛后再跑完整 Authoring 回归；本次规划不运行这些测试。

每片是一个完整审查/合并单元，可含作者与程序、生成物与锁、验收证据三个配套提交。大批生成物删除单独展示，但合并/发布点必须完整通过。S3/S4、S5/S6 共享模块按顺序集成，不能从旧基线分别重写。

本文件编号是本地规划编号，不代表已创建 GitHub 子 Issue。后续若拆票，以这些行为和退出条件建立父子关系，保留 A0–E 与规格覆盖，不新增独立内网映射产品或全包目录迁移任务。

### 检查何时执行

1. **开发时：** 受影响契约、工具或工作台测试；有状态/副作用的逻辑用能观察错误行为的测试约束，不写固定 Markdown 措辞断言。
2. **slice 集成时：** 相关公开路径测试、契约生成一致性和 Bundle 检查；生成器/公共契约变化后跑完整 Authoring 回归，涉及 TS 消费者补跨语言与工作台测试。
3. **可发布 Bundle：** 在隔离目录检查安装、注册、依赖、全部引用与来源锁；生成物与作者必须配套，禁止测试只因源码树提供了缺失文件而通过。
4. **S8 生产切换：** 冻结整组版本后，运行真实模型与提供方完整流程，核对回退能力。

将必要检查接入仓库既有 CI/构建入口，先核对当前 job 再扩展，不新增重复构建系统。生成器写文件与只读 check 不应在同一工作区同时跑；大规模完整回归在汇总分支集中执行，各任务先跑自身受影响测试。

### 不能同时改的共享面

- **共同契约与生成物：** `contracts/authored/` 同一契约指定一个负责人；消费者提变更需求，由作者合并后生成。导出器、Bundle registry 和锁由一个集成人维护；工作分支可自测生成，最终锁由集成结果重建。
- **候选与提交语义：** 内容、协调、存储不能分别定义 run/candidate/op 身份；接口未收敛前只能准备场景、夹具或实现无接口依赖的纯逻辑。
- **工作台状态：** `authoring-coordinator.ts`、`authoring-language.ts` 的 S2→S3→S4 语义变化顺序集成，不从同一旧版本同时各写一套状态机。
- **内容装配共享文件：** S3 候选入口先稳定，再由 S5 接新增数据，S6 接完整组合。映射 domain、运行时向量、恢复模块可并行，共享应用入口集中接线。
- **评测归因：** 同一比较批次不能同时更换模型、提示、参考注入和生产工具集合。独立用例可用隔离会话并发执行，但使用同一冻结配置，保留每次原始结果。

### 建议人员/执行槽分配

有 3 个实现槽时：P1 分为「Skill 作者」「分发构建」「评测设施」，共同契约由集成人先做小范围收敛；P2 分为「Python 上下文」「工作台」「契约/故障测试」；P4 分为「恢复与发布」「数据映射纵切」「扩展及格式测试」。共享接口与生成锁保持单人集成，不按前端/后端长期隔离成两套计划。

并行任务在独立工作分支/worktree 上围绕同一已冻结契约开发；完成后先合并接口和公共设施，再合并消费者，最后运行完整 slice 验收。预计可明显重叠的是 S1 文档/构建/评测、S2 前后端、S4 与 S5/S7；S2→S3 的状态演进和 S5→S6 的装配主链仍需顺序集成，不给出未经工作量实测的加速百分比。
