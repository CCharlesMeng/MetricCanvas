## 1. 结论与必须纠正的交付口径

当前实现是一个可运行的 MC 内容与布局能力基础包，已经形成同源契约导出、整包摘要、编译/检查/升级脚本和回归链路。它尚未形成“Skill 消费 MC 知识所需内容全部在包内”的交付闭环。

核心缺口有三层：

1. **内容范围不完整**：页面结构 Schema 已复制，协议语义、约束解释、知识主题、示例及部分工具契约仍在包外。
2. **消费能力不完整**：有些内容虽在包内，却不能通过当前查询索引定位；完整 Schema 单原子过大，也未接入已有按主题读取能力。
3. **完整性判断不完整**：生成器和 CI 只证明已声明的输出一致，没有证明全部应交付的 MC 事实都已进入输出。

因此，后续完成标准必须由“脚本可运行、摘要一致”升级为：**内容范围有明确清单、来源同源、可发现可读取、引用与执行依赖闭合、随产品变更同步生成、覆盖缺口可被 CI 检出**。

用户明确要求的规则应成为仓库完成条件：**每次 Schema 更新，都在同一批变更中重新生成并验证 MC 内容；新增语义、校验规则、能力或示例即使不修改 Schema 版本，也必须走同一链路。**

这项仓库构建与交付质量要求，不改变能力方分工：MC 返回事实和检查结论；Skill 决定采用与业务流程；MC 不新增保存或交付准入状态。

### 1.1 本轮已确认的边界

以下是用户在本轮 grill 中已选择的方案，后续实施沿用，不重新假设：

| 问题 | 已确认结论 |
|---|---|
| Q1 独立闭合 | MC 所需知识、脚本、示例、协议与使用说明在包内闭合；外部只有声明的运行依赖及平台、引擎、Relay 基础设施 |
| Q2 配套引擎与旧页 | 最新包面向配套引擎创作；旧页面按产品可读与迁移策略处理。流程应顺畅，已知不兼容必须在 MC 发包前说明 |
| Q3 完整性要求 | 应交付知识缺失使仓库构建/发包检查失败，同批补齐；这不增加运行时保存/交付准入 |
| Q4 历史知识 | 最新包包含当前完整知识、历史差异、能力下限与迁移说明；旧版精确知识查对应历史包，不复制每版完整快照 |
| Q5 验收职责 | MC 发包前完成产品契约、支持范围内旧页/迁移、产品引擎回放，并披露已知不兼容；Relay 采用前验证实际部署 |
| Q6 工作流边界 | MC 提供工具前置、版本与引用关系、受控操作、保存/预览回执及标记协议等技术约束；Skill 保留需求理解、解释确认、模板采用及最终交付编排。用户在边界说明后回复“ok，handoff” |

Q7 的首轮性能预算尚未冻结：1 秒检查 / 2 秒必要迁移仍是候选目标。该预算不阻止已确认范围的内容补全；先建立完整链路的测量证据，再确认正式预算。本轮已按用户要求整理[新窗口交接](implementation-handoff.md)，当前仍未实施生成器、协议或运行代码变更。

优先级 P0 表示宣称“完整 MC 依赖包”前须关闭；P1 为同批交付可靠性与实际对接必需项；P2 为有数据后优化。实施可以并行准备，但不把原定漏项另称可选后续批次。

| 编号 | 不足与证据 | 影响 | 弥补方式 | 优先级 |

| G01 | 只有结构 Schema，没有完整协议语义、规则、主题和样例投影 | 知道哪些字段合法，却不知道怎么正确选用、绑定及解释 | 从产品参考生成完整知识树与主题，不从安装后的 Skill 副本反向读取 | P0 |

| G03 | 其余 8 个工具未附内层 requestSchema，9 个均未导出完整 inputSchema | 参数分支、required、约束、引用定义可能丢失 | 从实际工具注册结果导出完整 inputSchema；嵌套请求 Schema 与业务行为说明同时闭合，回归对账 list_tools | P0 |
| G04 | D1–D4 仅迁移部分参考，部分 MC 事实仍混在 Skill 工作流中；当前 data-analysis 说明也包含流程选择 | 一边遗漏事实，一边把 Skill 流程误收进产品事实 | 建立逐条迁移对照：MC 事实、Skill 方法论、Relay 接线、部署事实；只迁事实，通用步骤引用事实 | P0 |

| G10 | manifest 锁产品契约等信息，尚未证明实际部署的引擎/工具产物身份；targetVersions 是传入字段精确相等检查 | 包内一致不等于部署一致，部分字段 checked 不等于整组通过 | 内容身份、产品支持范围和实际部署证据分开记录；发布记录锁源码与产物摘要，Relay 回填真实版本来源 | P1 |
| G11 | evaluate 当前仅执行 compile/inspect，对比 status；真实部署操作 not_run | 不足以证明知识覆盖、查询可达、旧页迁移或真实端到端集成 | MC 自身构建测试覆盖这些能力；调用方矩阵另外记录真实回执，不能仅比较一个 status | P0/P1 |
| G12 | MC 根目录独立，wheel 不含 MC；tools.py 注册缺失；说明文档也在外部目录 | 接收者容易把源码目录、wheel、内容包和完整 Skill 混为一物 | 将 MC 使用说明和交接契约纳入独立包；明确平台工具服务与 Relay Adapter 是外部前置，提供匹配的接线样例 | P1 |
| G13 | writeOutputs 顺序写多棵树，MC 生成读取磁盘锁/快照；中途失败可能留下部分新输出 | 构建顺序和旧中间产物影响最终状态 | 同一内存产品输出图生成派生物，生成完成后再写出；发布从验证后的暂存目录归档，不引入运行时激活管理器 | P1 |
| G14 | literal_errors 扫描整个 Python 包，范围包含内部自有 adapters | 内部适配改动可能影响公共错误索引与内容身份；这是静态代码推导的风险，未在本轮动态复现 | 明确公共源码白名单/来源分类，内部 Adapter 错误由部署回执补充，不进入公共知识生成分母 | P1 |
| G15 | 每次 query/compile 先扫描并摘要校验整包，扩容后成本随包大小增长 | 知识变完整可能增加调用耗时；当前没有新增真实性能测量 | 先测完整安装与重复查询成本，再决定是否优化；任何缓存按固定内容摘要隔离，不加入会话业务状态 | P2 |
| G16 | 更新约束目前散在说明中，未形成 MC 完整覆盖和版本升级的统一完成检查 | Schema 更新后容易只生成结构或漏掉新增语义 | 把第 7、8 节要求纳入仓库维护文档、检查命令和必需 CI，同批验证原 local-authoring 独立安装 | P0 |

G08 的现有检查仍有价值：它调用同源产品 normalize/parse 校验，并使用用数扫描。缺口是其自身声明检查范围没有扩展到全部结构，不应误称当前仅做 JSON Schema 结构校验。当前 compose 的组件枚举本来就限定在可装配集合中，保留这一约束。

## 4. `mc-content` 应覆盖什么

### 4.1 必须随包提供的 MC 知识与确定性能力

| 类别 | 完整范围 | 维护真源 |
|---|---|---|
| 页面协议 | 完整结构、字段语义、枚举、条件分支、字段绑定、格式、参数、筛选、行为、导航、显隐、查询与数据源、布局与组件 | packages/page/src、docs/page-metadata、reference-map |
| 创作与工具协议 | 活动工具完整 inputSchema、嵌套请求、操作闭集、状态和回执含义、参数工具约束 | 实际 MCP 注册、contracts/authored、公共用例代码 |
| 数据上下文与发现/查询 | 公开 Schema、身份与查询编码关系、版本/覆盖语义、就绪与未知/不支持的区别 | docs/schema-metadata、公共数据契约、受控发现/查询实现 |
| 规则与错误 | 产品不变式、稳定诊断、定位、可采取动作、不能推断的结论与后续参考 | 产品验证器、规则映射、公共诊断与 MC 作者说明 |
| 能力与布局 | 全组件的可渲染/可装配/可编辑区别、版本下限、模板、场景选择与适用前提 | 产品组件目录、AUTHORING_CAPABILITIES、活动 compose 契约、MC 模板 |
| 样例和反例 | 适用分支的有效完整例子、负例触发解释、运行完整输入的可定位资源 | 产品合法/非法夹具、reference-map 的覆盖见证 |
| 历史版本与迁移 | 当前写出版本、可读范围、能力下限、已支持迁移与已知语义缺口 | versionPolicy、产品升级实现、兼容夹具 |
| 程序实现 | 查询、局部知识读取、布局编译、产物检查、版本检查、迁移与确定性评测 | 同源程序与已有读取核心 |
| 使用与交接说明 | 独立安装、依赖、调用格式、结果状态、范围边界、更新方法和调用样例 | MC 维护的简短说明，纳入包摘要 |

“完整”只针对当前公开支持的 MC 契约及明确范围，不包括尚未实现的未来能力，也不意味着所有历史版本都可以无损迁移。IOC 组件的知识和能力说明应完整；IOC 自动装配仍可明确为不支持。

### 4.2 继续由 Skill / Relay / 集成应用维护的内容

- Skill：需求理解、通用创作方法、流程骨架、能力要求、正式采用矩阵与采用决定。
- Relay：SDK/加载器注册、可信上下文、权限、程序通道、并发/重试关联、模型摘要、包安装与脚本重载。
- 集成应用：渲染引擎安装和部署、Java/DQE/预览服务接线及真实运行回执。
- MC：提供稳定 Interface、所有 MC 事实与 Implementation；可以在拿到真实 Relay 加载契约后提供对应 tools.py 接线样例，不能把未验证的注册样例称为已接入。

MC 包无需包含整套渲染引擎 npm 产物、完整平台 Python 服务和内部 Adapter。它必须带齐自身知识、脚本、许可证及依赖声明，并明确外部服务前置。存储与执行依赖闭合，不等于包含所有外部系统。

### 4.3 原 Skill 内容的迁移规则

逐条建立迁移表，而非仅登记文件：

```text
原文件 / 段落 → 内容类别 → 真源 → MC key / Skill 保留位置
             → 生成或作者维护 → 样例/规则 → 校验方式
```

例如，参数工作流中的“询问用户选择”属于 Skill；candidate_id/param_id/instance_ref 的不同用途、日期形状、工具输入和回执语义属于 MC。已有页面刷新中“怎样选择业务任务”属于 Skill；execute(metadata) 的输入输出、initial 成败语义及不负责保存的事实属于 MC。

产品事实只维护一处。过渡期旧 Skill 的 MC 参考可以保留为同源生成的兼容投影，不再手工维护另一份。local-authoring 的整目录独立安装保持不变，不能为了去重改成运行时依赖外部 MC 目录。

### 4.4 Relay 反馈的 P1 / P2 / P3

此处 P1/P2/P3 沿用 Relay 的问题编号，与第 3 节的优先级标记分开理解。

**P1：发现/查询字段规范，纳入必补范围。** 当前工作流说明不能替代字段契约。需要为每项记录方向、类型/枚举、含义、前置条件、失败行为、版本和例子，并区分模型输入、可信程序输入、模型摘要输出、程序信封输出。

| 字段 | 当前实现事实与文档要求 |
|---|---|
| dataContextVersion | discover 输出的元数据快照版本；query 必须携带匹配值。不是页面 Schema 或用户确认版本 |
| validationMode | query 输出 strict/relaxed，由可信部署配置决定；不是模型可选参数。relaxed 不放松权限与基本类型约束 |
| discoveryProtocolVersion | v1 discover 输出 1.0；普通回退不输出。部署支持能力由实际 Adapter 声明，不能假设全部支持 |
| readyRequirementIds | discovery 输出的就绪集合；resolved/ready 不代替实际查询，也不是 query 输入 |
| interactionEnvelope | 程序通道的发现确认信封，不是模型输入；状态、动作与 revision 规则要随包提供 |
| businessDomain | 来自 discover 的真实模型业务域；不等同 business-report/usage-report 场景名称，不写死场景枚举 |
| queryBinding | 区分展示身份与实际查询编码，说明 groupBy、timeGranularities、filterDimension 等绑定 |
| granularities / metricCompatibility | 粒度来自实际发现能力；兼容性 unknown 不能当作已支持或不支持 |

事实来源：[semantic_catalog.py](../../../metriccanvas-authoring/tool/metriccanvas_authoring/data/semantic_catalog.py)、[validation_policy.py](../../../metriccanvas-authoring/tool/metriccanvas_authoring/data/validation_policy.py)、[发现实现](../../../metriccanvas-authoring/tool/metriccanvas_authoring/data/discovery/service.py)、[results.py](../../../metriccanvas-authoring/tool/metriccanvas_authoring/data/results.py)。可信发现上下文也需纳入适用契约，但不能冒充公开 MCP 模型参数。

**P2：业务域场景，纳入必补范围。** 将原有 business-report、usage-report 场景按来源投影进包，并登记查询入口、示例与约束。分开表达受控组件/绑定事实、可选阅读与布局建议、实际业务数据要求。原示例中的业务对象不是运行时固定事实；用户指定的业务结构可覆盖建议，场景说明也不能冒充编译器已经实现的检查。

**P3：Q6 已认可职责拆分。** 按技术约束所有权拆分：精确 page/workVersion、resultRef/instance_ref、操作语法与 dependsOn、保存/预览回执等归 MC；任务选择、解释确认、采用模板与最终交付决定归 Skill。目录按协议、工具或运行职责定位，不要求都塞进 protocols/。

现有标记约定已在平台 v2 协议中定义；本轮不凭文档另造一套格式。MC 当前预览校验精确 artifact/ref/binding 并检查 Adapter 回执；Relay 的最终标记替换、卡片注入及真实部署仍须单独验收。模型测试能检查文字标记，不能证明真实 Relay 已完成替换。

## 5. 生成与消费架构

### 5.1 复用已有生成链，不复制安装目录

```text
产品 Schema / 验证器 / 版本 / 迁移实现
产品语义正文 / reference-map / 不变式 / 夹具
活动工具注册 / 创作契约 / 公共能力表 / MC 作者源
                       │
                       ▼
             同一构建输入图与公共知识核心
                 ├─ MC 完整知识与能力包
                 ├─ local-authoring 独立目录投影
                 ├─ 既有 Skill 的兼容参考
                 └─ 覆盖记录与版本/摘要清单
```

可复用的现有职责包括：

- `page-reference.ts`：结构节点、语义注释、例子和分支映射、规则、引用。
- `local-authoring-knowledge.ts`：语义章节发现、显式主题选择器和主题生成。
- `local-authoring-knowledge-core.ts`：主题依赖闭包、局部约束及父约束、未展开引用。
- `local-authoring-projection.ts`：独立脚本打包、许可证和闭合检查。
- 产品 normalize/parse、升级、组件遍历及用数扫描：执行事实，不在 Python 重写。

应把其中与消费者无关的部分提取成共享核心。当前 localPageReference 会移除在线路由及仓外定位，不能把其安装输出整份当成 Relay 的完整产品知识真源。Relay 需要的在线工具语义与 local-authoring 所需的离线说明采用同一真源的适用投影；不建设通用多 Skill 框架。

Schema、语义正文、规则、示例和知识主题必须共享来源摘要。重复的分发副本可以存在，但不能变成可独立编辑的规则副本。

### 5.2 建议目录职责

以下是目标职责，具体子目录以实施时的引用闭合结果收敛；不是当前已存在文件的清单。

```text
mc-content/
  README.md / HANDOFF.md
  mc-content.version.json
  index.json
  protocols/                  页面、数据上下文、发现/查询等公开 Schema
  references/                 完整产品语义、规则、能力与可读参考
  knowledge/                  主题索引、结构节点、依赖与指针
  examples/                   完整合法例子与可执行负例资源
  tool-contracts/              完整工具参数、内层请求及行为说明
  errors/                     稳定诊断、修复说明和继续查询定位
  layouts/                    标准、说明与模板；目录区分可执行能力
  runtime/                    产品回执含义与契约对齐事实
  scripts/                    现有六个接口及其内部实现、依赖和许可证
  eval/fixtures/              MC 确定性夹具；不写入调用方采用结果
  coverage.json               范围、真源对应关系和未覆盖项
```

coverage 是构建完整性事实，不是 evalStatus 或运行准入状态。评测回执、业务页面和运行日志放包外，避免改变被测内容身份。

### 5.3 查询 Interface 保持集中

保留现有 `query_content(topic, key, options)`，扩展受控查询类别和索引即可，不为每个组件新增工具。建议支持模块、主题、Schema 节点、规则、组件能力、示例、工具/操作契约和布局正文的定位。

每个返回单元至少包含：稳定 key、内容版本/摘要、来源、适用版本、实际返回范围、依赖/继续定位，以及是否完整返回。已有字段应兼容保留；新选项和返回结构需要接口契约与回归，不能在 Relay 包装层自行发明。

局部读取须保留父级 required、分支条件、附加属性约束、字段语义和相关不变式。未展开的引用明确列出，并能通过同一 Interface 继续读取；它不是独立可执行的完整 JSON Schema。不得把片段当作完整校验器。

完整 Schema 保留为安装资源和校验输入。常见任务读小主题，不靠提高预算反复读取整棵树。当前“超预算不返回残缺原子”的行为应保留，同时提供合理的细粒度路径。

有界要求也覆盖 compile/inspect/evaluate 给模型的摘要。完整计划、检查细节与 document 留程序通道；Relay 负责最终传输预算，MC 提供稳定、可解释的摘要，避免 Relay 重写产品判断。

## 6. 版本、实际部署与旧页面

### 6.1 分开标识，按一组匹配产物交付

区分页面 schemaVersion、MC Interface 格式、模板版本、平台工具协议、产品包版本、内容摘要和实际部署产物。当前 Bundle 0.3.1、产品 1.0.0-rc.4 都不能单独唯一标识实现，需使用来源摘要和发布提交。

建议增加发布阶段生成的交付记录，关联：

- 公共源码完整提交；协议/引擎/工具产物的版本与摘要。
- MC 内容版本、完整摘要与产品契约摘要。
- 运行依赖及实际执行的构建、测试、未验范围。
- Relay 接收后的实际部署身份、支持范围与证据来源。

发布记录放在内容摘要计算之外，由 CI 在取得最终提交和产物后生成。不要把“包含自身最终提交/归档摘要的文件”放回参与自身摘要的内容树，也不要让每次普通校验因 HEAD 改变而重写内容身份。源文件摘要与 CI 的 GITHUB_SHA 分别解决可重现构建与发布追踪。

targetVersions 当前只做传入字段精确比较。这是保守的一致性检查，不是完整兼容性算法。后续应基于产品明示的读取范围、能力下限和工具 Interface 支持记录区分“相同”“已证明兼容”“不兼容”“未知”；没有规则时继续明确未知，不能仅用语义版本大小猜兼容。

实际渲染应用由集成应用部署，MC 内容包不自动安装引擎。编译合法、文件可读、装配可用和视觉正确分别报告。采用判断仍归 Skill。

### 6.2 每次升级必须保留的旧文件流程

1. 取得匹配内容包及真实目标环境事实，对原始旧文件做检查。
2. 分别返回读取合法性、使用能力的最低版本、迁移可能性和语义缺口。
3. 可读且只做旧能力范围内修改时允许保留原版本，不强制全页迁移。
4. 需要升级时默认只检查；明确写出到全新目录，保留 original 原始字节/SHA256、目标 page 和 migration 报告。
5. 原版本、目标版本和关键行为分别回归；已有目录拒绝覆盖，未知/未来版本或缺失迁移规则的语义明确报告。
6. 在目标运行时预览，真实取数、保存和预览交接分别验收，由 Skill 决定采用。

不需要保存 54 份重复说明来对应当前全部可读版本；需要从产品策略生成范围，并保留能定位的历史差异、能力下限和受支持的迁移规则。当前“临时下一 minor”演练应保留，再增加实质语义变化的演练，不能只证明版本号能换。

旧 inspectionSpec 与调用缓存按内容摘要隔离；整包替换后新建进程或完整重载代码。Relay 明确旧请求如何完成或重新编译，不混用旧代码与新资源。

### 6.3 发包兼容性与耗时说明

落实 Q2/Q5：每次发包按“变更 → 受影响输入特征 → 仍可读？→ 可自动迁移？→ 人工处理步骤 → 回归夹具/结果”提供说明。不能只写一个宽泛的版本范围。不可自动迁移的旧页仍可能可读，两个状态必须分别报告。

MC 发包前负责自身契约、支持范围内历史文件与迁移、受影响的产品引擎回放；真实 Relay/DQE/保存/预览部署由 Relay 采用前验证。包内和发布说明保留各层结论与未验范围，不把部署可用性默认为本地测试结论。

已进行 [30 次本地冷进程探测](../../evidence/mc-content-layout/schema-latency-probe.md)，底层检查/升级约 0.16–0.22 秒；这不包含 MC Python 包校验、Relay、模型、网络与引擎渲染。约 1 MiB 的样例主要增加 inline 行数，不代表复杂组件图的性能。

Q7 待确认的建议：在固定参考执行环境，以约 1 MiB / 1 万 inline 行的常规基准验证检查不超过 1 秒、必要迁移不超过 2 秒；复杂页面另列样例与测量，Relay 端到端耗时独立报告。具体回归统计方式、样例矩阵由实施补齐，当前探测不是生产 p95 或正式性能验收。

消费路径应避免无意义重复：检查已包含升级可行性判断；当前页不强制迁移；不得默认串行执行检查、dry-run、实际迁移三次才继续。迁移失败保留原件、给出路径和处理动作，不静默丢弃旧语义。

## 7. 仓库中每次 Schema 更新的同步规则

### 7.1 哪些改动必须触发

强制集合至少包括：

- `packages/page/src/` 的 Schema、版本、验证器、能力下限、迁移、组件目录与协议相关行为。
- `docs/page-metadata/` 正文、reference-map、字段/枚举说明、主题路由和样例映射。
- 合法/非法夹具、规则与分支见证、参与导出的页面例子。
- 活动 MCP 参数、创作请求/编辑操作、公共能力表、发现/查询/参数协议和公共诊断。
- 数据上下文 Schema 与适用的服务协议来源。
- MC 作者源、布局模板、生成器、脚本、依赖锁与分发声明。

不要仅检测 CURRENT_MINOR 或 schemaVersion 字符串。结构不变的语义修复、校验器收紧、工具参数和模板变更同样可能影响 Skill。

当前 CI 的 authoring job 没有按目录跳过，继续保留这一简单机制。若以后优化检查范围，须基于完整输入依赖图；不能用一张容易漏文件的路径表静默免检。Schema 同步批次不能把 skip/bypassed 当作通过。

### 7.2 作者与构建必须完成的顺序

```text
修改产品真源与适用版本/迁移规则
  → 更新语义说明、字段/枚举解释、主题与能力声明
  → 更新合法/非法样例和独立期望
  → 同一生成命令构建产品契约、MC 内容和 Skill 投影
  → 检查覆盖、引用、摘要和生成无漂移
  → 仓外安装与旧文件回归
  → 受影响装配、渲染和交互验证
  → 同一变更提交真源与派生物
  → CI 复算并检验，输出固定提交对应交付物
```

生成继续使用现有 `pnpm authoring:contracts`；它已经写 MC 内容，应扩充这一链路，而不是要求维护者再记一条独立同步命令。CI 运行 `--check` 验证生成结果，不在 CI 里自动修改、提交或推送工作树。

生成内部先构建完整输出图、检查引用与覆盖，再写入分发树并更新锁。重新生成应幂等，同一源码在不同检出路径、实际支持的构建环境下得到相同内容摘要。发布归档从已验证输出生成。

### 7.3 新增 MC 完整性检查的职责

建议新增 `mc:content:coverage` 和 `mc:content:check`，**这两个名称目前是实施建议，尚未加入 package.json**。前者只做范围对账，后者组织 MC 检查；不替代现有完整仓库检查。

| 检查 | 必须证明 |
|---|---|
| 结构一致 | 页面/数据上下文/创作协议快照来自活动真源，节点与分支无静默丢失 |
| 语义与规则 | 所有产品注册模块和语义章节可发现；字段/枚举说明与不变式可定位，新章节改名失配明确失败 |
| 覆盖分母 | 每个应交付项有源标识、内容 key、适用范围、规则/样例；已声明不适用项有原因，不能从生成结果反推“全部已覆盖” |
| 工具对账 | 完整工具输入 Schema 与真实注册结果一致，内层请求、$defs 和引用闭合，稳定行为有说明 |
| 能力对账 | 全部产品组件都有渲染/装配/编辑声明；不支持装配被正确呈现为能力事实 |
| 查询可达 | 面向调用方的内容有索引，常见主题有有界返回；依赖和未展开引用可继续定位 |
| 样例行为 | 当前作者例子通过产品校验，反例仍触发独立预期；不能把规范化后的所有旧例子冒充历史兼容验证 |
| 独立安装 | 只复制 MC 包并安装声明依赖、移除仓库和原 Skill 后，查询/编译/检查/迁移仍能执行 |
| 跨投影一致 | MC 与 local-authoring 的共同事实具有相同来源；适用差异明确，独立本地 Skill 无外部依赖 |
| 版本与迁移 | 旧文件保留、支持范围、能力下限、已有目录拒绝、未知旧语义和真实下一版本语义变化均覆盖 |
| 分发完整 | 摘要、文件集合、依赖、许可证、说明和锁一致，运行产物未写回包内 |

coverage 的缺口会使 MC 内容构建/交付检查失败。它不能使既有保存工具新增准入状态；两者职责不同。

### 7.4 必须增加的负向回归

现有测试继续保留。新增回归不能只读取当前生成结果再断言自身存在，至少需要独立改变真源后验证：

1. 新增字段/枚举：Schema、知识主题、约束、例子与摘要同步改变；漏路由或漏语义时失败。
2. 只改一条语义、规则或错误说明，不升 Schema：MC 对应内容与兼容参考改变，旧输出 check 失败。
3. 新增/改名语义章节、改变显式主题选择器：可发现或明确报选择失配，不能静默漏读。
4. 新增组件：公共能力必须显式表态，未装配能力不能被示例当作可用。
5. 修改 query/edit/参数工具分支：MC 工具 Schema 跟随真实注册变化，不限于 compose。
6. 删掉一个“应纳入、但生成器漏选”的知识类别：coverage 失败，即使现有 files/hash 全部一致。
7. 布局正文、例子或依赖资源没有查询入口：可达性失败；局部输出 unresolvedRefs 有合法继续入口则允许。
8. 移走原 Skill、外部 contract-snapshot 和仓库源码：独立包仍可执行，避免隐式借用兄弟目录。
9. 在隔离检出发布含实际语义差异的新 Schema：重生成整组产物，旧页面分别检查、迁移和目标校验，原始字节不变。
10. 混装资源、旧进程新资源、旧 spec 新内容：明确失败/未验；不冒充已检查。
11. 编译/检查给出 ok 但真实 DQE、保存或渲染未运行：报告仍保留这些未验项。
12. 内部 Adapter 变更：不影响公共 MC 内容身份，内部错误仍由真实回执表达。

W1–W4 可以在 MC 仓完成，不需要等待 Relay SDK。W7 需要真实加载器和完整产物接口；当前本地没有 Relay 仓。不要让缺失 Relay 代码成为继续遗漏产品知识的理由，也不能把未经验证的 tools.py 样例当成接入完成。

所有代码实施仍执行仓库复杂度要求，测修改函数和全部新增辅助函数；不因已有大函数超限而扩大无关重构。功能/协议消费方式变化需同步可观察场景、页面说明与 local-authoring，按受影响范围运行检查；不自动追加真实 DS 模型验收。

## 9. 完成定义

可再次宣称“MC 内容完整交付”必须同时满足：

- MC 事实范围有独立来源清单，原 Skill 中相关事实迁移有对照，没有不明归属。
- 结构、语义、规则、能力、例子和版本知识都在包内可定位；差异和不支持项明确。
- 所有必要的知识和脚本引用闭合，仓外安装不读取旧 Skill 或开发仓。
- 完整工具参数与活动注册对账；模型摘要、确定性程序输入及执行回执各守职责。
- Schema 及其他相关真源变更必须同批生成，CI 能发现“生成器没有纳入”的遗漏。
- 当前/旧版本检查和受支持迁移有行为证据，原件保留，真实部署与视觉未验范围不被本地结果替代。
- 交付记录能关联固定源码、协议/引擎/工具及内容身份；Relay 实际接入状态另行证明。

当前清单、脚本与先前 CI 结果作为保留基础，不删除重做；新增门禁和完整知识投影尚待实施。本轮没有改变既有产品、生成物或部署。
