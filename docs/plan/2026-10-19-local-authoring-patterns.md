# 本地创作页面范式规划

状态：独立设计规划，待用户细化。日期：2026-10-19。适用 `metriccanvas-local-authoring`，保留完整目录独立安装能力。本文件是范式工作的唯一主入口，后续在此更新，不并入平台工具装配实施计划。

## 1. 已确认事项与本规划边界

本轮已确认：

1. 用户首次明确指定布局形态即构成确认；已有页面局部修改沿用原形态；整页重组重新核对。
2. 确认摘要同时说明形态、组织方向、主要交互位置和候选范式，而不只询问 Dashboard／Report。
3. 用户要求、设计源或原页面出现实质冲突时，必须显式确认处理方案；已有类别选择不能替代对新冲突的确认。
4. 范式覆盖业务分组理由、阅读／操作顺序、组件选型理由与可替换范围；本部分先单独规划，由用户进一步设计。
5. 本批采用 Skill 流程约束及确认形态与最终文件一致的确定性检查；不新增受控创作入口。校验器不证明会话已确认。

布局形态是外框，范式是内容组织的参考。两者分别判断；同类图表、数据源或主题名称不能直接决定外框。统一领域术语沿用 [CONTEXT.md](../../CONTEXT.md)，平台创作边界参考 [ADR-0098](../adr/0098-profiled-page-composition-and-incremental-navigation.md)，本规划不宣称其平台装配能力已经实现。

范式细化不新增页面 Schema、组件或查询协议；发现表达缺口时单列能力需求，重新评估。当前已有的六张范式卡和结构摘要是候选草案，不表示分类体系、卡片内容或视觉基线已经定稿。本轮不继续扩写这些候选卡。

## 2. 当前材料与差距

| 层次 | 当前草案已有 | 进一步设计要解决 |
|---|---|---|
| 形态分流 | Dashboard／Report 分支与确认步骤 | 检查范式不会反过来替用户决定形态 |
| 候选分类 | 四种 Dashboard、两种 Report | 颗粒度、重叠关系、命名和是否增删 |
| 人工解释 | 适用目的、阅读骨架和部分易错点 | 形成稳定的业务分组、顺序、选型与替换规则 |
| 结构事实 | 从实际页面生成容器、轨道、组件树、Tab、variant 与来源哈希 | 哪些事实值得展示，哪些只是来源页面的偶然选择 |
| 业务与交互 | 说明部分口径与绑定风险 | 每张卡明确交互范围、数据前提、可用与未验能力 |
| 视觉证据 | 仍无本批验证的截图基线 | 是否需要、如何获取同版本宽／窄屏图，并解释适用条件 |
| 模型行为 | 一个自然语言需求的两轮本地复测 | 范式选择与内容组织的多场景独立评价 |

结构摘要不包含查询体、业务行、字段绑定、地址和自由文本。摘要可验证来源一致性，但仅凭组件树看不出为什么这样分组，无法替代人工设计与视觉／交互验收。源码相同也不等于运行结果或业务效果已经验收。

## 3. 候选范式盘点

以下是素材清单，供设计取舍；六类暂不视为封闭枚举。

| 候选 | 来源页面 | 值得提炼的关系 | 不能直接固化的部分 |
|---|---|---|---|
| Dashboard 地图概览 | [ioc-project-overview](../../pages/business/dashboard/ioc/project/ioc-project-overview.json) | 地域背景与业务主题共同扫描，卡内指标／分类／比率保持归属，Tab 切换重点对象 | backdrop、固定权重及业务卡数量 |
| Dashboard 主题分析 | [ioc-opportunity-analysis](../../pages/business/dashboard/ioc/opportunity/ioc-opportunity-analysis.json) | 主题 KPI 分组，组织层级 Tab 承载整组分析表 | compact 工具栏、层级名称和每组表数 |
| Dashboard 筛选清单 | [ioc-opportunity-list](../../pages/business/dashboard/ioc/opportunity/ioc-opportunity-list.json) | 从条件到对象集合，再到搜索、排序、分页、详情 | 具体列、筛选数量、导航目标与查询完备性 |
| Dashboard 对象详情 | [ioc-project-detail](../../pages/business/dashboard/ioc/project/ioc-project-detail.json) | 单对象身份、概况／规范、预测和进展之间的阅读关系 | 隐藏工具栏、特殊比例和字段叙述组合 |
| Report 经营月报 | [business-sdt-report-monthly](../../pages/business/report/sdt/business-sdt-report-monthly.json) | 基准期下先总体／趋势，后组织层级，再重点对象 | SDT 口径、近六月窗口和固定摘要 |
| Report 分析简报 | [flow-analysis-report](../../pages/business/report/flow/flow-analysis-report.json) | 指标、推演、风险和业务视角逐层提供证据 | 业务分类、推演字段及固定结论文字 |

入选标准建议：有可解释的信息关系、当前协议能表达、能够提供可观察的页面结果。来源页面本身的未完成能力和缺陷必须标记；不将整页视为已验收的标准答案。当前目录中的其他页面可以补充组件或交互样本，但先说明它补足哪一条关系，避免目录越大越难检索。

## 4. 范式卡的建议设计字段

以下是待设计结构，不是新增页面协议。建议先手工完成两张差异明显的卡验证可读性，再统一字段。

| 字段 | 要回答的问题 | 所需证据 |
|---|---|---|
| 适用任务与不适用边界 | 用户要完成什么任务，什么时候不选它？ | 原始需求、真实使用场景 |
| 布局形态与阅读目的 | 满宽／定宽如何确定，扫描／比较／定位／顺序阅读如何组织？ | 用户确认和设计源 |
| 信息分组 | 为什么这些指标、分类和明细属于同组？ | 业务关系与数据粒度，不能仅凭组件位置 |
| 阅读／操作顺序 | 用户先看什么，再做什么，操作影响哪一部分？ | 页面表现与交互轨迹 |
| 组件选型 | 为什么用组合卡、Tab、地图、表格或叙述文字？ | 当前组件能力及替代方案的代价 |
| 可替换与约束 | 哪些组件、主题和比例可替换，什么关系必须保留？ | 设计裁决；替换后仍可检验的关系 |
| 数据及交互前提 | 需要何种粒度、完整性、筛选消费、目标页面和口径？ | 数据契约、查询证据和依赖边界 |
| 正例与误用 | 新需求如何映射，哪些照搬会失败？ | 独立需求与可观察的结果 |
| 结构／视觉示意 | 什么图或摘要最能帮助模型理解？ | 当前协议的可加载样例，必要时同版本截图 |
| 来源、状态与验收 | 材料来源是什么，哪些层已经验证？ | 路径、版本、哈希、静态／模型／浏览器／真实数据结果 |

每条范式规则应说明适用条件，避免把来源页的某个 span、列数、组件 variant 或未实现交互升级为通用规定。比例和主题数量作为实例展示，稳定的信息关系作为可复用知识。

## 5. 知识组织与生成建议

建议维持三个层次，待用户设计完成后再固化：

1. **入口与检索**：入口承担形态识别、组织摘要和确认；分支目录按使用目的列出候选，模型只读取匹配卡。
2. **范式解释**：作者维护业务关系、选型理由、替换边界、误用和前提。图片／示意图是否加入、用哪种形式，留待本次设计确定。
3. **机械事实与完整样例**：导出器提取来源结构和哈希，完整可加载样例承担协议验证；独立安装包含实际要消费的全部文件。

来源路径与证据留在维护仓库；分发目录只含闭合知识与必要来源标识。现有 `references/page-patterns/*.json` 是结构摘要，不冒充可运行页面。需要通用完整范式页时，应显式使用 inline 演示数据，并重新验证；真实业务查询不能复制为普遍可执行模板。

用户设计优先于范式。没有匹配项时，以已确认的阅读／操作意图组合现有组件并说明缺口；不能套入最接近卡片而删减需求。是否允许一页组合多种范式、如何限制组合层级，须在设计阶段定义，再进入 Skill。

## 6. 后续设计需裁决的问题

这些问题属于范式设计阶段，本轮不代用户定稿：

- **分类颗粒度**：候选按整页任务分类是否足够？是否区分整页范式与可复用业务分组？
- **通用与业务专用**：六类保留哪些？IOC／SDT 只作来源实例，还是需要单独的业务语境说明？
- **设计表达**：使用阅读流程、布局线框、实际截图、结构摘要中的哪种组合？宽／窄屏如何呈现？
- **卡片深度**：每张卡包含多少正例、误用、替换方案？怎样避免迫使模型一次读取大量组件细节？
- **组装自由度**：允许何种混合、改造与不匹配回退？哪些信息关系必须保留？
- **样例策略**：复用经检查的业务页，还是建立少量去业务化完整样例？怎样防止两者漂移？
- **质量门槛**：什么证据使候选卡进入正式目录？是否需要真实模型、独立需求、宽／窄屏及交互结果？

推荐设计顺序：先确定分类与复用粒度，再做一张 Dashboard 和一张 Report 的样卡；根据样卡决定表达形式、字段与检索方式，最后确定自动投影和验收。不要先锁定文档格式，再强迫业务关系适配格式。

## 7. 实施阶段与交付

| 阶段 | 责任与动作 | 完成判据 |
|---|---|---|
| P0 当前素材盘点 | Agent 整理上述来源、草案与证据边界 | 页面、结构摘要与候选一一对应；未验项可见 |
| P1 分类与样卡设计 | 用户细化分类、使用目的、信息关系和表达形式；Agent 按需补充源码／页面事实 | 两张代表样卡和复用边界获用户确认 |
| P2 知识契约收敛 | 按确认后的设计定义作者内容、机械投影、完整样例及来源映射 | 每条知识只有一个真源；安装目录闭合 |
| P3 范式实现 | 更新分支检索、卡片、必要样例、导出与哈希；同步产品文档和 pages 入口 | 选定场景可加载，生成检查和仓外安装校验通过 |
| P4 独立验收 | 使用新需求及原始设计／数据，验证选择、组织与交互 | 分层报告静态、模型、浏览器与真实数据结果；不以单例代替整体 |

本轮完成 P0 规划整理，P1–P4 不因已有草案或之前的静态测试视为完成。具体卡片设计待用户继续。

## 8. 验收建议

| 场景 | 核对结果 |
|---|---|
| 相同月度指标分别明确选择 Dashboard／Report | 外框与确认一致，组织方式能解释不同使用目的 |
| 仅给含糊的“运营分析” | 推荐有依据，确认前不生成，摘要包含组织方向 |
| 明确 Dashboard，设计源却是 Report，且未授权转换 | 展示具体冲突，等待处理方案；不自动覆盖任何一方 |
| 用户明确允许对同一设计进行 Dashboard 重排 | 记录已解决冲突并继续，不机械重复询问 |
| Dashboard 详情使用 reportHeader | 沿正确形态生成，组件名称不引发错误分类或伪冲突 |
| 新需求与来源页字段、卡数和主题不同 | 保留信息关系并适配，不照搬业务事实或固定几何 |
| 包含 Tab、多查询或分页表格 | 子项完整，数据／交互作用域有明确依据 |
| 新设计没有匹配范式 | 按确认需求组合并说明依据，不强套模板 |
| 校验目标与用户确认不一致 | expected-layout 检查失败；不能从产物反推预期参数 |
| 目录独立安装与来源页变化 | 知识链接闭合，生成漂移可检出；不依赖仓库源码运行 |

行为期望从独立原始需求推导，模型不接收评分器答案或旧产物。确定性检查不能评价阅读组织是否合理；模型自述采用某范式也不能替代产物与浏览器检查。真实 DS 复验按 [现行验收流程](../agents/skill-ds-model-acceptance.md)执行，证据层级分别记录。
