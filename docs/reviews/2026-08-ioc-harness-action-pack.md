## 1 结论

**一、这套 harness 目前验的是"产物长得对不对",不是"数据算得对不对"。** 6 个已实现校验器全部检查形式(SerDe 在不在、CTE 在 INSERT 前、别名是不是 t1、列在不在表里)。没有一条检查数值。而这个垂直域存在的理由恰恰是后者。

**二、判据层的可信度低于声明层的完整度,而且方向是反的。** 实测:一份完全合法的 SQL 被判 FAIL 3 项(其中一项的"除法分母"来自注释里的 `hive/bi_test`),一份 ADS 直读 ODS + 引用不存在列的 SQL 被三个校验器全部放行 `[§3.1]`。目标用户是新人时,误报的代价翻倍——它既费一轮修复,又教会一条不存在的规则。

**三、上游完整意味着这是 fork 而不是新项目,而 fork 的三件套一个都没有:来源记录、方向约定、漂移检查。** 修复方向错了会被下一次同步冲掉;`.learnings/ledger.md` 的 `knowledge.doc-stale` 已经为同类问题计过 2 次数 `[§7.5]`。

**一句话**:先让判据能分对错(§3 批 0),再让判据落在数据上(§3 批 2),中间插一步定方向(R20),其余都可以等。

## 2 验收能力:你说的对,它是最根本的一条

我原报告漏了这一维——五个维度问的都是"harness 自己的行为对不对",没有一个问"交出去的数据对不对"。补上之后,它应该排在第一。

### 2.1 证据(三行,可复跑)

| # | 事实 | 位置 |
|---|---|---|
| 1 | L1/L2/L3 的判定 = 在 markdown 里正则匹配 `等级: L2`,而这份 markdown 由 Agent 自己写 | `deliverable_level.py:29-32` |
| 2 | 黄金样本声明「等级 L2(Mock 试算通过)」,但它引用的 `mock-data-plan.md` 不存在;`job-create` 门禁(要求 ≥L2)实测 PASS | `examples/.../validation-report.md:29` + 实测 |
| 3 | `GWT验收.md` 在全部 `.py`/`.js` 里只被引用一次,是存在性检查;**没有任何代码读过它的内容** | `blocks_when.py:31` |

补充一条:示例报告里"试算结果:128 行"是自述数字,无出处;`validation-report.md` 在守卫表里挂的是 `validators: []`(列而不查)。

### 2.2 为什么它比其他五项更根本

**因为等级阶梯的设计是对的,判据却是零。** `deliverable_level.py:4-6` 把验收分成三层,这个切法很准:

| 层 | 含义 | 应有判据 | 实际判据 |
|---|---|---|---|
| L1 | 结构合规 | 静态校验器 | 6 个,精度实测为负 `[§3.1]` |
| L2 | Mock 试算通过 | 输入数据 + 期望结果 + 逐行比对 | **无。改成一行文字** |
| L3 | 业务口径核验(GWT) | 验收标准与结果的绑定 | **无。GWT 从不被读** |

其他五个维度的问题是"判据不准"(准确性)或"判据可自述"(门禁);这里是**判据不存在**,而且缺的正是决定"数据对不对"的那两层。一个能强制 CTE 顺序、却无法判断指标算得对不对的 harness,优化的是错的回路。

还有一个更长期的后果:**没有回归**。一个 feature 交付后,它的验收资产(mock 输入 + 期望输出)没有沉淀成可重跑的东西。上游 DWS 表一变,昨天对的 ADS 今天可能错,而没有任何机制会发现。对数据仓库来说这是最贵的一类故障——错数会一直被消费,直到有人质疑报表。

### 2.3 让 L2/L3 长出牙齿:最小设计

核心思路一句话:**把人留在"执行"环节,把"判断"交给机器。**

**① `mock-data-plan.md` 从"方案"变成"数据"。** 保留 md 作为说明,但机器判据落在同目录的文件上:

```
<feature>/mock/
├── input/<source_table>.csv        # 每张来源表的 mock 行
├── expected/<target_table>.csv     # 期望的 ADS 结果行
└── actual/<target_table>.csv       # 试算导出结果(人贴回或工具拉回)
```

**② 一个 diff runner(约 150 行),分两种运行态。** 判据形状相同,来源可升级——与平台回执那条的设计原则一致:

- **能自动跑**:runner 建临时表、灌 input、跑目标 SQL、导出 actual、与 expected 逐行比对。
- **只能在平台跑**(更可能):runner 产出「可直接粘贴到工作平台的试算脚本」,人执行完把结果导出为 `actual/*.csv` 放回目录,runner 只做比对。**人负责执行与签名,机器负责判定。**

**③ L2 的判据换成 diff 为空。** `deliverable_level.py` 不再从 md 里读等级,改为:`expected/` 存在且 `actual/` 存在且逐行比对无差异 → L2 成立。等级从"声明"变成"算出来的"。

**④ L3 的判据是绑定,不是勾选。** `GWT验收.md` 的场景表加一列「断言 id」,每个"预期"必须指向 `expected/` 里的一行或一条断言;有场景没绑定即 L3 不成立。这样验收标准第一次真正流到下游——它现在只在 PRD 阶段被写下,然后在存在性检查里躺到归档。

**⑤ 归档时把 `mock/` 收进回归集。** `archive` 阶段把 input+expected 复制到一个 `regression/<feature-id>/`,来源表结构变更时可批量重跑。这是唯一能挡住"沉默错数"的机制。

**⑥ 顺带把"预期"写得可比对。** 当前示例的 GWT 预期是「数值一致」「趋势图按区域更新」——人都无法机械验收。要求每条预期至少给一个可比的数(或一条可判真假的断言),写不出来就说明口径还没定,应该出澄清项而不是往下走。

**这一条同时解决四件事**:L2/L3 有了真判据;GWT 第一次被消费;新人拿到的是"填两个 CSV"而不是"写一篇报告";回归有了资产。

## 4 内网自查手册

以下四件事我在这里做不到(拿不到上游仓、平台、真实 SQL),但每件都能给你一套可执行的判断流程。

### 4.1 判定"这 6 个校验器是移植件还是插件内重写"

**为什么必须先答**:它决定批 0 的修复写在哪一侧。若是移植件而你在插件里改,下一次同步会冲掉,并且上游继续误判。

```bash
# 在能同时看到两个仓的机器上
for f in validate_sql_ddl.py validate_sql_etl_patterns.py validate_domain_patterns.py \
         validate_lifecycle_columns.py validate_ads_clarification.py validate_gate_change.py; do
  diff -q <上游>/harness/tools/$f <插件>/harness/tools/$f && echo "SAME  $f" || echo "DIFF  $f"
done
```

| 结果 | 含义 | 动作 |
|---|---|---|
| 全 SAME | 原样移植 | **批 0 全部先在上游改**,再同步下来。同时:§3.1 的三类误判此刻正跑在上游生产链路上,按上游的流程报一个缺陷 |
| 全 DIFF | 插件内重写 | 批 0 在插件侧改;在移植方向表里把这些文件标为「插件原生,不回推」 |
| 部分 SAME | 混合 | 逐文件按上面两行处置;这种情况最需要 `porting-lock.json` |

**顺带取一个更值钱的信息**:上游那 50 个未移植的校验器里,有没有 `validate_sql_column_refs.py`(列引用)和 `validate_layer_consumption.py`(分层)。**这两个是最值钱的,如果上游已经有,批 0 的 0-6 就从"新写"变成"搬过来"。**

### 4.2 判定"插件是独立用还是装在上游工作区里用"

这决定白名单里 50 个"缺失" skill 是真缺失,还是运行时由工作区的 `.cac/skills/` 解析——直接改变一个 P0 问题的判级。

判据:**在一台只装了插件、没有上游工作区的机器上开一个会话,让 Agent 调用一个未移植的 skill(如 `ioc-ads-design-validate`)。**

| 观察到 | 结论 | 动作 |
|---|---|---|
| 明确报"skill 不存在" | 白名单确实超发 | `status` 字段(1-4)是主线,缺失必须对 Agent 可见 |
| 静默当作没有这回事、继续往下做 | **最坏情况** | 优先修:skills provider 读不到时不能静默返回空列表(`dsh/index.js:31-35`) |
| 能解析到 | 插件只在上游工作区内可用 | 在 README 写明部署形态,白名单无需改;但独立安装的宣传要撤 |

### 4.3 从上游取"移植优先级"(不必等真实运行)

按可得性从高到低,任一条都比按注册表顺序排好:

1. **翻最近 10~20 个 feature 的 `validation-report.md` 的"问题与处置"表**,统计出现频次 Top 10 的问题类型。这是现成的、写在文件里的失败记录,不需要任何日志设施。
2. **grep 上游的 `guard-report.md` 与 `*-clarification-questions.md`**,统计哪条策略/公理最常被触发,哪类澄清最常出现。
3. **访谈上游使用者,只问五个具体问题**——不要问"哪里不好用":
   - 上一次因为 SQL 写错而返工,错在哪?
   - 最常被门禁挡住的是哪一条,你通常怎么解?
   - 有没有哪条校验器你已经学会忽略它?(**这一条最值钱:它直接指出误报**)
   - 交付后被发现错数的那次,是什么错?本该在哪一步拦住?
   - 58 个 skill 里,你实际用过几个?

**排序键**:出现频次 × 被发现得晚的程度。交付后才发现的错,权重应当高于开发中被挡住的错。

### 4.4 判定"移植件有没有漂移"(在有了 lock 之后)

```bash
# 对每个"上游真源"类目录算一个内容哈希,与 porting-lock.json 比对
find codespec knowledge-base harness/stages -type f | sort | xargs shasum -a 256 | shasum -a 256
```

三种结果要给出三种不同的诊断,不能都报"不一致":本地已改 / 上游已变 / 两侧都动过。第三种是最需要人工介入的。

### 4.5 测一次校验器误报率(接阻塞路径之前必做)

取最近 20 个真实的 `hql_test/*.sql`(**必须是真实交付过的,不是样本**),全部跑一遍现有校验器,人工标注每条 FAIL:

| 标注 | 含义 |
|---|---|
| 真错 | 该拦 |
| 误报 | 校验器的 bug |
| 规范可疑 | 校验器实现对了,但策略本身值得商量 |

**门槛建议**:误报率 > 10% 的策略不得设为 `blocking`,先降为 `advisory`。这个数字本身就是批 0 完成度的度量——0-1 到 0-3 做完之后重测一次,应当显著下降。
