# 跨页下钻由宿主路由，统一运行时只上抛导航意图

IOC 作战地图是「概览 → 清单 → 详情」的三级下钻，而它的应用外壳——顶栏、250px 侧边栏、菜单树、角色切换、「返回 Cloud BI」——归已有门户所有。MetricCanvas 承载的是三张页面本身，通过 `packages/embed` 嵌入。

这个前提消掉了「MetricCanvas 需要长出多页应用这个一等概念」的大部分工作，但留下一个必须回答的问题：跨页下钻由谁执行。

现状是两套并存且都不适用。`apps/canvas` 有 `/pages/:pageId` 路由，运行时通过一个导航适配器调用它——这条路在嵌入场景下会和门户自己的路由打架，两套 history 互相覆盖。`packages/embed` 则完全没有路由，`mount()` 只把 `navigate` 事件抛给宿主，宿主怎么处理没有约定。

来源实现的回跳做法也需要一个位置：详情页的面包屑地址来自 `from` 参数，值是**来源页的完整 URL 查询串**，这样回去时清单页的筛选、搜索、分页、排序原样恢复。[ADR-0047](./0047-first-class-page-parameters.md) 已裁决 `from` 不进页面文档，那它归哪里。

## 决策

**统一运行时不路由。** 它把导航意图作为事件上抛：目标页面 id、编码后的目标查询串、以及来源页面 id 与来源页面当前的查询串。运行时到此为止，不调用 `history`、不改地址栏、不假设自己在什么容器里。

**回跳地址由宿主拥有。** 页面文档只声明「点这里去哪个页面、带哪些筛选、设哪些参数」（ADR-0047 的 `navigate`）；「从哪来」由宿主在接到导航意图时自行记录。宿主怎么记——压进自己的路由栈、写进 URL、放进会话存储——是宿主的选择，不进入本契约。

**页面标题栏与面包屑是两个东西，不要合并。** 面包屑（「机会点清单 ›」加一个回退箭头）是宿主的导航 UI。页面标题栏（项目名称加立项状态、级别、客户级别、行业四个标签）是页面内容，带业务字段，由 ADR-0047 的页面参数驱动 `reportHeader`。设计稿把它们画在同一条视觉条带上，这是视觉相邻，不是同一个所有者。

**`packages/embed` 的 `mount()` 契约在两个方向上补齐。** 入向是初始查询串——宿主把当前 URL 的查询串交给运行时，运行时据此水合筛选状态与页面参数。出向是导航意图事件。二者构成完整闭环：宿主路由到新页面、用新查询串重新 `mount`。

**`apps/canvas` 作为参考宿主实现完整链路**，包括记录来源与回跳，供开发、演示与验收使用。它不是生产宿主，但它必须走同一份契约，否则契约会因为「Canvas 里能跑」而悄悄依赖 Canvas 特有的行为。

**深链接必须有降级。** 直接打开详情页 URL 时不存在来源页。契约要求宿主在这种情况下明确处置——隐藏回退入口，或回到一个声明的默认上级页面——而不是留一个点了没反应的箭头。运行时不参与这个决定，但契约文档必须写明这是宿主的责任。

## Consequences

- 生产接入依赖门户方按契约实现路由与回跳，因此需要一份面向门户开发者的对外契约文档，而不只是包内类型定义。这份文档是本决策的实际交付物之一。
- Canvas 与生产宿主的行为可能不一致（回跳策略、深链接降级、查询串编码的保留字段）。**下钻链路的验收必须在生产宿主上做一次**，Canvas 上通过不等于接入通过。
- 运行时不再拥有导航栈，意味着它也无法提供「返回时保持滚动位置」这类体验。若后续需要，它是宿主能力，不要为此在运行时里恢复一个隐式历史栈。
- 现有的 `RuntimeNavigation` 适配器与 `drillThroughSearch` 的职责边界需要重新划：编码查询串仍属运行时（它知道筛选与参数怎么编码），执行跳转属宿主。
- 本决策不改变 [ADR-0021](./0021-page-id-is-not-a-rendering-switch.md)：页面 id 继续只用于加载、路由与修订归属，导航意图里携带 id 不构成「按 id 选择渲染」。
- 运行时只发意图；Canvas 用 sessionStorage 记来源，深链接无来源则不画返回；门户按接入文档实现自己的返回栈。

## Considered Options

- **在统一运行时里内建路由。** Canvas 场景下最顺，实现也最直接。但嵌入到已有门户时会出现两套 history 互相覆盖，且运行时开始依赖它无法控制的宿主环境。不采用。
- **运行时维护自己的导航栈（内存里记录来源页）。** 不碰 history，实现简单。但刷新即丢，跨嵌入边界不可靠，而回跳恰好是刷新后最需要成立的能力。不采用。
- **把来源 URL 作为页面参数写进页面文档。** 与来源实现最接近，页面声明也最自解释。ADR-0047 已否决：值域是 URL 的参数会把导航语义渗进页面文档，且每个可被下钻的页面都要重复声明。不采用。
- **让门户完全自己拼下钻 URL，运行时连意图都不抛。** 边界最干净。但「点表格某一行去详情页并带上这一行的哪些值」是页面文档里声明的知识，门户不掌握也不该掌握；让门户去解析页面文档来拼 URL，等于把页面协议暴露给宿主。不采用。
- **现在就为 MetricCanvas 引入「多页应用」一等概念（导航树 + 页面成员 + 面包屑规则）。** 长期看很可能需要，尤其在出现第二个多页应用之后。但本项目的外壳归门户，现在建这个概念会得到一个没有真实消费者的模型，且面包屑的真正难点（回跳要恢复来源页状态）本就不是静态导航树能表达的。留待第二个实例出现时再裁决。不采用。
