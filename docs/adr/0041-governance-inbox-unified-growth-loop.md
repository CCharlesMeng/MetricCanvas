# 治理收件箱：语义面成长回路的统一呈现与评审回执

语义面的成长机制在既有 ADR 里已分头裁决：别名候选从缺口条目产出、经人工背书进下一个快照版本（ADR-0031）；已验证查询由反馈产生候选、必须人工背书（ADR-0031）；缺口条目落库计数（ADR-0036）。但三条回路的治理动作没有统一入口，原型验证显示分面板、分动词（处理/采纳/背书）的呈现让治理者先学分类才能干活。竞品研究确认「自动化只在建议侧，人工只在采纳侧」是行业共识（Databricks 明文「Agent 行为不会仅因用户反馈而改变」）。

## 决策

**统一治理收件箱：三条候选流汇入单一待办列表。** 别名候选（缺口条目聚合的「用户说法→最接近指标」）、指标需求候选（高频缺口与高频临时口径形状，建议评估为新指标或派生模板）、已验证查询候选（用户在满意答案上的显式提名）以同一形态呈现：一句自然语言建议、证据（出现次数或提名人）、统一的**采纳/驳回**动作。类型是行内标签，不是分区；排序按证据强度。这是呈现层决策——三条回路的治理原则（ADR-0031/0036）原样成立，分类是系统内部的事，不转嫁给治理者理解。

**采纳不等于自动写回。** 采纳=接受建议进入落实：别名与已验证查询待人工更新数据上下文声明（版本化变更），指标需求转数据侧评估。ADR-0031「不允许问数过程直接写入别名」原样成立。别名采纳受硬上限（每字段不超过 10 个）与全域唯一性校验，防止别名膨胀反噬检索精度。

**已验证查询提名是用户显式动作。** 不自动从成功轨迹挖掘候选（数据面与治理规则都不具备）；用户点「提名为已验证查询」才产生候选。背书通过的已验证查询一份资产三种用途：检索与快路径的参照（ADR-0040）、评测金标准、空状态示例问题（ADR-0037「评测集与黄金问题集是同一批资产的两种用途」的自然延伸）。

**转人工评审与回执走会话事件流。** 用户可对可疑答案请求人工评审（「这个数对不对请人看看」），评审者为平台管理员角色；评审结论以步骤事件回到提问者的会话时间线——复用 ADR-0030 的事件落库与回放机制，不新建通知通道。没有回执的反馈按钮会沦为黑洞，回执是该通道成立的前提。

## Consequences

- 提名与评审动作进入工作台答案区；提名、评审请求、评审结论均为步骤事件，随会话可见性与保留期治理。
- 收件箱是缺口条目（ADR-0036）之上的呈现层，补齐其「台账无界面」的欠账；缺口排行与别名建议同屏，与「高频缺口与高频 formula 形状合并看」（ADR-0036）一致。
- 评审者身份当前为 mock 管理员；接入真实身份（ADR-0030 未决事项）前，评审结论的权威性与会话数据同级——结构成立、来源不可信。
- 数据上下文声明的人工更新目前是改文件；变更管理归属（谁改、怎么发版）在 #3 生产接入后另行裁决，收件箱不预设答案。

## Considered Options

- **按候选类型分面板分动词。** 信息组织最「对称」，但治理者需要先理解三种任务类型与三套动作词汇，原型验证反馈明确否定，不采用。
- **系统自动从成功轨迹挖掘已验证查询候选。** Snowflake verified query suggestions 的路子，但其前提是全量查询行为数据面与建议质量规则，当前都不具备；先做显式提名，挖掘留待信号充足后另议，不采用。
- **采纳后自动写回数据上下文。** 动线最短，但违反 ADR-0031 的人工背书原则，且数据上下文变更管理归属未定，不采用。
- **评审回执走独立通知中心。** 通用性更强，但为单一场景新建通道，且脱离会话上下文的回执可解释性差，不采用。
