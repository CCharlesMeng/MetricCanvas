# 指标缺口不阻塞问数，临时口径可见、计数并在沉淀处设闸

指标未定义是必然会遇到的情况，不是异常路径：用户想要的数据可能确实没有对应指标，需要数据侧新建指标与计算任务。ADR-0031 已确定指标不是问数的强制前置，但没有回答检索不到指标时系统具体做什么。答错、拒答与假装答对之间的选择，决定问数能否被信任。

## 决策

**检索不到合适指标时尽力回答，但结果必须被标注为临时口径。** 编排在数据上下文允许的范围内用 formula（ADR-0032）拼出一个口径并真实执行，同时把这次缺口记录下来。不恢复 ADR-0012 的 `METRIC_GAP` 阻塞状态：缺口是一条记录，不是一个卡住流程的状态机节点。

**临时口径在界面上必须与已定义指标视觉可区分。** 用户要能一眼看出这个数字是系统现场算的，还是公司口径。这是信任的分界线，因此它是首版要求而不是后续优化。

**缺口落库为结构化的指标需求条目，并统计出现次数。** 条目包含问题原文、检索过的词、最接近的候选及其口径差异、临时 formula、期望的维度与粒度、所属域与出现次数。次数是这条链的关键：反复出现的缺口才值得数据侧真的建指标、加计算任务。这与“不是所有问题都值得做成 Data App”是同一个原则往下一层的应用。缺口条目随会话事件流落库（ADR-0030），因此不需要单独的采集通道。

**沉淀设闸，但只设在沉淀为长期应用这一处。** 临时口径可以答、可以看、可以沉淀为 Report；沉淀为长期运行的 Data App 时必须过一道门：显式警告该页面存在无人负责的口径，由用户显式接受，且**接受记录持久化在页面上**——页面文档需能表达“本页面包含 N 个临时口径”，使其在后续查看与审计中始终可见，而不是只在保存那一刻弹一次窗。这样口径责任从系统责任变成可见的、已被接受的责任。

**部分可答时分开呈现。** 一个问题里能答的部分照答，缺的部分单独列为缺口，不把两者混进同一个数字或同一张图。混合呈现会让用户无法判断哪部分可信。

## Consequences

- 页面文档需要一处可表达“存在临时口径”的声明，以及其被显式接受的事实；这是页面协议的新增字段，受不可变修订与发布治理约束。
- 已发布页面因此可被审计出“口径无人负责”，这是刻意保留的可见风险，而不是应当被隐藏的瑕疵。
- 缺口条目是数据侧指标建设需求的第一个真实来源，其价值取决于问题原文的保真度；因此它与 ADR-0030 的隐私约束绑定，同样按身份可见性过滤与 90 天保留。
- 高频缺口与高频 formula 形状（ADR-0032）会指向同一批口径，二者应合并看，不建两套排行。
- 界面需要区分三种数字：公司口径指标、已验证查询、临时口径。只区分前两者不足以传达风险。
- 这条出口的存在意味着问数几乎不会“答不出来”，因此评测集必须包含应当降级的样本（ADR-0037），否则无法验证降级路径真的会降级。

## Considered Options

- **检索不到就拒答并记录需求。** 治理最干净，口径永不失控，但把大量本可回答的问题挡在门外，早期可用性过低，不采用。
- **尽力回答但不做区分。** 用户体验最顺，但临时口径与公司口径在界面上无从分辨，一旦出错会直接损伤对整个系统的信任，不采用。
- **临时口径完全不允许沉淀。** 能彻底避免无主口径进入长期应用，但会把“先问、再探索、值得了才沉淀”的路径在最后一步截断，且用户会绕道手工建页，不采用。
- **在保存时弹窗警告但不持久化标记。** 实现最省，但警告在保存后即消失，审计与后续接手者看不到风险，等于没有设闸，不采用。
