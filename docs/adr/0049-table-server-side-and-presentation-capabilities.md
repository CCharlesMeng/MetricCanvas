# 表格的服务端能力按数据源模式整体下推，呈现能力只识别不计算

IOC 作战地图三个页面的主体都是表格：概览页是三个 Tab 各一张表加一张地图，清单页是 32 列宽表加搜索、分页、列排序与列头筛选，详情页是两张规范性表加一张 12 月 × 3 子列、带分组小计与全局合计、首列跨行合并的销售预测表。

现有 `table` 组件比预期强：列节点是递归结构，因此多级表头已经支持；`fixed: 'left' | 'right'` 支持冻结列；`selection.writes` 支持从单元格原子写入多个筛选器；`pagination: 'query'` 配合 DQE 的 `total_count` 支持服务端分页。

差的是三类。

**第一类是被校验器显式拒绝的服务端能力。** `packages/page/src/validate.ts` 在查询分页下直接拒绝排序与列头筛选：

```880:885:packages/page/src/validate.ts
    if (column.sortable) {
      errors.push(schemaError(`${path}/sortable`, '查询分页暂不支持排序'));
    }
    if (column.filterable) {
      errors.push(schemaError(`${path}/filterable`, '查询分页暂不支持表头筛选'));
    }
```

这条限制在 DQE 时代是合理的保守选择，但清单页有 32 列、服务端分页、且预签金额与 12 个月度预测列都要求服务端排序，限制不解除就无法实现。

**第二类是声明了但没接通的交互。** `table.props.actions` 在 schema 里存在，但 `RuntimeView` 只给图表挂了点击处理（`handleChartClick`），表格只有单元格 `selection` 这一条路。而清单页需要「点机会点名称列跳详情，点客户名称列不跳」这种按列区分的行为。

**第三类是纯缺失的呈现能力**：分组小计与合计行的样式区分、首列相邻同值合并、单元格内的环比增减标记、以及宽表的横向滚动。

## 决策

**解除查询分页下的排序与列头筛选限制，改为整体下推。** 规则按数据源模式二选一，不混用：

- 数据源是 `query`：排序与列头筛选都是**生效查询的一部分**。排序编译成协议侧的排序位置（[ADR-0045](./0045-graphql-query-branch-with-structured-predicates.md) 的排序绑定），列头筛选编译成谓词。翻页、排序、筛选三者共同决定一次远程执行。
- 数据源是 `inline`：排序与列头筛选都在本地完成，与现状一致。

不允许「服务端分页 + 本地排序」这种组合。它看起来只是省事，实际语义是「对当前这一页的 10 行排序」，而用户以为排的是全量——这是会静默给出错误结论的一类失败。`pagination.mode === 'local'` 仅限 `inline` 数据源的现有约束不变。

**行点击导航接通，并按列声明入口。** `table.props.actions` 的 navigate 分支在运行时挂到行点击；列可声明自己是可点击入口，只有声明了的列才响应。来源实现里客户名称列的 `clickable: false` 对应的就是「不声明」。列上同时存在 `selection` 时以 `selection` 为准——它是更具体的意图。

**搜索是页面筛选器，不是表格属性。** 清单页那个搜索框在语义上与列头筛选完全同类：它是生效查询的一个输入，编译成若干字段的 `like` 谓词。放进表格 props 会让同一语义有两个位置（表格搜索与页面筛选），且它跨越多个字段（机会点名称与客户名称），本就不属于任何一列。它作为 `search` 类型筛选器由 [ADR-0050](./0050-filter-type-closure-and-hierarchical-dimensions.md) 承载。

**小计行与合计行由计算层产出，表格只识别不计算。** [ADR-0046](./0046-controlled-computation-with-named-operators.md) 的 `groupSubtotal` 与 `grandTotal` 产出带标记的行，表格声明一个行类别字段，按取值套用呈现档位（明细 / 小计 / 合计）。表格不做求和。理由与 ADR-0046 拒绝「只在组件层做」相同：同一口径可能同时出现在表格与其他组件里，算在组件层就会各写一遍。

**首列合并以「按字段合并相邻同值」声明，不引入行数。** 来源实现给每行算了一个 `rowSpan` 数值（组内首行取组大小、其余取 0），那是把渲染细节前置到了数据里。表格声明按哪个字段合并即可，相邻同值合并是确定性规则。

**单元格内的增减标记复用既有结构。** 列已有 `secondaryField` 与 `visual: 'signed'`，设计稿里 `+XX个` / `+XXP` 这类绿色增减标记由它们表达，不新增字段。

**横向滚动不进页面文档。** 表格比容器宽时横向滚动是渲染行为，与 12 列栅格是运行时不变量同理。

**本决策不做的事。** 不做可编辑单元格、不做行展开、不做列拖拽与列宽调整、不做导出。

## Consequences

- `validate.ts` 的两条拒绝规则删除，替换为正向校验：`query` 数据源上声明 `sortable` 的列必须在查询定义里有对应的排序绑定，声明 `filterable` 的列必须能编译成谓词。把「一律禁止」换成「必须配套声明」。
- `Table.svelte` 面临一次较大改动。[ADR-0025](./0025-converge-runtime-presentation-packages.md) 的待决节已记录 `Table.svelte` 拆分是既有遗留，本批是处理它的合适时机，但拆分本身应作为独立动作，不与能力扩展混在同一次提交里。
- 行类别字段在计算层与表格之间形成一份跨层契约：算子产出什么标记值、表格认哪些标记值，两侧必须同时校验，否则会出现「算出了合计行但渲染成普通明细行」这种只能靠肉眼发现的偏差。
- 排序、筛选、翻页三者共同决定生效查询，意味着任一变化都要重置或保持分页位置。约定为：排序或筛选变化时回到第一页，翻页不影响前两者。这条必须写死，否则「改了排序还停在第 7 页」会让用户以为数据错了。
- 服务端排序使表格的每次列头点击都产生一次远程请求。宽表加上默认 10 条分页，这个代价可以接受；但需要请求合并与取消，避免连点产生竞态。
- 落地进度（仍为 proposed）：`rowKindField` / `mergeBy`、`keyValuePanel`、`fieldText` 已进入 5.1 协议与表格呈现。查询分页下「暂不支持排序 / 表头筛选」的拒绝规则尚未解除；行点击入口与清单页用法仍在进行中。主体决策未齐，本 ADR 不标 accepted。

## Considered Options

- **保持本地排序，前端排完再分页。** 无需协议扩展。只对能一次性取回全量的结果集成立，清单页做不到。不采用。
- **允许服务端分页 + 本地排序共存，由作者自选。** 灵活。但它给了作者一个几乎总是错的选项，而错误的表现（只排当前页）在小数据量下看不出来，上线后才暴露。不采用。
- **让表格自己算小计与合计。** 改动最小，且表格确实拿得到全部行。但见上文，同一口径会在多个组件里各算一遍。不采用。
- **保留 `rowSpan` 数值形态，由数据侧或计算层算好。** 与来源实现一致，渲染最简单。但它把「合并几行」这个纯渲染问题固化进数据，一旦筛选或排序改变行序，预算的行数立刻失效。不采用。
- **把搜索做成表格 props。** 与设计稿的视觉位置一致（搜索框就在表格上方）。但它是生效查询的输入且跨多列，与页面筛选器同类；放进表格会让筛选输入有两个来源。不采用。
