# 页面参数一等化，与筛选器按可变性分界

IOC 作战地图的项目详情页从 URL 接收八个值：

| 值 | 用途 |
|---|---|
| `opportunity_code` | 全部四个查询的主键条件 |
| `mtime` | 全部四个查询的月份条件 |
| `page_title` | 页面标题栏的标题文本 |
| `ati_status_label` | 标题栏标签之一 |
| `project_initiation_level` | 标题栏标签之一 |
| `public_cloud_na_level_name` | 标题栏标签之一 |
| `sub_industry_level1_name` | 标题栏标签之一 |
| `from` | 面包屑回跳地址 |

只有前两个是查询条件。中间五个是纯展示——标题与四个标签，它们不影响任何查询。最后一个是来源页的完整 URL 查询串。

今天的页面文档只有 `filters` 这一个 URL 输入位置。把展示型的值塞成 `visible: false` 的维度筛选器，能骗过 schema，但会连带三处失真：它们会进入筛选状态、会被 `carryFilters` 携带到下一页、会占用 URL 的筛选命名空间，而它们在语义上根本不是筛选。更硬的一处是 `filterBindings` 的 target 闭集是 `dimension | time`，没有「绑到标题」这个目标，所以即使塞进去也没有办法让标题显示出来。

## 决策

**页面文档新增顶层 `params`：页面级的具名输入，值在页面打开时由 URL 确定。** 每个参数声明 id、值类型、是否必需、可选默认值与标签。顶层结构从六键变为七键。

**页面参数与筛选器按可变性分界，判据是单一的：这个值在页面打开之后还能不能变。**

- 能变的是**筛选器**——它有控件、或者能被组件 action 的 `writeFilter` 写入、或者能被跨页下钻覆盖。它属于筛选状态。`visible: false` 的隐藏筛选器仍然合法，覆盖的是「用户看不到控件但页内下钻会改写它」这种场景。
- 不能变的是**页面参数**——页面在这个值上是确定的，重新取一个值意味着打开另一个页面实例。

按这条判据，详情页的 `opportunity_code` 与 `mtime` 是页面参数而不是隐藏筛选器：在详情页里没有任何交互能改变「看的是哪个机会点」。而同一个 `mtime` 在概览页是用户可改的时间筛选器。同一个业务字段在不同页面可以是不同的东西，这正是判据落在**可变性**而不是落在**是否影响查询**的原因。

**同一语义不得在一个页面里同时以两种形态存在。** 校验器拒绝这种页面。这是真源归一的直接要求：两个位置都能影响同一个查询条件时，读页面的人无法判断哪个说了算。

**页面参数的消费位置由值的位置决定，不由组件类型决定。** 两类位置：

其一是查询谓词绑定：[ADR-0045](./0045-graphql-query-branch-with-structured-predicates.md) 的谓词值来源除筛选器外可绑定页面参数。

其二是**文本取值**——页面文档中一切渲染为用户可见文本的属性位置，其取值类型由 `string` 放宽为 `string | 文本取值引用`。这条规则一句话就能说完：**凡是会被人读到的文本属性，都既可以写字面量，也可以引用一个页面参数。** 它统一适用于分区标题、组件标题与副标题、`reportHeader` 的标题与标签、`text` 的正文、表格列标题等所有此类位置，不维护按组件枚举的白名单。

按组件类型划边界（例如「只有 `reportHeader` 能读参数」）会产生一个结构性错误：页面为了显示一个参数值而被迫引入某个组件。组件应当因为要表达的内容而存在，不应当因为它是某个能力的唯一入口而存在。按**位置**划边界没有这个问题，且规则更短、更好记、更容易被校验器统一实现。

[ADR-0018](./0018-keep-page-metadata-locally-explicit.md) 的局部显式由三条约束守住，而不是由缩小消费范围来守住：引用是**整值替换**，不是模板插值——`{{参数}} 详情` 这类拼接一律不允许，需要拼好的文本由参数本身或数据侧提供；参数取值只能是标量；引用可携带展示格式，且复用 [ADR-0013](./0013-format-belongs-to-component-field-binding.md) 已有的封闭格式闭集，不引入第二套。读页面文档的人在引用处看到的是「这里放参数 X，按格式 Y 呈现」，没有需要跳转才能理解的间接层。

**可选参数缺失时，引用位置整体消失。** 详情页标题栏的四个标签来自四个可选参数，来源实现用一句 `.filter(x => x)` 丢掉空值。本决策把这个语义写进契约：文本取值引用解析为空时，该属性视为未声明，而不是渲染成空字符串。数组型位置（例如标签列表）中的空引用被移除而不是留下空洞。

**跨页下钻可以设置目标页的参数。** `navigate` 现有的 `setFilters` 之外新增 `setParams`，值来源同样是当前行的字段引用。来源实现里那句「已立项取项目名称、未立项取机会点名称」的标题取值逻辑，在本模型里由数据侧返回一个已经择定的字段来承担，页面不做条件判断。

**`from` 不是页面参数。** 它的值是一个 URL 而不是业务数据，它的语义是导航历史而不是页面输入。把它做成页面参数会要求每个可被下钻到的页面都声明一个值域是 URL 的参数，导航语义就此渗进页面文档。它归 [ADR-0048](./0048-navigation-intent-and-host-routing.md) 的嵌入导航契约。

**每个声明的页面参数必须至少有一个消费者。** 没有消费者的参数是噪音，且通常意味着作者本想绑定却绑错了位置，校验器直接拒绝比留到运行时静默失效要好。

## Consequences

- 页面顶层新增可选的 `params`，文本属性取值类型放宽，二者都是纯增量变更，随本批进入 `schemaVersion` 5.1（[ADR-0051](./0051-additive-minor-versions-for-page-schema.md)）。`PAGE-METADATA.md`、zod schema、生成的 JSON Schema 与 `Page` 领域类型同批变更，存量页面不迁移。
- 文本取值引用需要在 schema 里落成一个复用的类型，而不是在每个组件里各写一遍联合。这会触及相当多的组件定义文件，但改的是同一处类型，不是各自的逻辑。落地时应先建立这个类型再逐个替换，避免出现「有些文本属性能引用参数、有些不能」这种最难解释的中间状态。
- URL 编码需要为参数开一个命名空间，与现有的维度前缀 `d:` 与时间前缀 `t:` 并列。参数值不参与 `carryFilters`，跨页传递走 `setParams`。
- 必需参数缺失时页面无法呈现。运行时需要一个明确的失败态——不是空数据，而是「页面输入不完整」，与查询错误分类区分开；深链接被裁剪或宿主传参错误时，这是唯一能让人看懂发生了什么的呈现。
- 跨页校验成为新需求：`navigate` 的目标页是否存在、`setParams` 的键在目标页是否声明、`carryFilters` 的筛选器在目标页是否存在。这要求校验器一次读多个页面文档，是校验能力的一次扩张，需要在 `packages/page` 的校验入口与 `packages/mcp` 的创作期工具上同时落地。
- 文本取值对参数开放后，校验器需要判定引用的参数存在、格式与参数类型相容、以及必需性——引用一个可选参数的位置必须能接受「该属性不存在」，因此必填文本属性（例如 `reportHeader.title`）只能引用必需参数。
- 详情页因此不需要 [ADR-0015](./0015-defer-cascading-data-source-input-semantics.md) 的级联数据源：来源实现里 `party_number` 取自项目详情查询的结果、再喂给客户活动查询，而机会点清单页的查询字段本就包含 `party_number`，改由下钻时作为参数传下来即可。这条绕行使级联数据源不再是本项目的阻塞项，ADR-0015 保持挂起。
- 文本取值的 JSON Schema 是「字面量或引用」联合；`materializePageDocument` 在解析接缝整值替换后，领域类型 `Page` 上这些属性仍是 `string`。纯渲染组件继续只面对字符串。能力探测必须读原始文档，不能读物化后的 `Page`。

## Considered Options

- **全部用 `visible: false` 的筛选器承载。** 零协议变更。但展示型的值会污染筛选状态与 URL 命名空间，而且 `filterBindings` 的 target 闭集里没有「标题」这个目标，标题与标签根本显示不出来。不采用。
- **只让 `reportHeader` 读参数。** 消费面最窄，间接层被压到一个组件内。但它会强迫每个需要显示参数值的页面都引入一个标题栏组件——组件因为「它是唯一入口」而存在，而不是因为要表达的内容而存在。这是结构性的错误耦合，且规则本身（一张按组件枚举的白名单）比按位置划界更长也更难记。不采用。
- **让任意 props 都能引用参数，包括结构化属性与枚举档位。** 表达力最大。但把参数引用开放到 `container`、`variant`、`display` 这类决定结构与档位的属性上，等于让 URL 能改变页面的形状，页面文档不再自描述；而真正的需求全部落在用户可见文本上。限定在文本取值这一类位置，既覆盖需求又不打开结构面。不采用。
- **允许模板插值**（`{{参数}} 详情`）。书写更方便，省掉一些数据侧拼接。但字符串模板是表达式的入口，[ADR-0003](./0003-strict-declarative-spec.md) 的判据一旦在这里让步，后面会有转义、条件、默认值接踵而至。整值替换是能守住的那条线。不采用。
- **按「是否影响查询」分界，影响查询的叫筛选器、纯展示的叫参数。** 直觉上更简单。但这条线会把详情页的 `opportunity_code` 判成筛选器，于是页面上出现一个谁也改不了、却占着筛选状态与 URL 筛选命名空间的筛选器，跨页 `carryFilters` 时还会被误携带。可变性才是真正区分这两个概念的属性。不采用。
- **把 `from` 做成页面参数。** 详情页的声明会更完整、更自解释。但它把导航历史写进页面文档，且每个可被下钻的页面都要重复声明。不采用。
- **不校验「参数必须有消费者」。** 更宽松。但未被消费的参数最常见的成因是绑错位置，此时页面能通过校验、能正常渲染、只是筛选条件没生效——正是最贵的一类失败。不采用。
