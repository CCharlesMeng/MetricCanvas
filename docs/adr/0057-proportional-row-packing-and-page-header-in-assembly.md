# 装配期按比例装箱铺满行宽,并产出页面级页头

ADR-0055 让一句问题铺开跨口径的一整页,组件形态也随口径差异多样化了(指标卡 + 折线图 + 柱状图 + 饼图 + 明细表)。但产物摆不成一页:装配的布局策略只有一行——`buildComponent` 里 `layout: { span: entry.defaultSpan }`,每个组件无条件取组件能力目录的默认宽度,不看同分区有几个组件、不看剩余列数、不做任何装箱。后果是「总量」分区一张 span 3 的指标卡孤零零占一行、右边 9 列全空;而多数口径组只有一个组件,于是折线图 8 / 柱状图 6 / 饼图 4 各自单独一行,右边缘参差不齐。

对比人工搭的看板可以定位到问题不在能力缺口:10 个手写页共 33 个分区、104 个顶层组件,只有 3 处视觉行没占满整宽;每分区组件数的中位数是 2、众数是 1。**手写页的不变量是「视觉行占满」,不是「一个分区里组件多」**——它同样有只含一个组件的分区,只是那个组件是通栏的。

同时,装配产物在页面文档里**没有任何页面级标题**。问题原文写进 `meta.description` 但全仓没有页面内渲染消费者;时间窗口被 ADR-0055 的分区标题按「全页共用即为噪声」剔掉,只留在取数核对与助手回复里。工作台画布上方只有工程元信息(pageId、组件数、数据源数),而沉淀后走 canvas 独立路径打开时连工作台外壳都没有。

## 决策

**组件能力目录的 `defaultSpan` 是相对比例,不是绝对宽度。** 依据是手写页对它的用法:33 个分区里有 14 个覆盖了 `defaultSpan`,但覆盖后的宽度几乎都保持了默认值之间的比例——指标卡(3)配柱状图(6)写成 4 + 8,三张指标卡(各 3)写成 4 + 4 + 4,两张排行卡(各 4)写成 6 + 6,两张指标卡(各 3)写成 6 + 6。目录默认值从不被原样采用,但比例一直成立。装配此前把它当绝对宽度用,是对这个字段的误读。

**装配在每个分区内做确定性装箱:按比例基线贪心分行,每行按各自比例缩放到恰好占满整行。** 因此每个视觉行的 span 之和恒等于分区列数,右边缘不再参差。余数按小数部分从大到小分配,同样大时给声明在前的那个,保证同一输入产出逐字节一致的文档。

`span` 是纯几何,不含语义成分,所以**布局智能放在装配期的纯函数里,模型不参与 span 决策**。这不是效率取舍而是方差取舍:模型每多一个决策就多一份方差,而装箱是可判定问题(输入组件类型序列与列数,输出 span 序列),没有任何需要语义理解的部分。策略落在 `packages/mcp/src/authoring/section-layout.ts`,与硬闸的机器判读表(`auto-visualize` 的 `dataShapeReadings`)同一形态:创作期策略放代码、可穷举单测,不进页面协议。

**装箱只在一个分区内进行,不跨分区搬动组件。** ADR-0055 的一组一分区不动:手写看板的分区划分本来就与口径组对应,它取得「一页」观感的手段是让独占分区的组件铺满宽度,而不是把不同口径合并进一个分区。允许跨口径组并排能买到的东西,分区内铺满已经买到了,而代价是削弱 ADR-0055 的核心判据(口径差异必须落在页面文档自己)。

**分行判断只在比例空间里做。** 目录 `defaultSpan` 以十二分之几表达,所以「这一行装不装得下」是关于比例的问题;声明了受控权重列轨(ADR-0054)的分区只改变最终整数分配,不改变分行结果。

**装配产出页面级页头,内容全部由口径派生。** 页头是独立的首个分区(`container: "plain"`,与手写看板同一做法),标题取各单元业务域的去重拼接,全页共用同一时间窗口时以 `asOf`(「数据窗口」)写出该窗口。任一单元未声明口径时不产出页头——页头的每个字都必须是可派生的事实,装配不替它编一个。

判据与 ADR-0055 让口径差异落进页面文档自己的那条完全相同:页面会被沉淀、被分享、在别的宿主里打开,只有写在文档里的事实才跟着走。ADR-0055 把时间窗口从分区标题剔掉时给的理由是「它在取数核对与助手回复里已经完整可见」,这与同一份 ADR 拒绝「只在聊天里提示」用的理由自相矛盾;页头是它的正确归宿。

**页头不用问题原文当标题。** 部分可答时问句里含缺口指标(ADR-0036),拿问句作页面标题等于让页面在最显眼的位置承诺自己没有的数字——ADR-0036 在数字与组件层面禁止的事,在标题层面同样禁止。问题原文继续只进 `meta.description`。

**页头不经组件推荐的硬闸,硬闸前提一个字不改。** `auto-visualize` 对 `bindsData: false` 的组件一律拒绝,理由「不消费页面数据源,不能承载取数单元结果」是正确的:硬闸回答的是「哪个组件能承载**这个取数单元**的结果」,而页头不是任何单元的呈现,它是页面级事实。因此页头在单元循环之外单独产出,而不是放宽硬闸让一个不绑数据的候选去承载某个单元。

**不产出 `text` 与 `aiSummary`。** `text` 的 `body` 是人写的分析结论,装配没有可信来源,硬造就是猜。`aiSummary` 在 10 个手写页里出现 0 次,没有证据支持它属于目标观感。

## Consequences

- `assembleTransientPage` 的出口形状再次变化(分区数多一个页头分区,组件 span 由装箱换算)。与 ADR-0055 同理:这是创作期装配的出口形状变化,页面协议不动,**不触发 ADR-0051 的版本递增**。
- 页面文档的分区组件不再全都绑定页面数据源。消费装配产物的代码必须按「有没有数据槽」分流,不能假定每个组件都有 `data.main`——编排的 `DocumentReadyEvent` 组件清单据此排除页头(页头不承载单元,不进清单),测试辅助函数同样只取绑数据的组件。
- `defaultSpan` 的角色被重新表述为比例基线。它仍然是产品/领域决策、仍然人写在 `packages/page/src/schema/components/*.ts` 的 catalog registry 里、仍然是全局默认;改变的只是装配对它的读法。手写页面继续显式声明 `span`,不受本决策影响。
- 装配产物里出现宽度上更极端的组合:独占分区的饼图与排行卡会被拉到通栏,而手写页里饼图的 span 只取过 3 和 4、排行卡只取过 4 和 5。目录没有「宽度上限」概念,本决策也不新增——**先按单一不变量(行占满)落地并观察真实产物**,确有需要再单独裁决上限,避免在没有证据前给每个组件类型手写一份宽度表。
- ADR-0038 的「行对齐运行时不变量」是行**高**对齐(同类型组件按最大自然高度对齐),与本决策的宽度装箱互不影响,两者叠加后同一行的组件既等高又占满整宽。
- 受控权重列轨(ADR-0054)仍然未被装配使用:权重轨是为表达外部设计源的精确比例准备的,装配没有设计源,12 列等权加比例装箱已经够用。

## Considered Options

- **让模型决定分区内的 span 组合。** 否决:span 不含语义,模型只能带来方差。同批实测已经踩过两次模型方差(意图被整句问题串味、单元数溢出被静默截掉)。
- **允许相邻口径组在呈现上合并进同一分区,以便小组件并排。** 否决:见上,收益可由分区内铺满取得,代价是削弱 ADR-0055 的核心决策。
- **用 `compositeCard` 把多个口径组的小组件收进一张卡。** 否决:组合卡的子组件白名单只有指标卡、饼图、仪表、键值面板与分类明细,装不下典型产物里的折线图、柱状图与明细表;且它同样要跨口径组合并。
- **给组件能力目录新增 `maxSpan`,拉宽时按类型设上限。** 否决(暂):这是在没有真实产物证据前先写一份全局宽度表,而 `defaultSpan` 已经是产品决策、改动影响所有消费者。留作后续按需裁决。
- **给不该拉宽的组件在分区内居中或留白。** 否决:对齐方式不在页面协议里,ADR-0054 明确页面文档不能写对齐方式;而留白正是本决策要消除的那个现象。
- **用问题原文作页头标题。** 否决:见上,与 ADR-0036 的缺口边界冲突。
- **不产页头,把页面标题交给宿主。** 否决:工作台画布上方只有工程元信息,而沉淀后走独立路径打开时没有宿主外壳,页面会完全没有标题。
- **让 `auto-visualize` 的硬闸放行 `bindsData: false` 的组件。** 否决:硬闸判读的是「哪个组件能承载这个单元」,页头不是单元的呈现;放宽它会让每个单元都可能被配成一个不绑数据的组件。
