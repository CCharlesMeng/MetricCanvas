# 独立创作包提供 MetricCanvas，RuntimeView 保持正式渲染

为渲染引擎独立交付，创作覆盖层拆为独立包，对外创作组件命名为 `MetricCanvas`；正式渲染继续使用 `RuntimeView`。创作包依赖渲染包，渲染包不反向依赖创作包，纯渲染消费者安装的依赖与构建产物均不包含创作专用代码。两种入口共用渲染与布局实现，不复制第二套布局。该裁决来自地图 [#95](https://github.com/CCharlesMeng/MetricCanvas/issues/95) 的 [#96](https://github.com/CCharlesMeng/MetricCanvas/issues/96)，已确认；实施由 #56 跟踪。

`MetricCanvas` 负责布局中的选中、拖拽、编辑触发和意图回传；页面文档由宿主持有和更新，属性面板、保存与撤销历史等工作台能力仍归宿主。本次是分离已有创作行为，不新增完整编辑器能力。`MetricCanvas` 是组件导出名，不据此裁决 npm 包名，也不新增同名领域概念。

## 取舍

- 不采用同包双入口：即使构建时排除创作代码，安装包仍包含它，不能满足本次选定的物理隔离要求。独立包的代价是额外的发布单元与兼容关系，交由 [#100](https://github.com/CCharlesMeng/MetricCanvas/issues/100) 定义包名、版本策略与发布门禁。
- 不保留 `RuntimeView` 的可选 `authoring` 用法：独立创作入口使正式渲染的 Interface 不再承担创作职责。platform 是当前唯一创作消费者，实施时一次性迁移，并删除旧参数及渲染包的创作专用导出，不另建过渡兼容入口。
- 不把 platform 工作台整体搬入引擎：创作画布处理布局交互，宿主继续管理编辑文档和工作台流程。字体、主题、页面文档来源、身份与数据网关的宿主契约仍由 [#97](https://github.com/CCharlesMeng/MetricCanvas/issues/97) 裁决。

## 实施与行为约束

[#96](https://github.com/CCharlesMeng/MetricCanvas/issues/96) 只记录切口决策，已有执行票 [#56](https://github.com/CCharlesMeng/MetricCanvas/issues/56) 实施并回归，不再依赖 [#55](https://github.com/CCharlesMeng/MetricCanvas/issues/55) 先提取运行时会话。定向核对发现，当前创作意图回传宿主修改页面文档，创作状态并未直接管理查询与筛选编排；#55 因而是独立重构，不是本次创作隔离的技术硬前置。

实施需守住以下不变量：

- 正式渲染的依赖图、安装依赖与产物中不含创作专用 Module，且不创建拖拽、选中、编辑或创作诊断状态；验证不能只检查包名或顶层导出。
- 仅选中组件或切换创作控件不重启查询、不丢筛选与分页状态。页面文档替换沿用已有初始化语义，本决策不新增“编辑永不重新取数”的承诺。
- 创作选择对页面原有交互的事件拦截关系保持一致；正式渲染的数据快照与筛选状态语义不变。
- 草稿布局允许的空内容分区不进入正式页面校验通道，不以创作需求放宽页面协议；两种入口共用页面协议和纯渲染组件。

包内重组及跨包组合接缝的具体实现由 #56 完成，不能用复制布局或反向引入创作代码来满足表面上的分包。需要对外导出的跨包接缝须在 #100 的公开 API 与版本兼容门禁中显式对账，不能仅以“内部”命名规避契约责任。
