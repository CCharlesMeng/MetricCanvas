# 页面时间范围支持结构化相对时间表达

长期运行的 Data App 的价值前提是时间窗会自己往前滚：一个“每月都要看”的页面，下个月打开必须看的是下个月。当前 `timeRange` 筛选器的 `default` 只能取 `today`、`last7d`、`last30d`、`last90d` 四个天级预设，或一对绝对时间 `{ from, to }`。分析师的真实表述是“近半年”“上个季度”“本年至今”“最近 6 个月”，这些既不在预设内，也不能用绝对时间表达——写成绝对时间的页面在下一个周期就是错的。

## 决策

**`timeRange` 的 `default` 新增结构化相对时间分支，与既有预设和绝对区间并列。** 相对表达由三部分组成：粒度单位（日、周、月、季、年）、区间描述（最近 N 个单位、上一个完整单位、本单位至今）以及锚点（默认为当天；允许显式指定固定锚点日期，用于复现历史结论）。相对表达是声明式数据，不是表达式字符串，也不是脚本——ADR-0003 的“页面不含表达式与脚本”原样成立。

**求值发生在服务端取数编排期，不在浏览器。** 相对表达在请求数据网关之前被求值为绝对区间，求值结果随查询一起流转；DQE 与其他协议收到的始终是绝对时间。这保证同一次页面加载内所有数据源看到同一个时间基准，不会因跨零点或多次请求而各自求值出不同结果。既有四个天级预设保持不变，视为相对表达的简写。

**保留绝对区间，因为 Report 需要它。** 按 ADR-0030，报告冻结在采集时点，其时间必须是绝对的；Data App 则必须是相对的，否则不会滚动。因此两种表达都不能删，且沉淀时的方向不同：沉淀为 App 时，若页面时间是绝对区间，必须显式改写为相对表达或由用户确认保留。

**问数生成的时间条件必须落到这套表达上。** 自然语言里的“近半年”由 ADR-0037 的编排映射为结构化相对表达并进入口径回显，不允许模型直接写死一对日期后再声称页面可长期运行。

**默认口径必须显式声明，不靠推断。** “本月”是否含当天、“最近 6 个月”是否含当月未完成的部分、周的起始是周一还是周日，这些无法从数据推断，也是问数最常见的静默错误来源。相对表达必须能显式承载“是否包含当前未完成周期”，其默认值在实现时一次性钉死并写进文档。

## Consequences

- `packages/page` 的 `timeRangeFilterZ.default` 从二选一联合扩为三选一，页面 JSON Schema 与 `PAGE-METADATA.md` 需同步；既有页面不需要迁移。
- 取数编排新增相对时间求值步骤，且必须在一次页面加载内共享同一个求值时刻；这一时刻应可注入，否则相关测试不可确定性复现。
- 内嵌初始行（ADR-0020）的语义需要澄清：初始行是按采集时刻的绝对区间取的，页面下次打开时相对区间可能已经不同。因此使用相对时间的 App 页面在默认状态下不能只靠内嵌初始行渲染，必须按新求值结果重新查询，否则会展示过期数据。这是相对时间引入的实质约束。
- 时间粒度从天级扩展到周/月/季/年之后，与指标条目的时间聚合方式（ADR-0031）产生耦合：跨粒度聚合方式错误会安静地算错，因此粒度改写必须受可加性约束。
- Monitor 未来所需的“每期自动重算”能力由这套表达承载，不需要另建调度期时间语言。

## Considered Options

- **继续只用天级预设加绝对区间。** 改动最小，但“近半年”“上季度”无法表达，长期运行的 App 只能写死日期，与产品目标直接冲突，不采用。
- **允许时间表达式字符串（如 `now-6M/M`）。** 表达力强且有业界先例，但引入需要解析器的表达式语言，与 ADR-0003 冲突，且模型生成的字符串无法被 JSON Schema 校验，不采用。
- **在浏览器求值相对时间。** 免去服务端改动，但同一页面的多个数据源可能求值到不同基准，且跨零点行为不可复现，不采用。
- **只扩充预设枚举（追加 `last6m`、`lastQuarter` 等）。** 改动比结构化表达更小，但枚举会随业务表述持续膨胀，且无法表达“是否包含当前未完成周期”与固定锚点，不采用。
