# 页面协议改为增量次版本演进，主版本递增须论证无法增量表达

`packages/page/src/version.ts` 的版本策略只有一个字段:

```ts
export const versionPolicy: VersionPolicy = { current: '5.0' };
```

`supportedVersions()` 返回单元素数组,`versionErrors()` 对任何非当前版本的文档报「旧版本必须在接入前完整迁移」。历史上两次版本变更都是硬切换:[ADR-0017](./0017-page-schema-v3-hard-cutover.md) 一次性删除旧结构化查询切到 3.0,[ADR-0038](./0038-section-container-and-row-alignment-invariant.md) 删除 `section.variant`/`section.layout` 切到 5.0。

**这套策略与本仓自己的生命周期模型直接冲突。** 页面修订不可变且线性前进（[ADR-0008](./0008-immutable-page-revisions-and-publish-leases.md)）;页面模板只保存对精确已发布修订的引用、不复制文档（[ADR-0010](./0010-page-templates-reference-published-revisions.md)）;报告保留查询定义与内嵌初始行、内容冻结在采集时点（[ADR-0030](./0030-transient-page-state-for-ask-and-explore.md)）。这三条都要求旧文档在很长时间内保持可读。而「迁移一份不可变修订」在语义上不成立——迁移的产物是一个**新**修订,模板引用的、报告冻结的、发布指向的仍然是旧那一个。硬切换会让它们同时失效。

前两次硬切换之所以可行,是因为当时没有生产内容:今天 `pages/` 下只有 7 份存量页面,迁移成本可以忽略。一旦有真实的 Data App 在跑、有模板引用、有冻结的报告,同样的动作代价完全不同。

`docs/adr/README.md` 已经记录了一个相关观察:3.0→4.0 的切换没有专门 ADR,4.0 版本内新增的 AI 总结组件、内嵌初始行与查询分页由 [ADR-0019](./0019-internalize-ai-summary-generation.md)、[ADR-0020](./0020-embedded-initial-rows-and-query-pagination.md) 分别承载。README 把它记为「ADR 记录里的一处已知空白」。事后看,那次恰恰是本决策要正式化的行为——版本内的增量增长——只是当时没有策略为它背书。

## 决策

**`schemaVersion` 采用 `MAJOR.MINOR`,两级各有明确含义。**

**次版本递增只用于纯增量变更。** 判据是封闭的四条:新增可选字段;判别联合新增分支;封闭闭集新增成员;放宽既有约束（原本被拒绝的文档变为合法）。满足这四条意味着**当前主版本内最新的 schema 是该主版本全部次版本的超集**,因此单份 schema 即可校验所有次版本,不需要为每个次版本维护一份。

**主版本递增用于破坏性变更**:删除字段、收窄闭集、改变既有字段语义、加严既有约束。**每次主版本递增必须写独立 ADR,并论证为什么该变更无法以增量方式表达。** 这条论证义务是本决策的主要约束力所在——它让「顺手清理一下」无法通过,因为清理的收益必须显式地与让全部已发布修订、模板引用与冻结报告失效的代价放在一起比较。

**例外(2026-08-25 补):从未被行使的开放面可以按次版本收紧。** 一处约束点若在全部存量页面文档中零使用,收紧它不会让任何既有文档失效,因此不产生本决策要防的那种代价。行使这条例外必须同时满足三条判据:

1. **零使用。** 该约束点在本仓全部页面文档中没有任何一处行使过——`pages/` 下的存量页面、`packages/*/fixtures/` 下的校验样例,以及模板引用与冻结报告指向的已发布修订,全部计入。
2. **可证。** 零使用由测试或脚本证明,并随收紧一并落地;不接受人工目测的结论,也不接受"翻了一遍没看见"。
3. **形式超集让位于实际超集。** 收紧后的 schema 严格来说不再是旧次版本的语法超集,本决策接受这一点,因为在**真实存在的文档集合**上它仍然是超集。这也正是判据二不能省的原因:证明失效时,超集关系就真的破了。

**这不是"加严既有约束"的一般性豁免。** 只要有一份存量文档行使过该开放面,哪怕只有一处、哪怕看起来无关紧要,收紧就是破坏性变更、就是主版本递增。"很少使用"不是判据,"零使用且可证"才是;判据必须是一条可执行的检查,否则这条例外就是绕过版本策略的后门——每次变更都会有人论证自己那次的使用量足够接近零。

本条的第一个适用对象是组件 `layout` 对象缺少 `.strict()`:每个组件的 `props` 都是 `.strict()`,`layout` 不是,因此写错键名(例如 `spans`)会静默通过,页面看起来正常而声明无效。补上 `.strict()` 是一次收紧,但 `layout` 的未知键从未被任何存量文档写过,满足上述三条。

**校验器接受当前主版本内不高于 current 的任意次版本。** 跨主版本不接受,也不提供自动迁移。

**声明的版本是能力下限,不是装饰。** 维护一张「能力 → 引入次版本」表,校验器从文档实际使用的结构推算它所需的最低次版本,高于声明值即报错。没有这条,`schemaVersion` 会退化成一个谁都可以随便填的字段:一份声明 `5.0` 却使用了 5.1 能力的文档能通过校验,然后在只支持 5.0 的嵌入宿主里渲染失败。这张表每个次版本只增几条——本批次是 `params`、页面布局形态与叠放层、数据源计算阶段、四类新筛选器、层级维度、级联、表格的三个新属性、四个新组件,二十余条——维护成本远低于它挡住的失败。[ADR-0045](./0045-graphql-query-branch-with-structured-predicates.md) 的 `graphql` 查询分支**不在本批次内**:它仍是提议,`QUERY_LANGUAGES` 只有 `dqe`,该能力由它真正落地的那个次版本登记。

**本批次交付 5.1。** [ADR-0045](./0045-graphql-query-branch-with-structured-predicates.md) 至 [ADR-0050](./0050-filter-type-closure-and-hierarchical-dimensions.md) 的全部页面协议变更逐条核对后均满足增量四条判据,没有一处破坏性变更。ADR-0048 不改页面协议。

## Consequences

- `VersionPolicy` 从单值 `current` 改为承载主版本、当前次版本与该主版本的能力表。`supportedVersions()` 的语义从「唯一支持版本」变为「当前主版本内已发布的次版本列表」,`pageDocumentSchemaZ` 的 `schemaVersion` 枚举随之扩展。
- 能力表是新增的维护负担,但它同时成为「某个能力是什么时候有的」的唯一真源——这个信息今天只能靠翻 ADR 和 git log 拼凑。新增能力时必须同批登记,否则能力下限计算会漏判;这一点应由测试守护。
- **兼容负担会在主版本内累积:一旦发布就不能删。** 这是有意接受的代价,也是本策略的成本所在。缓解方式不是偷偷删除,而是承认它——某个能力确实必须移除时,那就是一次主版本变更,代价显式呈现并经 ADR 论证。
- 已发布修订、模板引用的修订、冻结的报告在整个主版本生命周期内保持可读。这是本决策的主要收益,也是它与 ADR-0008/0010/0030 一致的地方。
- ADR-0017 与 ADR-0038 的硬切换不追溯、不改写。它们在各自的时点是合理的;本决策改变的是从此刻起的规则。
- 增量约束会对协议设计产生反向压力:新能力必须设计成可选的、可并列的,而不能修改既有结构的语义。这通常会让设计更好,但偶尔会让某个方案比「直接改掉旧字段」啰嗦一些。这是刻意的取舍。
- 运行时与嵌入宿主之间因此有了可协商的版本语义:宿主可以声明自己支持到哪个次版本,平台据此判断某份文档能否在该宿主渲染。本决策不设计这套协商,只是让它成为可能。

## Considered Options

- **保持单版本硬切换。** 校验器最简单,永远只认一个形状,没有兼容分支。但它与不可变修订、模板引用精确修订、报告冻结三条既有决策直接冲突,且冲突会随着生产内容增加而放大。不采用。
- **接受多个次版本但不校验能力下限。** 实现最省事。但 `schemaVersion` 会退化为装饰字段,嵌入方无法判断自己的运行时是否够新,失败推迟到渲染期。不采用。
- **为每个次版本维护一份独立 schema。** 最严谨,能精确表达每个版本的合法形状。但 schema 份数随版本线性增长,而在纯增量约束下超集 schema 加能力下限计算已经等价。不采用。
- **用能力清单协商代替版本号**(文档显式声明自己用到哪些能力)。表达更精确,粒度更细。但要求作者维护清单,AI 生成时极易漏写或多写,且清单与实际使用不一致时没有裁决方——版本号加上由工具推算的能力下限,把这个负担从作者移到工具侧。不采用。
- **允许次版本内做「小的」破坏性变更**(例如只影响某个很少使用的字段)。现实中很有诱惑力。但「小」没有判据,一旦开口,每次变更都会有人论证自己那次足够小,而受害者是无法参与讨论的已发布修订。不采用。
