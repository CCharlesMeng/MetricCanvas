# 查询分页下由上游执行排序与表头筛选

[ADR-0049](./0049-table-server-side-and-presentation-capabilities.md) 把表格分页分成 `none` / `local` / `query` 三档，但 `query` 档同时拒绝列上的 `sortable` 与 `filterable`（`validate.ts` 里两条硬拒绝）。原因是当时只有本地实现：本地排序与本地表头筛选都只作用于**当前页快照**，在分页下那不是降级，是错的——「按金额降序」的第一行应该是全表最大值，而不是首页那几行里的最大值。

代价在 `pages/ioc-opportunity-list.json` 上很具体：它有 15 列金额排序和 5 列表头筛选，为了保住这些，分页只能退到 `none`。现在才 10 行看不出问题，接上真库就是每次全表拉取。**「有分页」和「能排序」二选一**，这不是一个可以长期接受的形状。

## 决策

**排序与表头筛选在查询分页下由上游执行，两者不再互斥。**

**排序进生效查询，编码沿用中间层文档的 `@order(type, priority)` 语义。** `EffectiveQuery` 新增 `sort`，数组序即优先级；数据网关把它编成 `order.by`：

```json
"order": { "offset": 0, "limit": 5, "by": [{ "field": "bidding_amount", "type": "desc", "priority": 1 }] }
```

`type` 与 `priority` 不是新造的名字，它们来自 `docs/evidence/中间层分析.md` §2.3.5 记录的 `@order(type:"asc", priority:1)` 指令语义（asc/desc 两向、多字段按 priority 定序）。**这条编码尚未在真实环境复验**，与 `dimensionValuesDqeItem` 同批归 issue #3。

**表头筛选落到维度谓词上。** `select` 模式是集合包含，直接复用既有的 `filter.dims` 条目；`dateRange` 模式是同一维度上的两条带 `operator` 的比较谓词（`>=` / `<=`），端点各自可缺席。带 `operator` 的维度谓词本仓既有页面已在用，不是新形状。

**排序与表头筛选是会话态，不进页面文档。** 它们是用户当下的看法，不是页面的声明，因此存在编排器的会话里，随页面卸载消失。这与筛选状态可分享进 URL 的设计是两回事：筛选是页面声明的口径，表头交互是临时视角。

**两者变化都把页码重置到第一页。** 排序或表头筛选改变了结果集的组成，停在第 5 页去看新结果的第 5 页没有意义。

**字段没有 `queryField` 映射时整条跳过。** 计算产出等本地字段不是上游取来的列，拿字段 id 冒充查询字段会得到一条上游看不懂的谓词。

## Consequences

- `ioc-opportunity-list` 换回 `pagination.mode: "query"`，15 列排序与 5 列表头筛选全部保住。为了让分页真的存在，每页行数设为 5、`source.initial` 相应缩为完整的第一页 5 行、`totalCount` 保持 10。
- 浏览器证据钉的正是「全表排序还是当页排序」这件事：升序后第一行是 `OPP202604010`（金额最小，**在第二页**）。本地排序取不到它——它压根不在当前页的数据里。
- `Table.svelte` 里两处 `pagination?.mode !== 'query'` 的交互禁用随之解除。这两行是上述互斥在组件侧的投影，协议放开了它们就没有理由留着。
- 仿真侧的 `validOrder` 与 `pageOrder` 从「`order` 非空即视为分页」改成按 `limit` 判定：`order` 现在同时承载分页与排序，只声明排序时整份结果都要返回。
- `search` 筛选器仍走客户端 `inline-search`，它在分页下会退化成「只筛当前页」——与本决策要消灭的是同一类问题，但 search 没有绑定目标（[ADR-0085](./0085-query-binding-targets-for-the-non-dimension-filter-types.md) 明确把它排除在外），得先有谓词形状才谈得上下推。这是已知的剩余缺口。

## Considered Options

- **保持互斥，让作者在分页与排序之间二选一。** 不改任何东西。但这把一个实现限制冻结成了协议约束，而真实清单页两个都要。不采用。
- **查询分页下把当前页拉全（limit 设成 totalCount）再本地排序。** 排序结果正确，改动最小。但这等于取消分页，正是分页要解决的问题。不采用。
- **等真实 DQE 排序协议确认后再做。** 最稳妥。但排序编码只是数据网关里的一个映射函数，页面协议、编排层、组件交互这三层的形状与它无关；把三层一起挂起来等一个映射，代价远大于之后改一个函数。按本仓既有做法（`dimensionValuesDqeItem` 同样待复验）落地并标注。不采用。
- **把排序也做成页面声明（`props.orderBy`）而不是会话态。** 作者能定初始排序。这与本决策不冲突，但它解决的是「初始顺序」而不是「用户点列头」；初始顺序今天已经能由查询定义自带的 `order` 表达。不在本次范围。
