# 归因诊断作为与问数并列的分析形态

问数回答「是多少」，归因诊断回答「为什么变了」。后者是数据分析中最高频也最容易出错的一类诉求：它要求先确认波动事实，再拆解贡献、定位集中范围，必要时继续下钻，最后在证据不足处如实说不知道。存在一份可参考的外部实现（`参考/skills/attribution-analysis`），它证明了流程可行，但把五类职责揉在一起：指标与维度能力发现、查询语句生成与工具执行、归因流程与贡献计算、权限与特殊地区规则、Markdown 与私有占位符输出。查询工具、归因算法与页面渲染之间没有稳定 Interface，因此不能原样迁入。

现有问数编排（ADR-0037）覆盖不了归因诊断，原因是结构性的而不是功能缺失。问数是一条固定顺序的状态机：一次规划出多个**相互独立**的取数单元，串行执行，首个单元失败即整轮中止，每轮执行预算是一个硬编码常量（`MAX_UNIT_EXECUTIONS_PER_RUN = 6`）。归因诊断则是结果驱动的多阶段过程——本轮证据决定下一轮查询什么、是否继续下钻、何时停止。把结果依赖塞进 `applyUnitOperations` 会把问数那条已经稳定的路径拆坏。

同时，接入这类能力时最容易犯的错是为它新建一整套并行设施。此前讨论中出现过的 `metric-query` Skill 与 `anomaly-runner` 都属于这一类：前者依赖一个仍在规划中、当前不可用的接口（`/semantic/api/v1.1/metrics/query`），后者只是一个技术标签，且监测已由 ADR-0030 裁决为当前不建设。

## 决策

**归因诊断是 `AgentRunner` 的第二个实现，不是问数编排的扩展。** `AgentRunner.run` 返回 `AsyncIterable<AgentEvent>`，问数是它的一个实现（`createAskOrchestrationRunner`），归因诊断成为并列的兄弟实现。两者共享步骤事件的落库与 SSE 翻译、临时页面态、会话可见性过滤与页面校验准入；**不共享编排状态机**。共享的是设施，不是流程。

**分析种类路由发生在选择 runner 之前，输入只有问题原文。** 「为什么下降」「哪些因素贡献最大」这类明确诊断意图自动进入归因诊断，「查看收入趋势」继续走问数，模糊时澄清。**仅检测到数值发生变化不自动启动归因诊断**——那属于监测，已裁决不建设。路由结果必须向用户展示系统理解的指标、范围与比较基线，理由与 ADR-0037 的域回显一致：静默路由错会产出看起来完全正常的错结论。

**归因逻辑只面向分析证据 Port 编程。** 归因策略声明「需要什么证据」，不声明「怎么取数」。生产侧的指标证据适配器把证据需求转换成取数单元，复用 `deriveExecutableUnit`、清单校验与真实执行（ADR-0032）以及数据网关；专家经验是**第二个**生产适配器；测试侧的内存适配器提供稳定证据，使归因策略的黄金测试完全不接触网络与数据库。策略层不知道 DQE 存在。代码名 `AnalysisEvidencePort` 暂定，与 ADR-0032 的「取数单元」同例。

**确定性计算不经过模型。** 波动额、波动率、贡献度、Top K、覆盖率、方向判定与同维度内的贡献对账全部是纯函数，由黄金案例覆盖。模型可以选择已批准的分析路径、决定下一步需要什么证据、生成解释文字；**不得发明业务公式、修改贡献口径，或把任意字段解释为业务因子。**

**不同维度的贡献不可相加，且这是类型约束而非注释。** 贡献只在单个维度的作用域内存在，跨维度求和在类型上写不出来。同一维度内的成员贡献必须与总波动对账；不同维度是平行观察切面。页面禁止生成跨维度的总贡献排名。因子贡献与维度贡献分别计算、分别呈现。

**分析结果不是新的聚合根。** 看板页面仍是平台唯一聚合根（ADR-0006、ADR-0007）。分析结果是一次分析过程产生的结构化结果，经页面组装成为临时页面态；分析会话继续是服务端步骤事件记录，不是页面草稿。此处不引入服务端计算数据集，ADR-0033 的挂起原样成立。

**结果必须允许未知，并分四级表达。** 事实（数据直接计算）、归因发现（有贡献数据支持）、原因假设（存在关联证据但未验证）、未知（证据不足）。系统不得为了完整回答而把假设包装成结论；「已定位集中范围但无法确认原因」是一个合法且必须可表达的输出。第一版是**归因诊断，不承诺因果证明**：外部事件与专家经验只能作为关联证据，`confidence` 若采用则表示证据完整度或结论稳健度，不表示因果置信度。

**因子归因是读取上游已标注的诊断数据，不是本平台的计算。** 参考实现中不存在 `Δ = Σ 因子` 的加法恒等式：上游的场景匹配引擎在数据落表之前已经为每一行打上原因标签（`reason_info`），本平台消费的是打好标签的输出。因此本平台承担的是排序、按标签聚合与措辞，其中因果方向（反向／同向／中性／固定）来自一份带兜底行的声明式映射，上游新增场景不会打穿映射。**匹配谓词属于数据侧流水线的内部逻辑，不进入本平台。**

**专家经验的展示顺序与证据等级是两根独立的轴。** 人工录入的原因说明算作证据，展示优先级高于系统诊断结论；但它按上一条分级属**原因假设**，块上如实标注等级并带出录入人与录入时间。它排在**归因发现**之上，不排在**波动事实**之上——可以先解释原因，不能盖掉数字。顺序是产品裁决，等级是诚实度，两者不互相冒充。

**比较基线使用有优先级的规则。** 用户明确指定时以用户为准；指标存在默认基线时采用已配置基线；上下文只有一种合理解释时可自动采用但必须展示；同比、环比等存在多种合理解释时先澄清。基线在取数单元层由字面量时间与粒度确定性推导，不依赖 ADR-0035 的页面级结构化相对时间。

**自动多轮查询与下钻受约束，且在数据权限归属裁决前采用保守边界。** 原始分析范围内可以查询声明过的业务因子、对集中点继续下钻、获取同期数据。更换指标、扩大时间或组织范围、引入敏感维度、改变比较基线或超出预算时必须重新确认。**在「行级与指标级过滤由 DQE 还是本平台承担」被裁决之前，自动下钻只在用户已明确出现在筛选条件里的维度及其声明过的下级中进行，不做自主探索。** 参考实现最重要的安全规则是筛选维度必须全量转发、漏一个即越权；把下钻候选集从筛选条件推导而不是从「允许的维度全集」里挑，使这条规则成为结构约束而非实现时的小心。代价是部分本可自动定位的集中点需要用户多说一句话；该约束在权限裁决后可显式放开。

**自动下钻采用双层停止规则。** 平台硬限制：最大查询次数、最大下钻深度、最大耗时、最大返回行数、取消与权限失败。指标业务规则：贡献覆盖率、剩余波动阈值、最小样本量、允许的下钻维度、继续查询能否提升证据质量。首轮可用「最多 3 层、Top 5、覆盖主要贡献后停止」作为可配置起点，**具体数值不得硬编码为普遍业务规则**。既有的 `MAX_UNIT_EXECUTIONS_PER_RUN` 常量随之改为按形态传入的策略参数。

**归因诊断的自然沉淀形态是报告，不是 Data App。** 证据采集于一个确定时点，专家批注带责任人与录入时间，与 ADR-0030 中报告的语义一致（保留查询定义与内嵌初始行、不声明筛选绑定、冻结在采集时点、保住口径溯源）。因此 ADR-0035 的结构化相对时间不在归因诊断的关键路径上。

**明确不建设：** 独立 `metric-query` Skill；规划中的 `/semantic/api/v1.1/metrics/query`；`anomaly-runner`；为归因新增查询协议；Markdown 与私有占位符渲染链路；新的页面聚合根或服务端计算数据集；本范围内的异常监测、调度与通知。

## Consequences

- 归因结果的渲染目标在页面协议中**已经存在**：`recordList/detail`（ADR-0026）承载客户→云服务这类嵌套归因明细，`semanticHtml/detail`（ADR-0028）承载已完成组合的归因文案，ADR-0042 处理其中的金额。缺的只是 `assembleTransientPage` 当前从不自动绑定归因明细（排行详情的可选语义是刻意不自动绑的），因此需要一个诊断专用组装器显式绑定，而不是新建渲染链路。
- 分析证据 Port 下面自第一期起就有两个生产适配器（指标证据、专家经验），Port 抽象因此是被证明过的而非投机的。专家经验走 REST 但**不需要**数据网关适配器：ADR-0034 约束的是生效查询，而专家经验在创作期被采集、以内嵌内容进入页面。
- 分析会话需要新的步骤事件种类：阶段、证据摘要、发现、下钻路径、停止原因与证据质量状态。当前会话存储是进程内实现，**不足以支撑诊断复跑与事后审计**，落库能力成为归因诊断的前置项而不是后续增强。
- 承载归因规则的概念定名为**指标归因定义**（代码名 `MetricAttributionDefinition`），但它的字段集与 Schema 元数据的版本升级留作**独立决策**（ADR-0044，待数据侧输入到齐后撰写）。今天 `formatVersion` 仍是 `1.0` 且不存在一等指标条目（ADR-0031 裁决的 `1.1` 从未落地，可加性至今是 `description` 里的一句受控中文散文），zod `strictObject` 与 JSON Schema 的 `additionalProperties: false` 都会拒绝新键。规则集无处可挂，因此顺序是先偿还 ADR-0031 的欠账、再让归因规则成为指标条目上的可选块，第一期以仓库内带类型与校验的配置存在，不建治理平台。
- 领域词汇表已新增词条：指标归因定义、归因诊断、波动事实、分析证据、贡献度、归因下钻。其中**归因下钻**与既有的页内下钻、跨页下钻是不同概念——前者是创作期的分析取证动作，后两者是渲染期的筛选交互，词条已就此互相排除。
- 以下属可逆的实现设计，记录在此以免重新讨论：确定性计算内核先作为 `apps/platform` 内的 module，出现第二个消费者再按 ADR-0024／0025 的判据提包；会话步骤事件的 PostgreSQL 适配器在既有 `AnalysisSessionStore` 端口后实现（端口已存在，换实现是 drop-in），DDL 写成自包含迁移文件以便 #52 后续吸纳，不等 #52（它被 #48、#41 阻塞）；基期推导作为中立机件归入本 ADR 的地基部分，PRD #85 的派生度量模板直接复用同一份实现，不各写一遍。
- 首个真实纵向切片是公有云流水，当前阻塞于两项数据侧输入：指标条目所需的可加性与维度层级关系，以及一个业务认可的黄金案例。等待期内可推进的只有与指标无关的部分。
- 参考实现的多处内部矛盾不得盲抄：SKILL 的「公有云流水」与配置的「流水」、`scenario=归因分析` 与 `attribution_analysis`、专家经验接口的 POST 与 GET、以及只出现在实现说明中的 ≥5% 影响因子阈值（已裁决按诊断工具返回的贡献度为准）。

## Considered Options

- **扩展现有问数编排以支持结果依赖。** 复用最大，但要在一条已稳定的固定顺序状态机里引入单元依赖、失败隔离与循环，等于同时承担两种流程的复杂度；ADR-0015 挂起级联数据源输入语义的理由在此同样适用，不采用。
- **单独建设 `metric-query` Skill 承担取数。** 会形成第二条问数链路与第二套口径来源，且依赖一个当前不可用的规划中接口；需要的是领域侧的证据 Interface，不是 Prompt 驱动的查询 Skill，不采用。
- **建设 `anomaly-runner` 作为顶层概念。** 技术化命名，且异常检测若未来建设应是分析领域内的可选策略；监测已裁决当前不建设，不采用。
- **把因子拆解、维度归因、下钻、外部事件关联各设为顶层 Module。** 它们都是「归因诊断」这一阶段内部的分析动作，提为顶层会让模块关系反映实现步骤而非领域概念，不采用。
- **原样迁入参考 Skill 的 Markdown 与占位符输出。** 统一运行时将不得不解析一份私有协议，且富内容绕过受控语义 HTML 的治理契约，不采用。
- **让分析结果成为第二个聚合根，带独立 id、修订与发布治理。** 与 ADR-0033 拒绝计算数据集的理由相同（实质修订 ADR-0006／0007），且分析结果的价值在于被看见与被沉淀，不在于被长期治理，不采用。
- **第一期即放开自动跨维度探索。** 诊断质量更高，但在数据权限归属未裁决时，自动钻进用户未提及的维度正是越权风险最集中处，不采用；保留为权限裁决后的放开项。
