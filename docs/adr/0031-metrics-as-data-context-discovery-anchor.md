# 指标作为数据上下文的发现锚点，不回到页面协议

数据侧的资产链路是指标 → 指标关联数据资产 → ADS/DWS/DWD/ODS → 表服务/GraphQL/API/DQE → 前端消费。指标在数据侧是最上层的业务语言，也是分析师提问时实际使用的词。问数要准，靠的是可枚举的业务语义而不是更强的模型。

ADR-0014 已经把治理对象从预定义指标改为可执行查询，并删除了指标目录与指标履约。本决策不恢复那个模型：它解决的是另一个问题——**Agent 如何发现“有哪些业务概念可问”**。规模决定了这个问题不能靠 Prompt 硬塞：规划中有 5 个以上业务域，每个域约 300 张主题表，全量语义面放不进上下文窗口。

## 决策

**指标以发现条目和口径锚点的身份进入数据上下文快照。** Schema 元数据新增指标条目，描述业务名、别名、口径说明、单位、是否为比率、可加性与时间聚合方式、可用维度，以及**所属业务域**。指标不进入看板页面协议：页面数据源仍然只声明 DQE 查询定义与结果字段契约，不引用指标 id。ADR-0014、ADR-0016 与 ADR-0017 的结论全部保持。

**业务域是路由标签，不是执行环境隔离。** 各域共用同一个数据仓库与同一个 DQE 执行环境，因此域只用于把检索面从全量收窄到一到两个域（ADR-0037），不产生第二套凭据、端点或执行适配器。指标条目携带域字段是为了可路由，而不是为了表达物理隔离。

**可加性与时间聚合是必填而不是可选。** 允许模型自由生成 formula（ADR-0032）之后，跨时间窗与跨维度的聚合方式不再由预定义指标兜住：把比率直接求和、对期末余额跨月累加都会产出看起来合理的错数。条目必须显式声明该指标可加、半可加还是不可加，以及跨时间应当求和、取均值还是取期末值；发现层给不出这个信息时，编排必须把该指标视为不可跨粒度聚合。

**发现层描述 DQE 语义面，不描述物理表。** 当前 DQE 的查询体使用中文业务名称：`output_metrics` 与 `output_dims` 是业务指标名与维度名，`filter.dims[].dim_value_list` 是业务取值。因此发现层需要提供的是可枚举的指标名、维度名、维度取值域、时间粒度能力与指标维度可组合性约束，而不是 ADS 物理表名与字段名。物理表结构属于表服务与 GraphQL/REST 执行路径，按 ADR-0034 在接入数据网关时以同样方式描述。

**别名是一等信息，且必须可增长。** 分析师会说“没考察的客户”而不是“无公司考察客户数”。指标与维度条目携带业务别名，`search_data_context` 按名称、说明与别名做混合检索：别名与名称走精确与关键词匹配，口径说明走向量语义匹配，两路结果合并后排序。别名初始由人工维护，之后从会话事件流里的失败分类与缺口条目（ADR-0036）产出候选，经人工背书后进入下一个快照版本；不允许问数过程直接写入别名。缺少别名的发现层会把准确率损失伪装成模型能力问题。

**指标不是建页或问数的强制前置。** 找不到对应指标条目时，允许在数据上下文允许的范围内直接形成查询；不恢复 `METRIC_GAP` 这类阻塞状态，也不需要先走指标建设流程。缺口的非阻塞出口与临时口径的治理由 ADR-0036 承担。这正是 ADR-0014 拒绝预定义指标的核心理由，本决策不削弱它。

**已验证查询是可增长的口径资产。** 已验证查询继续留在数据上下文快照中，承载“这个业务问题的正确算法”。它有两个来源：一是从既有页面的 `query` 数据源反向抽取，二是用户对问数结果的反馈。反馈只产生**候选**已验证查询，必须经人工背书才进入快照——会话事件流（ADR-0030）记录的是发生过什么，快照记录的是被认可为正确的口径，二者不可互相替代。

**数据上下文的运行期边界不变。** 统一运行时仍不加载数据上下文，也不按 Schema 元数据推导页面字段。指标口径变化通过新的快照版本表达，已发布页面不因指标说明变化而漂移。

## Consequences

- Schema 元数据 `formatVersion` 从 `1.0` 升到 `1.1`，新增指标条目、别名、域、可加性与时间聚合方式；`docs/schema-metadata.md` 与 JSON Schema 需同步。
- `search_data_context` 的返回类型除 Schema、对象、字段与已验证查询外新增指标，检索需覆盖别名并支持按域过滤；混合检索意味着快照构建期要产出向量索引，这是新的构建产物。
- 问数与建页的失败模式变为可枚举：指标名、维度名或取值不在清单内时可在执行前拒绝并纠正，不必等真实执行报错。
- 可加性缺失从“信息不全”升级为“阻断跨粒度聚合”，这会让早期问数在元数据未补齐的域上明显保守；这是有意的，错数比拒答更贵。
- 现有页面里可反向抽取的真实 DQE 查询体只有 4 个，`output_metrics` 中其余取值是页面字段 id 而非业务指标名。已验证查询无法靠反向抽取冷启动，必须人工构造黄金问题集（ADR-0037）。
- Monitor 未来所需的稳定口径由指标条目承载，不需要为此把指标塞回页面协议。
- 指标条目只描述业务语义，不包含执行端点、凭据或业务数据行；这与 Schema 元数据既有边界一致。
- 指标条目中的英文 `metric_code` 与 DQE 中文指标名是否为同一实体尚未确认，条目允许同时携带两者但不假设映射。

## Considered Options

- **恢复指标为一等资产并要求查询引用指标。** 会重新把建页阻塞在指标建设流程上，正是 ADR-0014 否决的模型，不采用。
- **只用物理表 introspect 结果做发现。** DQE 不接受物理字段名，且物理字段不携带口径与单位，模型拿到的信息无法直接构成合法查询，不采用。
- **不建发现层，靠 Prompt 和模型常识猜指标名。** 名称错误只能在真实执行时暴露，准确率不可控且无法自动纠正，不采用。
- **只做关键词与别名精确检索。** 实现最简，但描述性提问与别名表述不重合时直接零召回，不采用。
- **只做向量语义检索。** 对描述性提问召回好，但会把相近指标混淆成同一个，且无法保证生成的指标名严格落在清单内，不采用。
- **把指标条目直接写进页面文档以便追溯口径。** 页面协议会重新出现跨引用与默认值，违反 ADR-0018 的局部显式原则，不采用；口径追溯通过数据上下文版本表达。
