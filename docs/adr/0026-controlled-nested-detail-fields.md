# 结果字段契约支持受控的一层嵌套明细

> [ADR-0028](./0028-controlled-semantic-html-detail-fields.md) 后续新增了与本能力并存的 `semanticHtml/detail`。它用于 DQE 已经完成内容组合的受控富内容，不把本决策的对象数组序列化为 JSON 字符串，也不取代 `recordList/detail`。

DQE 真实查询已出现「一条客户结果内含多条云服务归因」的稳定输出形态。原有结果字段契约只允许标量，会迫使页面丢弃归因明细、把对象数组序列化为字符串，或让组件绕过查询字段映射直接解析 DQE 原始字段。三种做法都会破坏结果字段契约作为数据网关与纯渲染组件之间稳定接缝的作用。

## 决策

**新增嵌套明细字段，但不放开任意 JSON。** 该字段使用 `type: "recordList"` 和 `role: "detail"`，只表示一层对象数组；数组项属性只能是现有标量类型，不允许对象、数组或递归 `recordList`。每个结果行的单个嵌套明细字段最多 100 项。

**数组项契约在外层字段就地完整声明。** query 页面数据源为外层字段和每个项字段分别声明 `queryField`、稳定页面字段 id、类型、角色和可空性。不新增可跨页引用的字段集或隐式默认值，保持 ADR-0018 的局部显式原则。

**递归归一化留在既有纯计算 Module 内。** 页面文档内嵌初始行和数据网关的动态 DQE 响应继续共用 `normalizeQueryRows` Interface；它把外层与项字段一次性归一化为稳定页面字段 id，并以结果行、明细项和字段定位类型或映射错误。统一运行时与纯渲染组件不感知 DQE 原始名称。

**组件必须明示选择消费 `detail`。** 通用字段绑定、图表、表格和 AI 总结不自动展开嵌套明细。首个真实消费者是 `rankingDetailCard`：它通过 `props.details` 绑定外层 `detail` 字段，再显式选择项标题、数值和说明字段，以可展开明细渲染。

`[]` 表示已确认没有明细；`null` 是否合法沿用字段 `nullable` 语义。DQE 把复合输出放在 `output_metrics` 时，`detail` 不被强制伪装成 `measure`；它仍然必须映射到该 DQE 输出字段。

## Consequences

- 结果字段契约、数据快照和数据网关现在能保留受控的客户→归因明细结构，不需要把一个命名结果集拆成临时级联数据源，也不改变 ADR-0015 对级联输入语义的暂缓决策。
- 既有标量页面文档和组件无需修改；新能力是 Schema 4.0 内的向后兼容扩展。
- 嵌套明细的语义、上限、错误定位和映射逻辑集中在一个 Interface 后，而不会复制到每个组件。
- 如后续需要多层嵌套、跨客户联动或把嵌套明细发送给 AI 总结，必须分别扩展对应的显式 Interface，不从本决策推导出隐式支持。

## Considered Options

- **把对象数组序列化为字符串。** 类型契约会通过，但每个消费者都要自行解析、验证和映射，删除此浅 Module 后复杂度不会消失，不采用。
- **字段值放开为任意 JSON。** 会让页面 Schema 无法限定深度、大小与消费方式，与封闭受控的页面 DSL 相冲突，不采用。
- **把归因明细拆成第二个页面数据源并由前端关联。** 会引入客户集合传递、失败传播、缓存键和取消等 ADR-0015 已暂缓的级联语义，不采用。
