# 创作期查询必须经清单校验与真实执行验真

页面搭建 Agent 与问数共同面对同一个问题：自然语言意图要变成一个能真的取到数的 DQE 查询定义。当前 `packages/mcp` 只提供数据上下文检索、页面校验、保存、预览与发布，没有任何执行验真工具。模型只能依据 Prompt 与数据上下文直接写出查询体并写进页面文档，第一次发现它取不到数的时刻是用户打开页面的时刻。

## 决策

**任何进入页面文档的 `query` 数据源，其查询定义必须先通过清单校验与真实执行。** 创作期能力顺序固定为：清单校验 → 真实执行 → 物化结果字段契约。未经这条路径形成的查询定义不得进入页面保存边界，也不得进入 ADR-0030 的临时页面态。

**闭集分层：名称层封闭，表达式层开放。** DQE 查询体的指标名、维度名、维度取值与时间粒度必须取自 ADR-0031 的数据上下文闭集，清单校验在执行之前拒绝不在闭集内的名称与取值并给出候选；模型不得发明字段名、不得书写物理表名或列名。但 `output_metrics` 支持内嵌 `formula` 表达式，因此指标层实际不是闭集：**允许模型自由生成 formula**，以换取环比、占比、同比这类组合口径的灵活性。这是一处有意保留的开放面，代价由留痕与沉淀门槛承担，而不是靠事前禁止。

**自由生成的 formula 必须留痕并被标注。** 每个 formula 记录问题原文、生成的表达式、引用到的指标名，以及所引用指标的可加性与时间聚合声明（ADR-0031）；引用了不可加或半可加指标而表达式跨时间窗聚合时，清单校验直接拒绝。formula 产出的口径按 ADR-0036 标记为临时口径，在结果上可见，沉淀为长期应用时需过门槛。

**结果字段契约由执行输出与数据上下文语义共同物化。** 输出字段名来自真实执行结果，字段类型、角色、标签、单位与 `defaultFormat` 来自数据上下文与指标条目声明。这不等于从返回样例推断契约：样例值不作为类型或语义的判定依据，`origin.md` 中“不从查询返回样例推断字段契约”的边界继续成立。formula 字段没有对应指标条目，其单位与格式必须由生成时显式声明，不得从数值猜测。ADR-0014 关于“结果字段契约由静态分析与真实执行验真形成”的结论在此落地。

**呈现选择受组件能力目录硬约束。** 从验真结果到页面文档的组件与格式选择，以字段角色、维度基数、时间粒度与组件能力目录作为硬闸：不满足能力约束的组合一律不可选。在硬闸允许的范围内由分析意图排序，具体的意图判定、回显与用户钉住规则见 ADR-0037。格式归属仍遵循 ADR-0013：`format` 属于组件字段绑定，数据源只提供 `defaultFormat` 建议。

**失败按四段分类。** 发现、生成、执行、呈现各自拥有结构化错误码，与既有的 `QUERY_MAPPING_ERROR`、`DQE_PROTOCOL_ERROR`、`DQE_EXECUTION_ERROR` 等运行期错误类型并列而不混用：后者描述已发布页面的运行失败，前者描述创作期未能形成可用查询的原因。四段分类是后续提升准确率的唯一抓手，因此它是首版能力而不是可选增强。

**验真只存在于创作期。** 统一运行时不执行清单校验、不物化契约、不选择组件；它仍然只确定性消费已经确定的页面文档。ADR-0030 的作用域澄清与此互为前提。

**验真结果可被复用为静态数据。** 同一次执行的归一化结果既可作为 ADR-0020 的内嵌初始行，也可作为 ADR-0030 中 Report 冻结的初始行，不需要为冻结再执行一次查询。

## Consequences

- `packages/mcp` 新增创作期执行验真与契约物化工具；数据网关 Interface 不因此扩张，创作期执行仍走同一个查询执行端口与同一份结果归一化能力。
- 问数与页面搭建共用同一套验真能力，两条路径不会各自演化出一套查询正确性标准。
- formula 开放面意味着口径正确性无法在创作期完全判定：清单校验只能拦住名称非法与可加性冲突，算法本身是否符合业务定义只能靠回显（ADR-0037）与沉淀门槛（ADR-0036）拦。这是已知残余风险，不是遗漏。
- formula 使用频次按表达式形状聚合统计，高频形状是下一批命名指标或已验证查询的输入。
- 开发环境使用 DQE 仿真完成验真闭环，验收场景不得以 `inline` 页面替代真实查询执行。
- 页面保存前的失败大多可在创作期内自动修复：名称不存在与取值非法都有明确候选来源。
- 反馈为“这个结果不对”时，被人工背书的查询按 ADR-0031 进入候选已验证查询，形成缓慢但可控的自我改进。
- 创作期执行会产生真实数据查询成本，需要按身份施加次数与资源限制；限制策略沿用数据上下文声明的查询资源约束。

## Considered Options

- **只做 JSON Schema 校验，不执行。** 结构合法但名称不存在的查询会通过校验并进入页面，错误只能在用户面前暴露，不采用。
- **禁止模型生成 formula，只允许一组命名算子。** 治理最强、口径最可控，但环比、占比这类最常见的追问会直接落到指标缺口出口上，早期可用性太低，不采用；命名算子仍可作为后续对高频 formula 形状的收敛方向。
- **用返回样例行推断字段类型与角色。** 违反 `origin.md` 的既有边界，且空结果或全空列时无法判定，不采用。
- **在统一运行时首次渲染时验真并自动修复。** 已发布页面将不再确定性可复现，且把创作期能力带进渲染路径，不采用。
- **让模型直接书写物理表名与 SQL。** 当前 DQE 语义面本就不接受物理字段，且会把权限与口径判断推给模型，不采用。
- **把呈现选择完全交给模型。** 组件能力与格式约束已经在能力目录中可枚举，交给模型会产生不可复现的视觉结果并绕过能力校验，不采用。
