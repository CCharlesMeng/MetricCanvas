# 受控计算以封闭具名算子分两批进入页面数据源

[ADR-0033](./0033-suspend-dataset-runtime.md) 挂起服务端计算数据集时，把派生计算交给了 DQE 的 `formula`。[ADR-0045](./0045-graphql-query-branch-with-structured-predicates.md) 让 IOC 作战地图整体走 GraphQL 后，这条出口消失了：GraphQL 服务返回的是既有 ADS 表的列，没有 `formula`，也没有可在查询里表达派生计算的位置。

来源实现把这些计算全部放在前端 `fitFunction` 与 `onGlobalVarChanged` 里，共 12 处，可分成三类：

| 类别 | 实例 | 作用域 |
|---|---|---|
| 行内派生 | 立项率、赢单率、机会点数环比差值、总预签金额环比差值 | 单行内的字段运算 |
| 结果集重排 | 销售预测表按业务类型分组小计 + 全局合计；客户活动按 `activity_type` 行转列 | 单数据源内的行集变形 |
| 跨数据源聚合 | 管道支撑率：按 `地区部_代表处` 组合键把三个数据源分别聚合后代入公式 | 三个数据源对齐 |

这些不是可以省略的装饰。管道支撑率是概览页的核心指标，既进 KPI 卡也进概览表也进地图着色；小计与合计行是详情页销售预测表的主要信息。

难处在于 ADR-0033 的挂起理由至今成立，且**在 GraphQL 路径上比当年更成立**。它的恢复条件一是「指标条目的可加性与时间聚合方式在目标域真实可用」；[ADR-0044](./0044-first-class-metric-entries.md) 让可加性变得可表达但没让它变得可用，而 GraphQL 路径上连指标条目都不存在——[ADR-0031](./0031-metrics-as-data-context-discovery-anchor.md) 的发现层描述的是 DQE 中文语义面，GraphQL 侧的发现描述按 ADR-0045 本批不交付。直接解冻 ADR-0033 的完整设计，等于在最不具备前提的路径上启用它。

## 决策

**在页面数据源上引入受控计算阶段，但不恢复 ADR-0033 的计算数据集聚合根。** 计算是页面数据源的一个可选阶段：输入是该数据源查询执行并归一化后的行集，输出仍是同一个数据源的数据快照。它没有独立 id、没有独立修订、不参与发布治理、不出现在页面目录。ADR-0033 拒绝的「领域层出现第二个聚合根」因此没有发生——聚合根仍然只有看板页面。

**只提供封闭的具名算子，不提供通用 `arithmetic`、公式字段或任何表达式。** 这条直接继承 ADR-0033 明文保留以备恢复的结论。算子的参数是字段引用与封闭枚举，不是可求值的字符串。

**分两批交付，第二批的形状在第一批经真实页面验证后再裁决。**

第一批只覆盖**单数据源内**的计算，对应上表前两类：

- `ratio`——分子分母两个字段引用，外加分母为零时的语义（取空还是取零）。这个语义必须显式声明：来源实现里立项率的分母为零取 `null`、管道支撑率的分母为零取 `0`，两种都真实存在，默认值会静默改数。
- `delta`——两个字段引用的差。
- `groupSubtotal`——按一个字段分组，对声明的度量字段各生成一行小计。
- `grandTotal`——对全部明细行生成一行合计。
- `pivot`——把「一行一个类别」的结果集按类别字段转成「一行多列」，列名与类别取值的对应关系就地显式声明。客户关系规范性那处「专题交流优先、缺失时取技术交流」的择一逻辑，以每个目标列声明一个有序的类别取值列表表达，取第一个命中的，不引入条件。

第二批只有 `joinAggregate`——按组合键把另一个页面数据源聚合后并入当前行集。**它本轮不定形状。** 管道支撑率因此在第二批落地前无法实现，这是有意接受的排期代价：跨数据源对齐正是 ADR-0033 与 [ADR-0015](./0015-defer-cascading-data-source-input-semantics.md) 共同挂起的那批语义（空集传播、失败传播、缓存键、取消语义），用第一批的实战经验去定它，比现在凭想象定要可靠。

**计算产出的字段必须就地声明在该数据源的结果字段契约里。** 与查询字段一样声明类型、角色、标签、单位、可空性；区别只是不声明 `queryField`（它不来自外部响应）。这守住 [ADR-0018](./0018-keep-page-metadata-locally-explicit.md)：读页面文档的人在数据源当前位置就能看到全部可用字段，不需要在脑子里跑一遍算子。

**折叠类算子要求被折叠字段显式声明可折叠。** ADR-0033 的恢复条件一无法满足，本决策用一条可校验的替代约束顶上：`groupSubtotal`、`grandTotal` 与将来的 `joinAggregate` 只能作用于在结果字段契约上显式声明了可折叠的度量字段，声明缺失即校验失败。这把「从指标条目的可加性推导」换成「在页面上显式声明并可被校验器判定」。它比 ADR-0044 的可加性弱——页面上的声明可能写错，而指标条目的声明有数据侧负责——但它至少让错误可见、可审计、可在评审时被质疑，而不是像今天的 `fitFunction` 那样对任何工具都不透明。

**格式化不是计算。** 亿/万自适应、百分比、千分位继续走 [ADR-0013](./0013-format-belongs-to-component-field-binding.md) 的组件字段绑定与 [ADR-0042](./0042-money-fields-and-semantic-embedded-values.md) 的货币字段，不进计算层。来源实现里那批 `_label` 字段是前端计算的产物，在本模型里它们不该存在——同一个数值字段在指标卡与表格里可以有不同格式，这正是 ADR-0013 的理由。

**ADR-0003 的边界被修订，不被推翻。** [ADR-0003](./0003-strict-declarative-spec.md) 禁止的是表达式与脚本：可被任意求值、语法面开放、无法被 JSON Schema 完整校验的东西。封闭具名算子是声明式数据，与 [ADR-0035](./0035-structured-relative-time-expressions.md) 的结构化相对时间表达同类——它也曾是「表达式字符串」的诱惑，最后落成了声明。ADR-0003 的正文需要同步修订措辞，把「复杂计算不进入页面层」改为「计算只以封闭算子表达，开放语法面不进入页面层」。

**本决策不做的事。** 不提供通用 `arithmetic`；不提供用户自定义算子；不提供条件算子或分支；不提供跨页面计算；不让计算改变筛选状态或触发查询。

## Consequences

- ADR-0003 需要一次措辞修订，ADR-0033 变为**部分恢复**：它「不提供通用 arithmetic，只提供具名算子」的结论被采纳，它的计算数据集聚合根与 Transform/Compute 分层没有被恢复。ADR-0033 的三条恢复条件本身仍然未满足，本决策不宣称它们已满足，也不解除对服务端计算数据集的挂起。
- 校验器需要新增一批判定：算子输入字段存在且类型相容、产出字段已在结果字段契约中声明、折叠类算子的可折叠声明齐全、算子之间无循环引用。
- AI 的生成面因此扩大。`packages/mcp` 的创作期校验与 `.agents/skills/repair-page-metadata` 的修复路径需要覆盖算子层，否则「校验通过但数字不对」的失败模式会增加。
- 与 [ADR-0032](./0032-authoring-time-query-verification.md) 的关系：计算发生在真实执行之后，因此结果字段契约物化时必须包含算子产出字段，验真的对象是「查询 + 计算」的整体输出，不是查询的裸输出。
- 概览页的管道支撑率阻塞于第二批。落地计划应把它排在最后，且在第二批裁决前不承诺该指标的交付时间。
- 分母为零语义必须逐处显式声明，这会让页面文档比来源实现啰嗦。这是刻意的：来源实现里两种语义并存且只能从代码读出来，正是最容易产生错数又最难发现的一类差异。
- `groupSubtotal.labelSuffix` 是可选的字面后缀（例如「合计」），不是模板、不含占位符。
- query 页面数据源的结果字段契约因此放宽为联合：带 `queryField` 的查询字段，或不带 `queryField` 的算子产出字段。无 `queryField` 的字段必须出现在计算阶段产出里，算子产出也不得再声明 `queryField`。存量只含查询字段的 5.0 页面形状不变。

## Considered Options

- **全部下推数据侧，页面只做展示。** 最守现有 ADR，也是本仓一贯的方向。但取数协议已定为既有 GraphQL 服务上的既有 ADS 表，改表要走完整的数据开发链路，周期与成本不在本项目可控范围内。这是一次业务侧裁决，不是技术偏好。不采用。
- **恢复 ADR-0033 的完整计算数据集。** 表达力最强、语义最完整。但它引入第二个聚合根（实质修订 [ADR-0006](./0006-metadomain-layering-and-naming.md)/[ADR-0007](./0007-demote-spec-to-document-form.md)），且三条恢复条件一条未满足。不采用。
- **引入通用公式字段或表达式求值。** 一步到位覆盖全部 12 处计算，实现也最简单。但 ADR-0003 的前提全失：语法面开放，AI 写错时校验器只能判语法不能判语义，自动修复无从谈起。这恰好是 ADR-0001 选择自研封闭 DSL 而非通用 agent→UI 协议的全部理由。不采用。
- **只在组件层做，比如让表格自己算合计。** 改动面最小。但合计只是 12 处中的 2 处；且同一个口径（例如立项率）在指标卡、表格与地图着色里都要用，放在组件层意味着同一计算写三遍，各自漂移。不采用。
- **第一批就把 `joinAggregate` 做进去。** 概览页可以早三个月上线。但它要求现在就回答空集与失败传播、输入集合上限、循环依赖校验、缓存键与取消语义这五个 ADR-0015 明确列为「恢复设计前需依次确定」的问题，而我们此刻既没有实践经验也没有真实失败案例。不采用。
