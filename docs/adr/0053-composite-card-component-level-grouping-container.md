# 组件级分组容器「组合卡」,与分区容器按层次分工

IOC 概览页的设计稿顶部是三张卡并排:580×280「机会点概况」、580×280「项目分层分级管理」、440×280「复盘总结」,三张都是 `bg-[#ffffff] rounded-[16px]` 无边框。每张卡内部是「标题 + 一组数字 + 一个环形图 + 一份按类别列出的三列明细」——那份明细看着像图例,其实是带列头的三列小表。第三张卡下半部还有四个奖惩计数,与上半部之间隔着一条 `1px dashed #dcdbdb`。清单页顶部同样是三张卡(440/580/580,都没有标题),其中一张内部是 2×2 的虚线分格。**这些不是「一个卡片组件」,而是一组组件被一个卡片外壳框在一起。**

当前页面协议表达不了这件事:

- `metricCardComponentZ.props` 是 `.strict()`,没有任何嵌套子组件的入口;
- 唯一能嵌套的 `tabContainer` 只接 `table`(`tabItemZ.component` 就是 `tableComponentZ`);
- `section.container: "card"` 的语义确实是「白色小节卡片 + 左对齐小标题 + 内部按 12 列栅格放多个组件」([ADR-0038](./0038-section-container-and-row-alignment-invariant.md)),但内容分区只能纵向堆叠,三张 580 宽的卡横向并排用三个分区表达不了。

缺口因此是一句很干净的话:**缺一个能进内容分区的 12 列栅格横向并排、内部能放多个组件的分组容器。** 概览页此前只能把三张复合卡拆成六个同级卡位(各 `span: 2`)去近似,那是一次登记在案的还原豁免,不是协议能表达的结构。

## 决策

**新增组件类型 `compositeCard`(组合卡):一个组件级的分组容器。** 它是 `sections[].components` 判别联合的一个新分支,因此天然进入 12 列自动流、天然可以与其他组件横向并排,卡宽就是它自己的 `layout.span`。取名「组合卡」:「卡」说明它有一张卡的外观,「组合」说明它装的是若干组件而不是一组数字。不叫「分区卡片」——那会与分区容器撞车;不叫「组件分组」——那听不出有卡壳。

**它与 `section.container: "card"` 的分工是层次,不是功能。** 两者都是「白卡 + 标题 + 内部多组件」,含糊了作者与 AI 都会选错,因此判据只有一条,不看内容也不看观感:**要装的这组组件本身是不是一个分区。** `container: "card"` 是**分区级**声明——一个内容分区一张卡,卡宽由分区决定,卡与卡之间只能纵向堆叠;`compositeCard` 是**组件级**声明——一张卡就是一个组件,进 12 列栅格,卡宽由 `layout.span` 决定,同一分区里可以并排若干张。需要三张 580 宽的卡横向并排,只有 `compositeCard`;需要一整段内容自成一节、下一节接着往下排,就是 `container: "card"`。两者可以嵌套(一个 `card` 分区里并排三张组合卡),但不得互相替代:`container` 仍是分区外观的唯一真源(ADR-0038),组合卡不改变、不推断,也不参与分区外观。

**组合卡自己不承载数据。** 它不声明 `data`、不声明字段绑定、不声明 `actions`,只有可选标题、一位分隔声明和子组件数组。这样「用组合卡还是用 `metricCard`」的判据是结构性的——**有没有子组件**,一眼可判;而「哪个功能更多」不是判据。一个既能显示数据又能嵌套子组件的容器会与 `metricCard` 在语义上重叠,重叠处只能靠观感和惯例选择,那正是本决策要消灭的含糊。`reportHeader`、`text`、`aiSummary`、`tabContainer` 已有「不得声明 `data`」的先例,校验规则不新增形状。交互仍归子组件:卡里哪个数字可点,由那个数字所属的组件自己的 `actions` 声明。

**子组件是白名单,不是「任意叶子组件」。** 首批准入五种:`metricCard`、`pieChart`、`gauge`、`keyValuePanel`、`categoryBreakdown`(见下一条)——两个设计源里的卡内构成用这五种就能表达,不多给一种。`text` 与 `fieldText` 结构上没有障碍,但设计源里没有它们的实例:卡内那句看起来像说明文案的东西大概率归 `categoryBreakdown` 的列头与类别行,`text` 因此更没有首批准入的实证,真实需要时按闭集新增成员放开。明确不准入的与理由:`table` 自带卡壳与分页,卡内多表切换归 `tabContainer`;`mapChart` 的几何自适应与安全区通道以分区为单位([ADR-0052](./0052-dashboard-layout-form-backdrop-and-safe-area.md));`barChart`/`lineChart` 需要自己的宽高基线,等真实需求;`rankingCard`/`rankingDetailCard` 自带卡面,且行对齐不变量按「同一父 Grid 的同一视觉行」分组,放进容器会让分组语义跨层漂移;`reportHeader` 是页面级;`aiSummary` 是生成型垂直组件([ADR-0019](./0019-internalize-ai-summary-generation.md))。选白名单而不是「任意叶子」的理由是方向性的:白名单加成员是闭集新增成员,属纯增量([ADR-0051](./0051-additive-minor-versions-for-page-schema.md));而从「任意叶子」收回白名单是收窄闭集,属破坏性变更。代价是每种子组件准入都要有一次「在卡壳里渲染正确」的实证,这正是我们希望付的代价。

**白名单里的第五种是同批新增的一个叶子组件:分类明细(`categoryBreakdown`)。** 环形图旁边那块看起来像图例的东西,实际是三列小表——类别 + 机会点数 + 预签金额,带列头——而且是**复现形状**:概览页出现两次(卓越/战略/核心;公司特级到代表处级四档)。它不用 `table`(分页、排序、表头筛选、固定列、列组、选择写回一条都用不上,太重);不用 `keyValuePanel`(那是键值对,结构上表达不了三列带列头);也不给 `pieChart` 加图例属性(那是把一份独立的数据展示塞进图表 props,以后图例形状变一次就得动图表)。按仓里先例,**新增叶子组件类型不单独写 ADR**——`gauge`、Tab 容器、key-value 面板与字段绑定长文本都记为「组件目录扩展,无独立 ADR」(见 [`docs/plan/ioc-operation-map.md`](../plan/ioc-operation-map.md) §2.2)——因此它随 5.2 批次登记在这份 ADR 的白名单里,不另立一份。

**分类明细与并排饼图之间有一条硬约束:颜色按类别取值决定,不按行序决定。** 分类明细的色点必须与环形图扇区同色同序。两边各自按调色板顺序取色只是「看起来对上了」:数据顺序一变就错位,而且错位是静默的——图和表各自都自洽,只有对着看才发现颜色串了。因此两个组件绑同一个类别字段,颜色由类别取值查得,不由行序或扇区序号查得。页面文档只声明两处的类别字段,颜色不进页面文档;这条约束在实现时必须有测试钉住(同一份数据换一次行序,两边配色不变)。

**禁止递归:组合卡内不得再出现组合卡或 `tabContainer`。** 页面树因此从「分区 → 组件」两层变为「分区 → 组合卡 → 组件」最多三层,深度有界。理由有三条:两个设计源都只有一层,没有第二层的真实需求;无界递归会让 `span` 与自动流的参照系在每一层重新定义,并让组件 id 判重、能力探测与行对齐分组都必须走任意深度;而「先禁后放开」是纯增量,「先放开再禁」是破坏性变更。

**卡内布局复用同一条 12 列自动流,不引入第二套布局词汇。** 子组件照常声明 `layout.span`,含义从「分区内容宽度的十二分之几」变为「卡内容宽度的十二分之几」,组件数组顺序仍决定自动流顺序。设计稿的「数字行 + 分隔线 + 环形图与分类明细并排」因此写成一个 `span: 12` 加两个 `span: 6`,清单页的 2×2 分格写成四个 `span: 6`。不新增 `rows`、`stack`、`direction`、`gap`、`align` 这类布局轴:12 列栅格是运行时不变量、列数与几何不进页面文档(ADR-0038),本决策只增加这条不变量的第二个应用点,不把它变成递归布局语言。`layout.layer: "backdrop"` 在卡内禁止(与 Tab 内同理:没有分区可铺满);`connectPrevious` 在卡内保持同一语义,不为卡内单独禁用。

**标题可选;分隔线是容器上的一位信息,位置由结构派生。** 标题沿用组件标题约定(`props.title`),可选是因为清单页那三张卡确实没有标题。分隔线不写索引、不写坐标、不写线型:容器上一位布尔声明「相邻子组件之间分隔」,线画在 12 列自动流已经形成的单元格边界上——行与行之间是横线,同一行相邻子组件之间是竖线。这一位信息同时覆盖概览页「上下两段一条横线」与清单页「2×2 虚线分格」两个真实形状,而 `1px dashed #dcdbdb` 是主题实现,不进页面文档([ADR-0003](./0003-strict-declarative-spec.md))。**明确否掉**两个替代:新增一个 `divider` 装饰组件充当子组件(它会变成一条到处可以画线的自由样式面),以及在子组件 `layout` 上写 `dividerBefore`(把位置索引写进页面文档,插入一个子组件就得改另一个组件的声明)。

**至少一个子组件;子组件 id 与顶层组件一起判重。** 只有一个子组件的组合卡合法——卡壳本身就是它的价值,这与「分区不能只有 `backdrop`」不同,那一条禁止的是叠放在没有覆盖物时失去意义。子组件 id 参与页面内组件 id 判重,与 `tabContainer` 一致。

**12 列栅格表达不出设计稿的 580/580/440,概览页那三张卡取 `span` 4/4/3。** 卡片行 1632 宽、间距 16px,一列约 121px,因此 `span: 4` ≈ 533、`span: 5` ≈ 671,580 落在四列与五列之间——精确宽度在 12 列里没有落点。取 4/4/3 是保比例而不是保像素:设计稿的 580:580:440 是 1.32:1.32:1,列数比 4:4:3 是 1.33:1.33:1,差约 1%(算上列间距后实际渲染宽度的偏差略大);代价是右侧空出一列。**本 ADR 只记这个事实和取比例的理由。** 具体判据、以及空出那一列怎么处置,属于还原口径,归 QA 基线,不进本 ADR 也不进页面文档——几何不进页面文档是 ADR-0038 与 ADR-0052 的既有结论,这里没有例外。

**卡高不进页面文档,分段首批不跨卡对齐。** 设计稿的 280px 是实现基线;同一视觉行的组合卡由 12 列栅格天然等高,但卡**内**的分段高度各卡自算——首批不为组合卡发布行对齐能力,因此三张卡的分隔线不保证落在同一高度。这是有意的:跨卡对齐会让并排的卡互相牵制,而这种耦合在没有设计过的场景里比参差更难收回。真实需要时按行对齐不变量的既有机制发布能力,页面文档不变。

**按 ADR-0051,本决策是纯增量,为 5.2 登记两条能力。** `compositeCard` 与 `categoryBreakdown` 都是判别联合新增分支,其余是新增可选字段,存量页面不迁移;两者各自作为一条能力进能力表,声明 `5.1` 的文档使用它们即触发能力下限错误。5.2 批次的其余变更是字段级增量与一处 ADR-0051 例外条款下的收紧,与本决策不交叉。

## Consequences

- 纯渲染组件第一次需要按类型分派地渲染一棵子组件树。`tabContainer` 已经开了嵌套的头,但它只认一种子类型。渲染入口的归属(在 `widgets` 内递归,还是由 `runtime-ui` 下发单元格)是实现决策,约束不变:容器不发起查询、不访问页面全局状态([ADR-0025](./0025-converge-runtime-presentation-packages.md))。
- 校验器、组件遍历与能力探测都要走进容器的子组件数组。`walkDocumentComponents` 已经为 Tab 子组件走过一层嵌套,这里是同类的第二处。
- 组件目录里从此有两个「装东西」的类型:`tabContainer`(卡内切换,只接表)与 `compositeCard`(卡内分组,接白名单)。选择目录必须让这两行的选择条件互斥且可读,否则含糊只是从「分区还是组件」搬到了「切换还是分组」。同批多出的 `categoryBreakdown` 也要在目录里与 `table`、`keyValuePanel` 划清:它是「少数几行 × 少数几列、无分页无排序」的紧凑明细,不写清楚会被当成「小一号的表格」滥用。
- 分类明细与饼图的取色契约是仓里第二条跨组件呈现契约(第一条是行对齐)。它同样不进页面文档,因此测试是它唯一的保障;没有那条测试,颜色错位会以「看起来没问题」的形式长期存在。
- 概览页可以撤销「三张复合卡拆成六个同级卡位」的权宜表达,奖惩四档也可以回到「复盘总结」卡内。两件事都要等本决策实现之后再做。**协议层已随 5.2 批次交付**(`packages/page` 与 `PAGE-METADATA.md`):两个组件类型、白名单、禁递归、卡内 12 列与分隔线一位布尔都已可校验,同色同序由「开启色点即要求同页有饼图绑同一个类别字段」钉住。**Svelte widget 与运行时渲染尚未实现**,因此存量页面暂时还不能改写;改写与 widget 属下一轮。
- 白名单会持续带来「为什么这个组件不能放进去」的追问。每次放开都要补一次实证,不接受「看起来能用」。
- 卡内嵌套让「同一视觉行」在行对齐不变量里出现第二种父级(分区 Grid 与卡内 Grid)。首批不在组合卡内发布对齐能力,代价是并排三张卡的卡内分段与分隔线可能参差;这是接受的,理由见决策里「卡高不进页面文档,分段首批不跨卡对齐」那一条。

## Considered Options

- **给 `metricCard` 开嵌套口子。** 最省事:三张卡各是一个 `metricCard`,子组件塞进 `props`。否决——`metricCard` 已经承载 `summary`/`activityProgress`/`compactSummary`/`dualSummary` 四种形态,外加 `progress`、`secondaryRows`、`panelLayout`,是一个排布已经很重的**叶子**组件。再加嵌套会让同一个类型既是叶子又是容器:校验器要写条件规则(有子组件时 `rows` 还必填吗),widget 要处理子组件渲染,存量页面里 23 处 `metricCard` 的每一处都多出一条「可能有子组件」的代码路径。接口变宽、语义变浅,换来的只是省掉一个类型名。
- **用 `section.container: "card"` 表达。** 不成立:内容分区只能纵向堆叠。若为此给分区补「多个分区横向并排」的能力,那是在分区层重造一遍 12 列栅格,并让分区同时承担两种排布语义。
- **给内容分区加子分区层级或 `rows`/`stack` 递归布局。** ADR-0038 以「当前没有需要独立 DOM 所有权的场景」否决过这个方向,本决策**推翻的只是这条前提**:场景出现了——一张带自己卡壳、自己标题、自己分隔线的白卡确实需要独立 DOM 所有权。前提失效不等于结论全废,所以放开的是一层非递归的组件级容器,而不是 `rows`/`stack` 这种递归布局语言。
- **在容器上开放 padding、gap、surface、分隔线线型等样式轴。** 表达力最强,但它就是自由样式 DSL 的另一种拼法,ADR-0003 与 ADR-0038 已经两次拒绝。
- **不加类型,继续用六个同级卡位近似。** 它现在就在跑。代价是卡壳、卡标题与卡内分隔线全部无处安放,与设计稿的差距不可收敛;还原目标从「近似」变为「尽可能还原设计稿」之后,这个方案不再成立。
- **环形图旁边那块用 `table`、`keyValuePanel` 或 `pieChart` 的图例属性表达。** 三条都否掉了:`table` 的分页、排序、表头筛选、固定列、列组与选择写回一条都用不上,拿它装三行三列是用最重的组件做最轻的事;`keyValuePanel` 是键值对,表达不了三列带列头;给 `pieChart` 加图例属性会把一份独立的数据展示塞进图表 props,图例形状一变就得动图表。因此新增 `categoryBreakdown`,并按仓里先例不为它单写 ADR。
- **容器也能显示数据**(既有自己的字段绑定,又能放子组件)。少一个组件类型、页面写起来更短。但它与 `metricCard` 的边界会立刻变成一场关于「哪个功能更多」的争论,而纯容器把判据降为一条结构规则。
