# 查询输入过滤与分页排序级联：功能和架构影响

日期：2026-10-14。范围是本次6.19行过滤与6.20分页窗口输入实践；按当前主工作区实现核对。本文不把已有依赖调度、排序编码或并行进行的共享执行包迁移计作本次新建架构。

## 功能行为的变化

| 方面 | 原有约束或行为 | 本次结果及影响 |
|---|---|---|
| 上游结果复用 | 绑定从上游全部原始行提取维度集合 | 绑定可独立where筛行，再提取集合；上游行不被裁剪，多个下游可以使用不同条件。 |
| 查询范围 | 结果绑定只允许完整结果或无offset的固定有限选择 | 显式query分页窗口也可作为输入。下游结果反映当前窗口；它不代表全部项目。 |
| 排序 | 被结果绑定引用的查询源拒绝运行时查询排序覆盖 | 查询分页源开放通用列排序、多列优先级与方向变化；服务端先排序再取窗口，排序可能改变下游业务条件。完整结果与固定TopN仍保留保护。 |
| 分页 | 页码和大小控制上游浏览窗口 | 翻页及页大小变化同时驱动依赖更新；排序重置上游页码，受影响下游分页也回到第一页。页码不作为下游绑定的业务输入。 |
| 展示排序 | 本地表格视图不参与原始结果绑定 | 这条边界保留：本例评估表mode=none只对已有结果做展示排序，项目表mode=query才查询联动。不能把sortable=true等同于所有数据源自动联动。 |
| 完整性 | complete源在有totalCount时要求原始行数一致 | 查询窗口允许totalCount大于rows.length；按本轮实际limit核验行数，不能把声明的初始10条固定用于后续20条窗口。 |
| 空集合与缓存 | 空集合跳过请求，生效查询可缓存 | where后为空同样跳过请求；排序仅改变次序而选中字段集合相同时，可复用下游缓存，不承诺每次交互所有查询都重新访问服务端。 |
| 导出 | 普通分页表取完整结果；固定有限选择保留范围 | 使用窗口输入的级联链保留捕获时的当前页、大小和排序，重新取窗口并解析下游。该链导出不扩大为全业务数据；无级联普通分页表继续完整导出。 |

完整配置解读见[查询绑定 metadata](../../page-metadata/queries-and-bindings.md#配置解读首轮查询任意列排序与分页级联)，本地验证见[分页场景证据](paged-scenario.md)。

## 对架构约束的实际修订

### 查询结果的范围成为输入语义

原ADR-0099禁止查询分页窗口进入结果绑定，以防局部结果被误当作完整业务集合。ADR-0107只在明确query分页声明下放开窗口输入；分页源不能声称complete，也不能承担grandTotal/groupSubtotal/timeFill全量统计。

这使页面作者必须区分完整业务结果、固定TopN与可交互分页窗口。分页是查询状态，也是绑定输入范围的一部分。totalCount管理页数，raw rows提供本轮输入，maxValues约束最终去重键集合，三者各有用途。

代码接缝：packages/page/src/validate-query-results.ts与version.ts；Python query_results.py和page_validation.py同步校验；6.19引入where，6.20引入分页引用组合，旧版本明确拒绝新能力。

### 执行集合响应交互，依赖关系仍显式声明

运行时从resultBindings.source求受影响的查询闭包，取消旧请求、使旧结果失效，待本轮输入就绪后恢复查询。分支可并行，汇合等待全部输入，多层传递继续使用已有依赖图。sections顺序和业务列名称不作为执行规则。

本次没有引入可动态猜测边的图：页面声明谁消费谁；排序、页码和返回值决定本轮谁需要执行及何时就绪。查询和计算阶段继续分开，循环仍被拒绝。也没有增加组件之间手动调用的动作协议或通用工作流引擎。

代码接缝：packages/engine/runtime/src/orchestrator.ts的setQuerySort/setQueryPage/setQueryPageSize/refetch/publish；复用既有请求代次、AbortController与有效查询缓存。

### 输入解析需要实际窗口上下文

解析器不能只读模板中的order.limit，因为用户可把10条改成20条。resolveQueryResultInputs增加可选内部windowLimits参数，由运行时、共享单次执行和导出供给各自有效窗口大小；它不进入页面JSON、不复制到下游维度条件。

主工作区解析器位于packages/data-execution/src/query-result-inputs.ts，engine使用重导出。共享data-execution包来自并行进行的执行统一工作；本次是接入同一规则，没有另建第二套执行包。独立交付工作区最初沿原engine模块实现；交付前已对齐远端main，将同一规则接入共享data-execution模块，并重跑受影响检查。

### 交互、单次执行与导出要保持语义一致

交互使用当前页；单次执行从第一页开始；导出使用捕获时的页。三个入口共享相同的过滤、字段提取、去重、空集合与上限逻辑，但各自明确何时捕获查询状态。captureQueries与prepareExportSnapshots必须保留级联窗口，避免出现屏幕用第3页、导出却使用第1页或全量的不同业务输入。

### 创作与分发必须同步可表达能力

没有增加inputScope或分页绑定参数。6.19增加受控where结构，6.20通过现有分页声明和结果绑定的组合给出窗口语义。结构Schema不足以单独证明此组合合法，还需要能力门禁与文档内语义校验。

本次补齐Python对Tab内部查询分页表的识别，保留共享合法/非法向量，不豁免失败。协议参考、完整样例、独立Skill校验器及Bundle锁须从同一产品真源生成。主工作区存在其他未交付改动，本批生成完整产物保存在独立工作区，未覆盖并行任务产物。

## 执行成本与使用时需要明确的范围

按请求调度逻辑推断，排序或翻页可能增加上游与多个下游请求；依赖越深，完整结果就绪需要经过的请求阶段越多。现有批量执行、缓存、请求取消与声明上限可控制重复和过期工作，但不会消除合法新输入的查询成本。本批未进行并发压力或性能基准测试。

业务文字需要明确当前页口径：当前窗口中的风险项目数、评估结果或局部汇总不能标成全部项目的结果。需要全业务统计的组件应使用另一个明确完整的数据源。导出入口也应说明窗口级联链的导出范围，不能仅靠“完整导出”标题让消费者推断全业务范围。

## 本次保留的功能边界

- 提取字段仍是原始string/number维度，目标仍是下游dimension条件。可以按金额等度量过滤后提取编号，不能把金额值集合直接作为下游指标谓词。
- where使用受控字面量条件，未增加表达式、脚本、参数/筛选引用或按当前排序列自动切换条件的分支。
- 多个结果绑定提供各自去重集合并以AND组合，不承诺多个字段之间逐行元组对应。
- 本次查询排序联动开放给查询分页源；被引用的完整结果与固定TopN仍不接受运行时排序覆盖。若需要这些源也成为通用排序触发点，应另外确定完整结果或TopN业务范围如何保持。
- 查询窗口不会被转换为完整统计输入；原始查询输入不读取compute产出。DQE查询执行接口与数据网关端口未新增，复用既有排序、分页及维度条件编码。

本地仿真HTTP、浏览器、共享单次执行、导出及TS/Python测试提供本地证据；真实DQE/Relay/Java、真实DS模型、CI及部署未在本批验收。
