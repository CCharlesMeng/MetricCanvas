## 0. 诊断表经 DQE 查询（已确认）

`IOC_COCKPIT_TOP_CUSTOMER_REVENUE_DIAG_REASON_M` 按可经 DQE 查询处理。参考实现是通过 MCP 工具 `get_waterfall_diagnose_top_cloud_service` 读它的，不走 DQE；确认走 DQE 后，归因证据就是普通取数单元，复用 ADR-0032 的清单校验与真实执行，不需要按 ADR-0034 新增数据网关适配器。

这是唯一一项会改变模块拓扑的输入，其余各项只是往既定结构里填值。

该表已知属性（来自 `ioc-waterfall-introduction.md`）：聚合粒度为**客户 + 云服务**，存储流水金额、变化量、变化率与归因因子 `reason_info`。仍需数据侧确认的细节：可用时间范围、刷新时点、以及**账期字段是哪个**。参考实现有一条规则是「NL2SQL 与诊断工具的账期必须一致，不一致就只出概况不出明细」，说明这两条链路的账期在生产上确实会漂。

## 1. 归因场景匹配规则（已关闭，不需要）

`attribution-scenario.md` 被 `ioc-waterfall-introduction.md` 引用两次（第 145、168 行）但从不存在。**本平台不需要它。** 数据流是：

```
流水明细数据 → 场景匹配引擎（reason_info） → 归因结果数据（数据表存储）
```

场景匹配引擎在表的上游，`reason_info` 到达表时已经打好标签。匹配谓词属数据侧流水线的内部业务逻辑，本平台消费的是打好标签的输出。

本平台真正需要的是 `reason_info` 取值到因果方向的映射，而这份内容在 `ioc-waterfall-introduction.md` 的话术生成规则表中是完整的：

| 因素类型 | `reason_info` 取值 | 因果 |
|---|---|:---:|
| 代金券类 | 月结产品使用代金券、非月结产品使用代金券 | 反向 |
| 用量变化 | 用量 | 同向 |
| 新增类 | 新购、升配、增配、续订 | 同向 |
| 减少类 | 退订、降配、减配、未续订 | 反向 |
| 账务调整类 | 预估金额调整、账单调整、辅账逆向、缴费核销、手工核销、欠费、按需转包周期、包周期转按需、一次性确认流水 | 中性 |
| 常规交易类 | 常规一次性、包周期其他 | 中性 |
| 跨站报备 | 跨站报备 | 固定文案 |
| CDN 合作项目 | 包含「CDN合作项目」（模糊匹配） | 中性 |
| 默认兜底 | 其他所有情况 | 中性 |

反向指「因素减少 → 流水上升」（代金券减少 → 实付多 → 流水升），同向指「因素增多 → 流水上升」，中性只说明引起上升/降低而不做因果推断。

**最后一行的兜底使这个取值集合不必是闭集**，上游新增场景不会打穿映射，只会落到中性。这消除了原本对取值集合稳定性的担忧。

## 2. 指标条目字段（挂起）

按 ADR-0043，流水将来以一等指标条目的形式进入数据上下文快照。需要：稳定标识、业务名、别名、口径说明、单位、是否为比率、**可加性与时间聚合方式**、可用维度、所属业务域。

**可加性不能省。** ADR-0031 已裁决「声明缺失时拒绝派生，错数比拒答更贵」，而归因的每一步都在跨粒度聚合。

**维度层级关系是当前最硬的缺口。** `waterfall-config.md` 列了 18 个可用于筛选与归因的维度，默认首层归因维度是客户，但配置里没有层级声明——它用 `agg_dim` 表达下钻，且除客户与云服务外的维度都在第二层塌缩回「客户 × 云服务」。需要确认哪些是真层级：

- 地区部 → 代表处 → 城市
- 父客户 → 客户
- 公有云赛道 → 公有云子赛道 → 云服务

没有层级声明，ADR-0043 的「最多 3 层下钻」在数据里无法表达。当前快照里每个业务域只有 2 个非时间维度、零层级，连测试都构造不出来。

顺带需要确认：`packages/data-gateway/fixtures/metric-base-info.json` 里的英文 `metric_code` 与 DQE 使用的中文指标名是否指向同一批实体（ADR 基线已将此列为未决事项，明确「不得假设映射」）。若流水在两边都有名字，请给出对应关系。

## 3. 比较基线的业务约定（部分确认）

**已确认：环比基期 = 上一自然周期。**

同比在参考流程里未被使用——Step 1.3 只查累计值、变化金额与环比，且年粒度明确不支持（月 ✅ / 日 ✅ / 年 ❌）。因此「同比是比同月还是同期累计」不阻塞第一个切片，但它仍是 ADR-0037 黄金问题集的未决输入。

**仍未确认：「本月」是否含当天。** 暂按表中可用账期兜底，不硬编码。

基线选错的代价是结论正负号反转，而报告会看起来完全正常。参考实现「必须按实际数据描述方向，即使与用户说法矛盾」这条规则，前提就是基期本身没错。

## 4. 参考实现的矛盾（已裁决）

**≥5% 影响因子阈值：不采用。** 该阈值只出现在 `ioc-waterfall-introduction.md` 第 3.2 节，SKILL 3.1.0 的配置驱动路径并不复现它。裁决为**以诊断工具返回的贡献度为准**。

**专家经验接口 `/rest/cdi/cdinl2databuilderservice/v1/abnormal-cause`**（入参 `customer_code` + `time_dimension`，返回 `expert_reason`、`update_time`、`update_user`；文档中 POST 与 GET 自相矛盾，需数据侧给出实际方法）：**人工录入的原因算作证据，展示优先级高于系统诊断结论。** 按 ADR-0043 的分级它属「原因假设」，因此展示顺序与证据等级分成两根独立的轴——它排在归因发现之上、波动事实之下，块上如实标注等级并带出录入人与录入时间。

其余未裁决的文档不一致（SKILL 的「公有云流水」与配置的「流水」、`scenario=归因分析` 与 `attribution_analysis`）在接入时以实际接口返回为准，不据文档推断。

## 5. 黄金案例与异常样例（挂起）

需要：

- 一组经确认的真实 DQE 查询体及其输出字段
- 三个异常样例：无数据、零分母、权限不足
- **一个业务认可的完整归因案例**：某个月某个对象的流水波动，业务侧认可的结论是什么

最后一项是归因内核的黄金测试。没有它无法证明贡献度、覆盖率与对账算对了，也无法给出可比较的准确率基线。

## 与既有未决事项的关系

- **数据权限归属**（行级与指标级过滤由 DQE 还是本平台承担）尚未裁决。参考实现最重要的安全规则是筛选维度必须全量转发、漏一个即越权；自动下钻会主动查询用户未提及的维度，因此 ADR-0043 在裁决前采用保守下钻边界。
- **查询成本与配额**尚未确定。归因的多轮下钻会显著放大单次分析的数仓成本，现有每轮 6 次的执行预算常量需改为按形态传入的策略参数。
- **真实身份接入**是上生产前置条件。归因诊断把会话中的敏感内容量放大一个量级。
