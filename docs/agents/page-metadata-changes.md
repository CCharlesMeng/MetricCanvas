# 页面元数据定义与修改流程

页面元数据是对外契约。新增或修改字段前，先从作者实际要写的完整 JSON 判断是否容易理解，再实现 Schema 和运行行为。命名一致性由实现者自检，不应依赖用户逐字段发现问题。

本文补充[功能与协议能力验收要求](feature-acceptance.md)，不增加重复审批。用户已经确认的需求直接实施；只有尚未确定且会改变业务含义的选择才需要澄清。

## 先写声明，再写实现

每次协议变更先在实施说明中给出最小完整声明，以及受影响的同层字段。小修改用几行说明即可，不要求额外计划文件。

本次 AI 总结的完整组件声明是：

```json
{
  "id": "usage-summary",
  "type": "aiSummary",
  "layout": { "span": 12 },
  "props": {
    "mode": "generated",
    "promptTemplate": "分析当前期间的用量变化。",
    "relatedDataSources": ["usage", "comparison"]
  }
}
```

与同层的 `relatedSections: ["usage-region"]` 对照，两者都选择一组对象，故使用复数。显式数据源优先于内容分区推导；不是把两组范围自动相加。字段名、值形态、优先级和省略含义要一起定，不能只在讨论中说“支持传数据源”。

实施前明确以下信息：

| 核对项 | 必须说清的内容 | 本例 |
| --- | --- | --- |
| 业务含义 | 作者希望表达什么关系 | 摘要分析哪些页面数据源 |
| 路径与基数 | 所属对象，单值/数组/映射 | `aiSummary.props.relatedDataSources`，ID 数组 |
| 引用与所有者 | 引用什么；定义由谁拥有 | 引用 `page.dataSources` 的键，不复制字段定义 |
| 省略与空值 | 未声明、空数组、空字符串是否等价 | 未声明可用 relatedSections；空数组非法 |
| 组合规则 | 与同层字段的互斥、优先级 | 显式数据源优先；新旧拼写不能同时声明 |
| 运行行为 | 条件变化如何影响查询、状态和缓存 | 使用当前有效查询与非明细快照；ID 顺序不影响生成输入 |
| 错误与版本 | 错误位置、读取兼容和能力下限 | 未知/重复 ID 报准确路径；正式复数为 6.53 |

## 以现有词汇和形状约束命名

先查 `CONTEXT.md`、相邻 Schema 与现有真实声明，再命名。新增概念不要仅凭临时英文翻译决定。

- 单个引用采用单数；一组对象采用复数。优先延续同层已有组合，例如 relatedDataSources / relatedSections。
- ID 数组与按 ID 索引的映射都可能使用复数，因此必须同时展示实际 JSON。不要仅凭名字推断值类型，也不为追求统一擅自更名已有稳定字段。
- 定义放在其所有者处，使用处尽量引用。页面数据源已经拥有字段类型、角色、标签、单位等信息，摘要不再维护第二份 field/term 对照。只有确有局部差异的需求才设计覆盖机制。
- 页面声明业务意图与引用；云宝端点、鉴权、SSE 事件和任务队列等实现细节不进入页面元数据。

命名审核不仅查拼写，还要查主语、单复数、数量形态和同层对称性。不能用“接口小”“字段少”代替语义检查。

## 从产品真源改，按影响面生成

1. 修改产品 `packages/page/src/schema/`，从 Schema 派生类型和公开结构；引用规则与运行行为沿现有职责实现。
2. 同批更新能力下限、语义校验、完整 Playground 页面、产品参考正文与引用索引。版本规则见 ADR-0051；当前版本以 `versionPolicy` 为准，不在各处另写规则。
3. 从这些真源运行 `pnpm authoring:contracts`，生成契约、协议知识、独立校验器和 local-authoring 分发清单。生成差异回到真源解释，不手改派生文件，也不把并行任务的未提交变更混入生成结果。
4. 更名时区分当前正式声明和历史读取兼容。已发布字段不能因为是拼写问题就默认零使用；旧字段保留时集中解析，不在每个消费者重复维护新旧分支。当前范例和创作指导只推荐正式字段，旧拼写只在兼容说明与兼容测试中出现。真正的写出器也须纳入影响清单，不能只改文档便声称输出已迁移。
5. 新旧字段同时出现时明确诊断；不要悄悄任选一个、合并范围或扩大数据量。删除已发布字段必须按版本规则论证，不能以“全部替换”代替兼容决策。

## 用契约检查补足行为测试

本次错误说明：Schema、示例和测试可以同时沿用错误字段名，并一起通过。行为测试不能代替声明质量检查。

针对本批明确的字段，测试直接使用需求确认过的字面量，独立断言正式字段名和实际值形态。例如验证页面确实声明 `relatedDataSources`，且不再写出单数；这个期望不能从被测 Schema 动态推导。无需为所有英文名引入通用复数推断器或大规模重命名。

协议变更至少核对三类输入：

- **正式声明**：完整页面能校验和运行；集合的数量、范围、顺序及省略行为符合约定。
- **错误声明**：错误拼写、错误值形态、空值、未知引用、重复引用或冲突字段被拒绝，并报告能定位的路径。
- **历史声明**：原版本仍可读，原语义和错误位置保持；新能力不能在旧版本中偷渡，新旧别名不能同时生效。

运行行为继续按实际影响验证取数、时间切换、缓存、显隐、活动 Tab 和导出，不因字段更名机械重跑无关外部联调。纯重构需要保持完整有序错误列表及输入不变性；新增函数和修改函数按复杂度规则逐个实测。

## 完成口径

交付说明分别给出：正式 JSON、兼容方式、实际检查结果、未覆盖的外部服务、提交与远端状态。静态校验、浏览器、DQE Sim、Mock 和真实服务是不同证据；`[skip ci]` 只表示跳过 CI。

最终应能沿一条链路追溯：用户确认的声明 → 产品 Schema 与语义 → 版本和诊断 → Playground → 生成知识与独立校验器。该链路既要能证明“代码按声明执行”，也要能检查“声明本身是否合理”。
