# IOC 作战地图 — 前端计算能力对账清单

## 0. 这是什么

我们在重建 IOC 作战地图的过程中，把原系统散落在前端的计算收编成了页面数据源上的一个**受控计算阶段**：只提供封闭的具名算子，不提供公式字段、表达式或任何可求值的字符串。第一批五个算子已经落地。

现在需要你帮我们回答一个问题：**这个闭集够不够用。**

我们自己已经识别出五类它表达不了的计算，也追出了各自的结构原因。但我们的识别是从 IOC 三个页面的十几处计算反推出来的，样本太小——而原系统里有一份全仓前端计算场景汇总（我们了解到有 95 个以上场景，此前只要过其中的 77~99），那份材料才是判断闭集覆盖率的真正依据。

**这份清单要的不是代码贴回，是分类结论。** 你读原系统的计算逻辑，按第 3 节的四个判据给每个场景打标，我们据此决定要不要扩闭集、扩哪里。打标结果比任何一段源码都有价值——因为我们缺的不是实现细节，是"这类计算到底存不存在、有多少处"。

## 1. 我们已经做了什么

计算是页面数据源的一个可选阶段：输入是这个数据源查询返回并归一化后的行集，输出仍然是同一个数据源的行集。算子按声明顺序作用，后一个算子看到前一个算子的产出。计算产出的字段必须就地声明在这个数据源的字段契约里，和查询字段一样声明类型、角色、单位与可空性。

已交付的五个算子：

| 算子 | 做什么 | 参数 | 对行数的影响 |
|---|---|---|---|
| `ratio` | 两个字段相除 | 分子、分母、产出字段名、**分母为零时取空还是取零**（必须显式声明）、输出刻度（可选，只允许 100） | 不变，每行加一列 |
| `delta` | 两个字段相减 | 被减数、减数、产出字段名 | 不变，每行加一列 |
| `groupSubtotal` | 按一个字段分组，每组追加一行小计 | 分组字段、要求和的度量字段、小计行标记、可选的标签后缀 | 增加 |
| `grandTotal` | 追加一行全局合计 | 要求和的度量字段、合计行标记、合计行标签 | +1 |
| `pivot` | 行转列：「一行一个类别」折成「一行多列」 | 类别字段、取值字段、每个目标列一个**有序**类别列表（取第一个命中的） | 减少 |

三条硬约束，是理解后面五个缺口的前提：

- **算子的参数只能是字段引用或封闭枚举**，不能是可求值的字符串。这是为了让页面文档可被完整校验、AI 写错时能被自动修复。
- **格式化不算计算**。亿/万自适应、百分比、千分位、`_label` 伴生字段，在我们的模型里全部归组件的字段绑定，不进计算阶段。所以你在原系统里看到的 `xxx_label`、`xxx_show` 这类字段，**不用报给我们**——它们不是计算缺口。
- **不提供条件算子或分支**。唯一的择一手段是 `pivot` 目标列的有序类别列表。

## 3. 五个缺口与求证方法

五个缺口收敛到四个结构原因。**其中两个是我们主动裁决的（有明确代价论证），另外两个是当初盘点时根本没看见的**——后者才是这份清单的重点。

| 缺口 | 结构原因 | 性质 |
|---|---|---|
| 3.1 跨数据源对齐 | 计算阶段的作用域被定死为「单个数据源的一份行集」 | 主动裁决 |
| 3.2 行间与窗口计算 | 行集没有一等的「序」 | **盘点遗漏** |
| 3.3 占比 | 折叠结果是「新行」不是「新列」 | **盘点遗漏** |
| 3.4 排名与 Top-N | 同 3.2，无序 | **盘点遗漏** |
| 3.5 条件派生 | 封闭性禁止条件与表达式 | 主动裁决 |

### 3.1 跨数据源对齐

**我们已知的实例**：管道支撑率。分子来自机会点汇总表，分母是「收入目标 − 存量预测 − 年初至今已实现」三张表分别按 `地区部代码 + "_" + 代表处代码` 聚合后相减。汇总层级与概览表行级各算一次，公式相同、聚合粒度不同。

**我们为什么做不了**：求值入口只收一份行集，编排层按数据源逐个调用，算子拿不到别的数据源。这是决策本身而非实现疏漏——跨源要先回答一批边界语义（某个源没返回这个 key 怎么办、一个源查询失败怎么办、缓存与取消怎么算），我们没有足够案例来定这些答案。

**我们的推断**：全仓跨源计算可能就管道支撑率这一处（含它的两个粒度）。如果确实如此，我们打算不做跨源算子，改让服务端把四个字段放进同一个结果集，用 `delta` → `delta` → `ratio` 表达。

**请求证**：

| # | 问题 | 判定标准 |
|---|---|---|
| G1-1 | 全仓一共有多少处计算，其输入来自**两个及以上**数据源？逐处列出：页面、字段名、涉及哪几个数据源、聚合 key 怎么组装 | 只有 1~2 处 → 我们不做跨源算子；5 处以上 → 我们必须做 |
| G1-2 | 是否存在**超过 3 个源**对齐的实例？最多的一处是几个源？ | 决定跨源算子的输入是「一个附加源」还是「一组源」 |
| G1-3 | **某个源没有返回这个 key 的行时，当前代码怎么处理？** 当作 0 参与运算，还是整个结果取空？请贴回那段判断原文 | 这是我们定跨源算子最缺的一个答案 |
| G1-4 | **某个源查询失败时，界面显示什么？** 整卡报错、显示空、还是显示用剩下的源算出的错误值？ | 同上 |
| G1-5 | 聚合 key 的组装规则在不同粒度下是否一致？（已知全球/地区部级用一个字段、代表处级用两个字段拼接） | 决定 key 要不要支持多字段 |

**怎么找**：

```bash
# 在 fitFunction 里找同时引用多个数据源 id 的
rg -n "fitFunction" -A 40 --type ts | rg -n "dataSource|globalVars\."

# 按已知的 key 拼接方式找同类实现
rg -n '\+ "_" \+|`\$\{.*\}_\$\{.*\}`' --type ts

# 找聚合动作
rg -n "reduce\(|new Map\(|forEach.*set\(" --type ts
```

### 3.2 行间与窗口计算

**这是我们没看见的一类。** 我们已知的两处环比（机会点数较上月、总预签金额较上月）都是**同一行内两列相减**——本月值和上月值由查询成对返回。这种我们能表达。

**我们表达不了的是**：结果集按时间一行一期，要算「本行比上一行增长多少」。因为算子拿不到"上一行"——计算阶段没有序的概念，而排序在我们这边只存在于呈现层（表格的排序是视图状态，不回写数据）。

**我们的推断**：原系统里所有同环比都是成对返回的，不存在真正的行间计算。如果这条成立，我们就不补窗口算子。

**请求证**：

| # | 问题 | 判定标准 |
|---|---|---|
| G2-1 | 有没有任何一处计算，**先对数组排序、再按下标取相邻元素**（`arr[i-1]`、`index - 1`、`prev`）？ | 有 → 我们必须补窗口能力；没有 → 不补 |
| G2-2 | 有没有前端做的**累计**（YTD、累计完成、滚动求和）？还是所有累计值都由服务端返回？（已知 `ytd_amt` 是收入表直接返回的一列） | 前端累计 → 需要窗口；服务端返回 → 不需要 |
| G2-3 | 同环比的上期值，**全部**都是查询成对返回的吗？有没有哪一处是前端自己再发一次「上月」的查询然后对齐的？ | 后者等价于跨源对齐，归 3.1 |

**怎么找**：

```bash
rg -n "\.sort\(|sort\(\(|\[i - 1\]|\[index - 1\]|prev[A-Z]" --type ts
rg -n "ytd|累计|cumulative|runningTotal" --type ts
```

### 3.3 占比

**这一条最需要你确认，因为我们发现了一处矛盾。**

原系统的指标规格里，前端计算字段被归纳为「比率、差值、**占比**、分组聚合」四类，但同一份文档逐条列出的七个前端计算指标里，没有任何一个是占比——全是比率（分子分母都是独立字段）和差值。

**占比和比率不是一回事**：比率的分子分母都是行内的两个字段，我们能算；占比的分母是「本组合计」或「全表合计」，我们**算不了**。原因是我们的小计与合计算子产出的是**追加的一行**，不是回填到每一行的一列，而除法只能取行内字段——分母根本不在能取到的位置上。

**请求证**：

| # | 问题 | 判定标准 |
|---|---|---|
| G3-1 | 「占比」这一类具体指哪几处计算？逐处列出：页面、字段名、公式 | 决定这条缺口是否真实存在 |
| G3-2 | 每一处占比的**分母来自哪里**？选项：(a) 服务端返回的一列合计值；(b) 前端先把全部行加总再逐行相除；(c) 前端按某个字段分组加总，再让组内每行除以本组合计 | (a) → 我们不用补；(b)(c) → **我们必须补**，且 (c) 比 (b) 更难 |
| G3-3 | 如果是 (b) 或 (c)：分母的求和范围是**当前页**还是**全量数据**？分页时占比会变吗？ | 涉及我们和分页的交互语义 |
| G3-4 | 图表（尤其是饼图、环形图）的百分比，是前端算的还是服务端给的？ | 饼图百分比通常由图表库自算，属呈现不属计算，需要区分开 |

**怎么找**：

```bash
rg -n "占比|percentage|percent|proportion|share" --type ts
# 先求总再逐行除的典型形态
rg -n "reduce\(.*\+.*\)" -A 10 --type ts | rg -n "/ *(total|sum|all)"
```

### 3.4 排名与 Top-N

**我们已知**：概览页有 TOP 表和丢单表，排序走查询侧的排序模板条件；概览表本身是数据全量加载到前端后用比较函数排序的，不走服务端。

**我们的落点不同**：我们的表格排序是纯呈现层的视图状态，不改变数据；而且我们目前没有任何算子能改变行序或截断行集。所以：

- 如果「TOP 10」是**查询侧排序 + 取前 N 条**，我们能对上（把排序和条数写进查询定义即可）。
- 如果名次列（1、2、3……）是**前端排序后按下标生成的一列**，我们表达不了。
- 如果有「排序后再基于名次做计算」的逻辑，我们同样表达不了。

**请求证**：

| # | 问题 | 判定标准 |
|---|---|---|
| G4-1 | TOP 表的 N 是多少？写死在代码里还是可配置？是查询侧 `limit` 还是前端截断？ | 查询侧 → 我们能对上；前端截断 → 需要新增截断能力 |
| G4-2 | 界面上显示的**名次数字**，是服务端返回的一列，还是前端按排序后的下标生成的？请贴回生成那一行 | 后者 → 我们表达不了，需要裁决 |
| G4-3 | 概览表用前端比较函数排序——**排序之后有没有基于排序结果的再计算**？还是排序纯粹只影响显示顺序？ | 纯显示 → 归呈现层，我们已支持；有再计算 → 缺口 |
| G4-4 | 前端排序的**并列处理**：主排序键相等时怎么办？（已知有一处是按代表处名称降序兜底）这个兜底规则是每张表各写各的，还是有统一实现？ | 影响我们要不要把多列排序做成声明 |

**怎么找**：

```bash
rg -n "compareFn|localeCompare|sort\(" --type ts
rg -n "rank|index \+ 1|序号|名次|TOP|slice\(0," --type ts
```

### 3.5 条件派生

**边界要先划清**：我们把两件事分得很开——

- **条件格式化**：按值决定颜色、图标、显示文案。这在我们这边归组件，**不是缺口**，不用报给我们。
- **条件计算**：字段的**值本身**按分支不同而不同。这才是缺口。

我们已知的唯一一处条件计算是客户关系规范性那里的「专题交流优先，没有则取技术交流」。这种"有序候选、取第一个命中"我们能表达（行转列算子的目标列接受一个有序类别列表）。**我们表达不了的是带比较运算的分支**，比如「金额大于某阈值时按 A 口径、否则按 B 口径」。

**请求证**：

| # | 问题 | 判定标准 |
|---|---|---|
| G5-1 | 全仓有多少处计算，其**产出值**取决于一个条件判断（不是取决于格式化）？逐处贴回那段三元表达式或 if 分支的原文 | 逐处判断能否用「有序候选」改写 |
| G5-2 | 这些条件里，有多少是**空值兜底**（"没有 A 就用 B"）、多少是**阈值比较**（"大于 X 时……"）？ | 前者能用有序候选表达；后者不能，需要单独裁决 |
| G5-3 | 空值判断有几套不同实现？（我们了解到至少有三个工具函数，其中一个把 `0` 也当作空）不同的计算分别用了哪一套？ | 直接决定我们的零值语义要不要分档 |

**怎么找**：

```bash
rg -n "fitFunction" -A 40 --type ts | rg -n "\? .* :|if \("
rg -n "isNull|isNotEmpty|validate\(" --type ts
```

## 5. 两处已发现的矛盾，请确认

这两处是我们在读规格时发现的，都指向"同一个业务口径存在多份实现"。这件事对我们很重要——它是我们判断"计算该不该收编到一处"的直接证据。

### 5.1 立项率有两份实现，语义不同

同一个「立项率」，在指标卡和概览表行级是两套算法：

| 落点 | 是否乘 100 | 分母为零时 |
|---|---|---|
| 指标卡 | 乘 | 返回空 |
| 概览表行级 | **不乘**（留给格式化时再乘） | **返回 0** |

**请确认**：这是有意的（两处业务含义确实不同），还是一处历史遗留的不一致？如果是不一致，界面上这两个数字会不会在分母为零时一个显示空、一个显示 0%？

顺带一提，管道支撑率分母为零时返回 0，而立项率（指标卡）返回空——**同一个页面里两种零分母语义并存**。这正是我们要求每个除法都必须显式声明零分母语义的原因，但我们想知道原系统这两种选择是业务要求还是各写各的。

### 5.2 「占比」这一类在逐条清单里找不到

指标规格把前端计算字段归纳为「比率、差值、占比、分组聚合」四类，但逐条列出的七个计算指标里没有占比。

**请确认**：是那份归纳写宽了（实际不存在占比），还是逐条清单不全（占比在别的页面）？这一问的答案直接决定 3.3 那个缺口是真是假。

## 7. 如果时间只够做一件事

**做第 4 节的全量场景分类表，哪怕每个场景只填 A~E 五列、描述留空。**

理由：第 3 节的五个缺口是我们**已经猜到**的，即使你不回答，我们也能按推断先做、后面再校正。第 4 节不一样——它回答的是"我们有没有猜漏"，而这个问题我们自己无论如何回答不了，因为我们的样本只有三个页面。

一份只填了五列打标的表，就能让我们算出闭集的真实覆盖率；而一份写得很详细但只覆盖已知三页的材料，价值反而低得多。

如果还有余力，第二件事是 5.1 和 5.2 两处矛盾的确认——它们各自只需要一句话，但分别决定我们要不要为零分母语义分档、要不要补占比能力。
