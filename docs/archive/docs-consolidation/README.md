# 过程性文档聚合瘦身（2026-09-21）

清理前 `docs/` 有 347 个文件，其中 68% 是过程件（计划、交接、grill 记录、票据实证、调研报告），散在六个地方。**问题不是"文件多"，是同类东西没有单一去处，所以谁也不知道该往哪放、什么时候该清。** 这批用一天做完，2026-09-21 收口。

## 最终生效的结论落在哪

这批的产物不是文档，是**三层结构加两道守门**，它们各自的规矩写在自己的入口页里，不在这里重复：

| 产物 | 规矩写在哪 |
|---|---|
| 四种寿命、四个去处；批次收口必做的三件事 | [`docs/plan/README.md`](../../plan/README.md) |
| 什么算论据、什么只是被引用 | [`docs/evidence/README.md`](../../evidence/README.md) |
| 归档批次的结论页三段式 | [`../README.md`](../README.md) |
| ADR 状态真源在 frontmatter，两张表由脚本生成 | [`docs/adr/README.md`](../../adr/README.md) |

**真正治本的那一条是"把手抄换成生成"**：83 份 ADR 的状态原先手抄在一张 90 KB 的表里，ADR 自己不知道自己的状态，两边必然漂移。现在状态写在每份 ADR 的 frontmatter，`pnpm adr:index` 生成速查表与主题索引，`pnpm adr:index:check` 守门。主题索引的"覆盖的 ADR"列也是从主题页正文**实际出现的链接**推出来的——写错就是链接错，链接错脚本直接报错。

附带一条防复发：**每份 ADR 的结论至少要落在一个主题页里**，否则索引末尾自动列出孤儿编号。它当天就在两份老 ADR 上抓到漏网，之后又在新落盘的 0084/0085/0086 上响过一次。

## 被推翻的方向与推翻它的依据

- **S1「机器证据出文档目录」裁决为不做。** 原方案要把测试夹具迁进 `tests/fixtures/`。执行时发现两件事：归档做完后 `docs/plan/` 只剩 6 个属于在做项的 json，原始理由消失；而剩下那两份夹具在批次内部有同目录假设（checker 用 `Path(__file__).with_name()` 找它，实证正文写着「同目录」），迁走就得改已冻结的记录。**改归档件的正文就改变了这份记录当时说了什么**——归档层唯一的价值就是这个。完整论证见方案 §4.6。
- **`tests/fixtures/` 这个落点本身也被否掉**：仓里没有这个目录，既有约定是夹具跟着消费者走。
- **「被代码或文档引用」不足以进证据层。** 方案原先按这条划，会把 `ioc-operation-map.md`、`t18-execution-contract.md` 这类执行件也划进去。执行时收窄为：**论据是报告/调研/基线，说明某个裁决为什么这么定；执行件是这批活怎么干的记录。被引用不等于是论据。** 否则证据层会慢慢变成第二个 `plan/`。

## 两个值得记住的坑

- **解码失败被当成"跳过"而不是"报错"**，是批量改写最容易静默出错的地方。两个 SVG 不是合法 UTF-8，改写脚本整份跳过，方案里点名过的引用方就这么漏了，只能靠事后字节级复扫发现。
- **"按解析结果重定位"对目标不存在的链接无效**——解析不到实体就跳过，于是同一文件里别的同类链接都对、偏偏那两条深度少一级。正确做法是对所有相对链接一律做路径算术，只在结果与原文不同时才写回。
