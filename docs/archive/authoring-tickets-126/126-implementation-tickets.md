## 规划定位

#95 继续负责静态 Platform 真部署、真实异构集成及盘古基础接入的终点；#126 在既有架构上增加创作生命周期与盘古独立开发要求。#126 不是 #95 的替代地图，也不承担其全部普通问数场景。

事实以当前代码和最新有证据评论为准，而不是旧正文的勾选状态：#104 在 2026-09-10 评论确认静态化提交 8ee924d 已推送；当前代码亦为 adapter-static。#108 的 2026-09-10 评论确认本地状态隔离已完成，生产 UI/真实产物读取与恢复未完成。#95 正文部分仍写 adapter-node，不据此新建静态化任务。

### 与旧规划有意不同的地方

- #95 早期移除发布治理前端；#126 已明确新增创作候选及人工确认发布。T19 建设新外部服务消费流程，不恢复旧 Node、数据库、独立模板库或 ACL 管理。
- #95 早期只消费 Java 已有接口；本轮授权产出修改方案。T04 可以设计拟新增能力，但不能称其已被提供方接受或已实现。
- #95 普通问数的临时页面态/检查点与本版创作草稿修订分开。T20 不能把全部 Ask 改成自动保存。
- 上游更新便利性属于新增验收要求：T01 建立配置及源码分离并演练；#107/#108 真实接入时沿同一方式验证。上游破坏性接口变更仍需升级适配层。

## 顺序、依赖与并行

先完成必要架构前置：T01 对话边界、T02 创作协调、T03→T05/T06→T07 布局协议迁移。T04 外部方案可同步推进。先完成这批再集中实施新业务能力，是用户要求的交付顺序；表中的 Blocked by 只记录真正技术依赖，不把这个排期约束伪造成每张票都相互阻塞。

布局字段跨约 101 个当前文件出现，按 expand–migrate–contract 分成四票：T03 先兼容读取；T05 浏览器、T06 Python 分别迁移；T07 收口。承诺保留的旧文档读取边界不会被 contract 阶段误删。T05/T06 的生成产物统一由 C0 管理。

T01/T02 都触及工作台共享接入点，合入由同一 C0 所有者串行处理，分别提供对话端口和创作协调端口，不同时改同一工作台整文件。两者没有互相运行依赖，所以不添加虚假阻塞边。拆票发布后，实施前把独占修改范围落实到具体文件。

同一模块内部仍有顺序：T08 建立内容操作入口后 T09/T10/T11 才能各自扩展；T13→T14→T15 逐步完成保存、恢复、历史；T16 属性面板消费保存入口。T17 拥有参数协议，T18 消费执行结果；T19 汇合发布。T20 先用代表性既有组件走通语言保存交接，不等待全部新组件操作完成。

共享注册器、导出源、协议快照及工作台组装点各指定一位所有者；其他任务通过扩展模块交付并由所有者合入。一个大目录不是排他所有权，也不能以“可并行”暗示在同一文件同时开发不会冲突。

## 外部门槛不等于整张旧票阻塞

- 本仓功能票以内部端口和确定性替身验收。内部提案与已确认外部契约分别标记，替身不得改写已知 HTTP 契约。
- 精确历史、幂等、参数提取/发布及执行服务须由 Java 方兑现；真实用户身份、工具路由和草稿通知须由 Relay/盘古兑现。对应事实登记在 T04 和 #105/#106/#108，不把整张 #105 或 #108 的关闭状态套到每张本地票上。
- 真实 SDK 接线、鉴权读取/完整性、会话恢复继续跟踪 #107/#108；真实载体及异构消费分别沿 #104/#103。它们的未完成不会被新票通过所掩盖。
- 后续真实联调若需要拆出更窄执行票，应按缺失能力再拆，避免一次性新建与 #103–#108 重复的全链路验收票。
- 新票建议作为 #126 的原生子 Issue，正文引用 #95 对应任务；新票之间建立原生阻塞关系。不会修改/关闭父 Issue；现有任务范围若需更新，单独展示增量后再处理。
